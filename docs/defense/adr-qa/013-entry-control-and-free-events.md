# ADR 013. Контроль входа, бесплатные события и лимит билетов — разбор к защите

Неделя 4 (02–08.11.2026). ADR: [`docs/adr/013-entry-control-and-free-events.md`](../../adr/013-entry-control-and-free-events.md).

## Суть в трёх фразах

На входе билет должен пройти один раз, хотя у контролёров нет учётных записей, а в фойе или подвале часто нет связи. Решение — ссылка сканера с секретным токеном: онлайн проход засчитывает сервер под блокировкой строки билета, без сети сканер ищет id билета в заранее скачанном списке, а при синхронизации засчитывается самое раннее сканирование. Тот же ADR вводит два вида бесплатных событий (свободный вход без билетов и билеты с ценой 0) и лимит билетов на покупателя за всё событие, чтобы перекупщик не набирал билеты несколькими заказами.

Что добавили более поздние ADR:
- [ADR 016](../../adr/016-organizer-cabinet-and-scanner.md): сделан экран сканера — PWA с камерой и очередью офлайн-сканирований. API этого ADR не менялось.
- [ADR 020](../../adr/020-waiting-room-and-ip-limit.md): к лимиту на покупателя добавлен мягкий лимит билетов на IP-адрес, по умолчанию 40.
- [ADR 028](../../adr/028-postgres-failover.md), строки 64–69: уникальность по `client_scan_id` названа защитой прохода от повторов при сбое базы. Механизм тот же.

## Почему так, а не иначе

- **Секрет подписи на сканере для офлайн-проверки.** Проще, но секрет один на всю платформу (`TICKET_SIGNING_KEY`, `internal/platform/config/config.go:54-55`). Утечка с одного телефона позволила бы печатать билеты на любое событие.
- **Учётные записи контролёров.** Противоречат spec.md: вход один, у организатора (spec.md:121). Ссылку проще выдать на смену и отозвать.
- **Время устройства и для онлайн-сканирований.** Отвергнуто после теста конкурентности: два контролёра могли оба получить «проход разрешён». Онлайн время ставит сервер.
- **Свободный вход как событие с «пустой» схемой.** Организатору пришлось бы рисовать фиктивный зал, например для парка. Вместо этого схема у такого события запрещена ограничением в базе.
- **Лимит на заказ.** Не защищает от перекупщика: он делает несколько заказов подряд.

## Чем подтверждено

- **Один засчитанный проход под конкуренцией:** 30 одновременных онлайн-сканирований одного билета — 1 `accepted`, 29 `duplicate`, в базе одна засчитанная строка. `internal/ticket/scanner_test.go:243-274`; evidence.md:103.
- **Онлайн время устройства не перебивает проход:** сканирование с часами в прошлом получает `duplicate`. `TestOnlineScanIgnoresDeviceClock`, `scanner_test.go:385-398`.
- **Офлайн засчитывается самое раннее:** позднее сканирование синхронизировалось первым, раннее пришло потом и стало засчитанным, первое стало повтором; время из будущего заменено временем сервера. `TestOfflineSyncFirstScanWins`, `scanner_test.go:200-239`.
- **Все пять итогов и повторная отправка:** `accepted`, `duplicate`, `invalid` для подделки, мусора и пустой строки, `revoked`, `wrong_event`; тот же `client_scan_id` даёт тот же итог и одну строку в базе. `TestScanResults`, `scanner_test.go:123-195` (повтор — `:149-162`).
- **Ссылка сканера:** в базе хеш, а не токен; отзыв, повторный отзыв, отзыв чужим организатором. `TestScannerLinks`, `scanner_test.go:77-121`. По HTTP без токена и с отозванной ссылкой — 401: `TestScannerHTTP`, `scanner_test.go:306-381`.
- **Список для работы без сети:** id из токена QR находится в списке билетов. `TestManifest`, `scanner_test.go:276-304`.
- **Свободный вход:** событие со схемой и цены отклоняются, публикация без мест, на публичной странице `layout: null` (`internal/catalog/free_entry_test.go:12-65`); заказ отклоняется кодом `free_entry` (`internal/booking/orders_test.go:516-523`).
- **Бесплатные билеты:** заказ сразу `paid`, одно событие `order.paid`, платные места того же события ждут оплаты (`internal/booking/payments_test.go:267-289`). Сквозной путь до выпуска билета, оплату начать нельзя: `cmd/worker/flow_test.go:279-297`.
- **Лимит за всё событие:** после оплаченного заказа второй заказ сверх остатка — `ticket_limit_exceeded`, в пределах остатка проходит, другой покупатель лимит не делит (`payments_test.go:242-264`). 10 параллельных заказов одного покупателя дают 1 корзину: `orders_test.go:336-362`; evidence.md:91.
- **Нагрузкой не проверялось.** Ни один эксперимент в `docs/experiments/` не нагружает сканер. Реестр помечает тест на 30 сканирований как «контроль входа, не продажа» (evidence.md:103).

## Вопросы комиссии

1. **Что такое ссылка сканера и почему у контролёров нет учётных записей?**
   Ответ: Организатор создаёт для события ссылку с секретным токеном и отдаёт её контролёру. Ссылка даёт право только читать список билетов этого события и отправлять сканирования, её можно отозвать. Учётные записи контролёров противоречат spec.md: вход в кабинет один, у организатора.
   Источник: ADR 013, «Ссылки сканера» (строки 21–24), «Альтернативы» (строка 63); `internal/ticket/scanner.go:48-72, 92-110`; spec.md:121.

2. **Как защищён токен ссылки?**
   Ответ: Токен — 256 случайных бит, в базе лежит только его SHA-256, показывается он один раз. Токен стоит во фрагменте адреса `/scan#<токен>`: браузер не отправляет фрагмент на сервер, поэтому токен не попадает в логи. Отозванная ссылка получает 401 и для списка билетов, и для сканирований.
   Источник: ADR 013, строки 22–23; `scanner.go:56, 68-70, 143-145, 340-343`; `migrations/00010_scanner_links.sql:4-16`; `internal/ticket/http.go:244-260`; `scanner_test.go:77-121`.

3. **Как сканер проверяет билет без сети и почему ему не выдали секрет подписи?**
   Ответ: Сканер заранее скачивает список билетов события: id, статус, место. В QR лежит токен — id билета и HMAC от него, без сети сканер достаёт id и ищет его в списке. Секрет подписи один на платформу, с украденного телефона можно было бы подделывать билеты на любое событие. Подобрать чужой id нельзя: в UUIDv7 из PostgreSQL 18 62 случайных бита (`uuidv7()` в `migrations/00002_core_schema.sql`).
   Источник: ADR 013, «Работа без сети» (строки 29–31), «Альтернативы» (строка 62); `internal/ticket/token.go:27-47`; `config.go:54-55`; `web/src/lib/scanner.ts:37-46`.

4. **Два контролёра онлайн одновременно сканируют один билет. Что будет?**
   Ответ: Сервер блокирует строку билета `FOR UPDATE`. Первое обработанное сканирование переводит билет в `used` и получает `accepted`, остальные видят `used` и получают `duplicate` со временем первого прохода. Схему страхует частичный уникальный индекс: одна строка `accepted` на билет. В тесте 30 одновременных сканирований дали 1 `accepted` и 29 `duplicate`.
   Источник: ADR 013, строки 37, 40; `scanner.go:272-307`; `migrations/00010_scanner_links.sql:27-29`; `scanner_test.go:243-274`; evidence.md:103.

5. **Почему онлайн время ставит сервер, а офлайн учитывается время устройства?**
   Ответ: Онлайн решение принимается сразу, и часы телефона не должны его менять. Первая версия брала время устройства и онлайн, и тест конкурентности поймал, что два контролёра могли оба получить «проход разрешён». Без сети люди уже прошли, сервер только записывает итог, поэтому важно, когда это случилось на самом деле. Время дальше допуска в будущее (`clockSkew`) заменяется временем сервера.
   Источник: ADR 013, строки 37–39, 64; `scanner.go:221-222, 266-270`; `scanner_test.go:385-398`, `:232-238`.

6. **Два входа без сети пропустили один и тот же билет. Что запишет система?**
   Ответ: Физически прошли оба: без сети сканеры не знают друг о друге. При синхронизации засчитывается самое раннее сканирование по времени устройства, второе записывается как повторная попытка, как требует spec.md. Если раннее сканирование пришло позже, оно становится засчитанным, а прежнее понижается до `duplicate`. Организатор видит попытку в данных, но предотвратить её без сети нельзя.
   Источник: ADR 013, строка 38; spec.md:160; `scanner.go:295-304`; `scanner_test.go:200-239`.

7. **Сканер отправил пачку, связь оборвалась, он отправил её снова. Не появятся ли двойные проходы?**
   Ответ: Нет. У каждого сканирования есть id от устройства, уникальный индекс `(scanner_link_id, client_scan_id)` не даёт записать его второй раз. Повтор получает сохранённый итог. Если два одинаковых запроса пришли параллельно, проигравший ловит нарушение индекса и тоже отвечает записанным итогом. Так правило 3 выполняется без общего middleware идемпотентности.
   Источник: ADR 013, строка 36; `scanner.go:257-259, 313-317`; `migrations/00010_scanner_links.sql:19-25`; `scanner_test.go:149-162`; ADR 028:64-69.

8. **Чем свободный вход отличается от бесплатных билетов?**
   Ответ: Свободный вход — страница без билетов, схемы и цен: `admission = free_entry`, ограничение в базе запрещает схему у такого события и требует её у событий с билетами. Бесплатные билеты — категория с ценой 0: заказ на сумму 0 в той же транзакции становится `paid`, места — `sold`, событие `order.paid` выпускает билеты тем же конвейером, что у платных. Бесплатные и платные категории можно смешивать, платный заказ идёт через оплату.
   Источник: ADR 013, «Бесплатные мероприятия» (строки 50–54); `migrations/00009_free_entry_events.sql:4-10`; `internal/booking/orders.go:444-450`; `internal/booking/payments.go:107-122`; `payments_test.go:267-289`.

9. **Почему лимит на покупателя за всё событие и как его обойти?**
   Ответ: Лимит на заказ перекупщик обходит несколькими заказами. Поэтому в заказе не больше мест, чем лимит минус уже купленные этим покупателем на событие: считаются места оплаченных и частично возвращённых заказов без аннулированных билетов. Две корзины одновременно не создать: у покупателя одна корзина на событие. Обход — несколько номеров телефона, против него ADR 020 добавил мягкий лимит на IP, 40 билетов на событие.
   Источник: ADR 013, «Лимит билетов» (строка 58), строка 66; `orders.go:223-235`; `internal/booking/queries.sql:202-210`; `payments_test.go:242-264`; evidence.md:91; ADR 020:22-28.

10. **Что в контроле входа не доказано?**
    Ответ: Тесты интеграционные: сканер под нагрузкой и размер списка билетов для стадиона не измерялись. Без сети сканер не проверяет подпись, поэтому подделку с настоящим id сервер отклонит только при синхронизации. Список устаревает: билет, купленный или возвращённый после последней загрузки, без сети определяется неверно. Сквозной прогон экрана сканера описан в ADR 016, но его сценария в репозитории нет.
    Источник: evidence.md:103; `web/src/lib/scanner.ts:34-46`; `web/src/views/ScannerView.vue:141`; ADR 016:116-120.

## Где слабое место

- **Без сети двойной проход физически возможен.** Два входа без связи не знают друг о друге, система только записывает итог (ADR 013:38). Почему приемлемо: spec.md:160 прямо задаёт такое поведение, а работа без сети — требование MVP (spec.md:42, 47). Что дальше: чаще обновлять список, пока есть сеть; при связи решает сервер.
- **Без сети подпись не проверяется.** Сканер верит id из токена (`web/src/lib/scanner.ts:34-46`). Подделку с настоящим id сервер отклонит при синхронизации, когда человек уже прошёл. Почему приемлемо: чужие id есть только в списке билетов, а его отдают по ссылке сканера, которую организатор отзывает. Что дальше: отдельный ключ подписи на событие — тогда его можно выдать сканеру, и утечка касалась бы одного события.
- **Отстающие часы телефона не исправляются.** Заменяется только время из будущего (`scanner.go:268`). Офлайн-сканирование с часами в прошлом выглядит более ранним и может забрать «засчитанный» у онлайн-прохода (`scanner.go:295-304`). Почему приемлемо: меняется только запись о том, какое сканирование первое; билет так или иначе `used`, на продажу мест это не влияет.
- **Список билетов устаревает.** Билет, купленный после последней загрузки, без сети — «не билет»; возвращённый — проходит (`web/src/lib/scanner.ts:41-43`). Список обновляется, пока есть сеть (`ScannerView.vue:141`).
- **Лимит обходится несколькими номерами.** Идентичность покупателя — номер телефона (spec.md:118). ADR 020 добавил лимит на IP, но он мягкий: два одновременных заказа с одного адреса могут его чуть превысить (ADR 020:27).
- **Откат миграции 00009** возможен, только если нет событий со свободным входом (ADR 013:71; `migrations/00009_free_entry_events.sql:13`).
- **Нагрузки нет.** Ни один из экспериментов не трогает сканер; доказательство — тесты с горутинами (evidence.md:103).

## Проверь себя

1. Онлайн-сканер засчитал проход в 19:05 по серверу, позже пришло офлайн-сканирование того же билета с временем устройства 19:00. Что запишет база, и что изменится, если часы того телефона отстают на час?
2. Почему для повторов сканирования хватает `client_scan_id` и не нужен общий ключ идемпотентности из ADR 008?
3. Что опаснее украсть — ссылку сканера или секрет подписи билетов? Что даёт каждое и как каждое закрывается?
