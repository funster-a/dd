# ADR 003. Проверки состояния и корректная остановка процессов

Статус: принято, 2026-09-28

## Контекст

api и worker работают в контейнерах и зависят от PostgreSQL, Redis и RabbitMQ. Оркестратору (сейчас Docker Compose, позже, возможно, что-то ещё) нужно знать, жив ли процесс и готов ли он принимать трафик. При перезапуске нельзя терять запросы и сообщения, которые уже в работе: для продажи билетов оборванный запрос может обернуться потерянной бронью.

## Решение

1. **Два эндпоинта с разным смыслом.**
   - `/healthz` — процесс жив. Зависимости не проверяет и отвечает 200, пока сервер работает.
   - `/readyz` — процесс готов. Параллельно проверяет PostgreSQL, Redis и RabbitMQ с общим таймаутом 2 секунды. Отвечает 200 или 503 со статусом каждой проверки. Подробности ошибок пишутся только в лог, наружу не уходят.
2. **Ленивые подключения.** Процесс стартует, даже если зависимости недоступны. Готовность отражает `/readyz`, соединения восстанавливаются сами, RabbitMQ — с нарастающей паузой.
3. **Корректная остановка по SIGTERM и SIGINT.**
   - api перестаёт принимать новые соединения и дорабатывает начатые запросы. Их контексты не отменяются сигналом.
   - worker перестаёт брать сообщения и дорабатывает текущее. Неподтверждённые сообщения возвращаются в очередь.
   - Весь выход, включая закрытие соединений, укладывается в `SHUTDOWN_TIMEOUT` (15 секунд по умолчанию). В Compose `stop_grace_period` больше этого значения, чтобы Docker не убил процесс раньше.
4. **Конфигурация только из переменных окружения** со значениями по умолчанию для локального запуска. Неверное значение останавливает процесс при старте, а не всплывает позже.
5. **Request id.** Middleware принимает `X-Request-ID` от клиента или генерирует новый, возвращает его в ответе и добавляет в каждую строку лога запроса. Небезопасные значения заменяются новыми.

## Альтернативы

- **Один эндпоинт health с проверкой зависимостей.** Если его использовать для проверки живости, то при недоступной базе оркестратор начнёт перезапускать здоровые процессы, и они лягут все сразу. Отклонено.
- **Падать при старте без зависимостей.** Порядок запуска становится хрупким, а временная недоступность Redis превращается в перезапуски. Отклонено.
- **Остановка без ограничения по времени.** Оказалось, что `pgxpool.Close()` при зависшей базе ждёт бесконечно, это проверено экспериментом. Без общего бюджета процесс не завершился бы. Отклонено.

## Следствия

- Балансировщик или оркестратор может выводить экземпляр из ротации по `/readyz`, не перезапуская его.
- Сообщение может быть обработано повторно: после сбоя или по истечении таймаута остановки неподтверждённые сообщения возвращаются в очередь. Поэтому обработчики должны быть идемпотентными, что и так требуется правилом 3 из `CLAUDE.md`.
- Подкоманда `api healthcheck` нужна для проверки здоровья в образе distroless, где нет shell и curl.
