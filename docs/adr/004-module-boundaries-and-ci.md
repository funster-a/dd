# ADR 004. Контроль границ модулей и CI

Статус: принято, 2026-09-28

## Контекст

Модульный монолит (ADR 001) держится на правиле: пакеты в `internal/` не импортируют друг друга напрямую, общий код живёт в `internal/platform`. Если за правилом следить только на ревью, у одного разработчика оно нарушится при первом дедлайне. Кроме того, по Definition of Done код должен проходить линтер, тесты и миграции, а `docker compose up` должен поднимать проект с нуля. Это нужно проверять автоматически на каждый push.

## Решение

1. **Границы модулей проверяет линтер.** В `.golangci.yml` настроен `depguard`: каждый доменный модуль (catalog, booking, payment, ticket) не может импортировать остальные, а `internal/platform` не может импортировать ни один из них. Нарушение ломает `make lint` и CI.
2. **Версия линтера закреплена** (golangci-lint v2.14.0), одинаково в Makefile и в CI.
3. **CI в GitHub Actions на каждый push**, четыре независимых задачи:
   - Build — `go mod tidy -diff` и сборка;
   - Lint — golangci-lint;
   - Test — миграции `up`, `reset`, `up` и все тесты с детектором гонок, включая интеграционные, против настоящих PostgreSQL и RabbitMQ в service-контейнерах;
   - Compose — `docker compose up --build --wait` с нуля, проверки `/healthz` и `/readyz` и доставка тестового сообщения до worker.

## Альтернативы

- **Разнести модули по отдельным Go-модулям.** Границы стали бы жёсткими, но появились бы версии, `replace` и сложность сборки. Для одного бинаря это лишнее. Отклонено.
- **Проверять границы только на ревью.** Ненадёжно без второго человека. Отклонено.
- **Интеграционные тесты на testcontainers.** Понадобилась бы новая зависимость и Docker внутри тестов. Service-контейнеры CI и `make infra-up` локально дают то же самое проще. Отклонено на текущем этапе.

## Следствия

- Нарушение архитектурного правила обнаруживается сразу, а не на защите.
- Интеграционные тесты пропускаются, если не задан `RABBITMQ_TEST_URL`. Поэтому `make test` работает без инфраструктуры, а полную проверку даёт `make test-integration` и CI.
- Задача Compose дольше остальных (сборка образов и старт всех сервисов), зато именно она проверяет пункт DoD «`docker compose up` поднимает проект с нуля».
