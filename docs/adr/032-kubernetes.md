# ADR 032. Kubernetes: манифесты и автомасштабирование по загрузке процессора

Дата: 2026-10-06. Статус: принято; эксперимент подготовлен, но не выполнен (см. «Эксперимент»).

## Контекст

Этап 6 плана развития — Kubernetes: манифесты и автомасштабирование по метрикам. Эксперимент — автомасштабирование при штурме и обратное сжатие.

К этому этапу:
- **Состояния в процессах нет.** api и воркер взаимозаменяемы (ADR 023), их число — вопрос нагрузки, а не настройки.
- **Ёмкость известна.** Один экземпляр api держит около 250 заказов в секунду, узкое место дальше — PostgreSQL (ADR 023, ADR 031).
- **Готовность отделена от живости.** `/readyz` даёт 503 только без PostgreSQL; отказ Redis, реплик или хранилища — 200 `degraded` (ADR 030). Иначе отказ общей зависимости вывел бы из ротации все поды сразу.
- **Корректная остановка есть** (ADR 003): api дорабатывает запросы за `SHUTDOWN_TIMEOUT`.
- **Перед api — nginx с кэшем на краю** (ADR 031).

## Решение

### Манифесты: kustomize, base и overlay

`deploy/k8s/base` — приложение:
- **migrate** — Job с goose;
- **api** — Deployment, два Service и HPA;
- **worker** — Deployment и HPA;
- **edge** — nginx с кэшем на краю, Deployment и HPA;
- **web** — сайт.

`deploy/k8s/overlays/local` — то, что зависит от окружения:
- адреса зависимостей;
- секреты, только значения для разработки, как в `docker-compose.yml`;
- зависимости в одном экземпляре: PostgreSQL, Redis, RabbitMQ, SeaweedFS, мок платёжного провайдера.

Для продакшена — свой overlay: те же base, адреса управляемых PostgreSQL, Redis и RabbitMQ или кластеров из ADR 028–030 через операторы, секреты из внешнего хранилища.

kustomize встроен в kubectl, отдельный шаблонизатор не нужен. Имена ConfigMap и Secret получают хэш содержимого: смена настроек перезапускает поды сама.

### Поды

- **Пробы api:**
  - startup и liveness — `/healthz`: процесс жив;
  - readiness — `/readyz`: под выводится из ротации только без PostgreSQL.
- **Остановка:**
  - `preStop: sleep 5` — пока Kubernetes убирает под из Service и край перестаёт слать ему запросы, под ещё отвечает;
  - затем SIGTERM и корректная остановка;
  - `terminationGracePeriodSeconds: 25` > 5 + `SHUTDOWN_TIMEOUT` (15 с).
- **Обновление:** `maxUnavailable: 0` — ёмкость при выкатке не падает.
- **PodDisruptionBudget:** обслуживание узлов выводит не больше одного пода за раз.
- **Распределение:** `topologySpreadConstraints` разносит поды по узлам. `ScheduleAnyway` — на одном узле kind они тоже запустятся.
- **Безопасность:** `runAsNonRoot`, read-only корень, без capabilities. Образы уже distroless nonroot; край — `nginx-unprivileged`.
- **Ресурсы api:**
  - запрос процессора — пол-ядра;
  - лимита процессора нет — троттлинг на старте продаж хуже, чем сосед по узлу;
  - лимит памяти есть — утечка не должна уронить узел.

### Автомасштабирование: HPA по загрузке процессора

| | Метрика | Мин–макс | Вверх | Вниз |
|---|---|---|---|---|
| api | CPU 60% от запроса | 2–10 | сразу, ×2 или +4 пода за 15 с | после 5 мин спокойствия, по поду в минуту |
| edge | CPU 60% | 2–6 | так же | после 5 мин |
| worker | CPU 70% | 2–6 | так же | после 5 мин |

**Почему процессор.**
- **api упирается в процессор** (ADR 023): заказ — это JSON, проверки, запросы к базе и Redis. Загрузка процессора растёт вместе с заказами.
- **Метрика встроена:** metrics-server, без адаптера метрик Prometheus.
- **Запас в 40% от запроса** — на рост, пока поднимается новый под.

**Почему такое поведение.**
- **Вверх — сразу.** Старт продаж — это стена запросов за секунды, а не плавный рост. Стабилизация 0 и удвоение за 15 секунд — HPA догоняет, а не опаздывает на минуту. Это и поведение HPA по умолчанию; у api оно записано явно, чтобы его не поменяли случайно.
- **Вниз — медленно.** Между волнами — после пропуска очереди, после первой минуты — HPA снимал бы поды и тут же поднимал снова. Окно стабилизации 5 минут — у всех трёх; у api ещё и не больше пода в минуту, чтобы не терять ёмкость рывком.

**Очередь ограничивает приток.** При штурме очередь (ADR 020) пропускает 150 человек в секунду. Это позволяет HPA успеть: нагрузка на api растёт с известной скоростью, а не всем стадионом сразу.

**Потолок — PostgreSQL.** 10 подов api — около 2 500 заказов в секунду, больше, чем выдерживает ведущий узел (ADR 023, ADR 031). Больше подов не добавят продаж, только соединений к базе: 10 подов × `pool_max_conns` должны укладываться в `max_connections`.

### Край находит новые поды сам

Край ходит в api не через ClusterIP Service, а через headless Service `api-pods`:
- **Список подов.** nginx разрешает имя в адреса всех подов (`server … resolve`) и перечитывает DNS каждые 10 секунд. Нагрузку делит сам nginx.
- **Почему не ClusterIP.** Долгие keepalive-соединения nginx через ClusterIP остаются на старых подах, и поды, поднятые HPA, почти не получают нагрузки — масштабирование не помогает.

Адрес DNS кластера nginx берёт из `/etc/resolv.conf` (`NGINX_ENTRYPOINT_LOCAL_RESOLVERS`). Сайт (`web/nginx.conf.template`) теперь делает так же, а не прописывает `127.0.0.11` из Docker: тот же образ работает и в Compose, и в Kubernetes.

Кэш на краю у каждого пода свой. Ответ живёт 2–60 секунд (ADR 031), поэтому с шестью подами края в api придёт до шести запросов на адрес вместо одного — несущественно рядом с заказами.

## Эксперимент

`loadtest/k8s-storm.sh`:
- кластер kind, metrics-server, приложение из `overlays/local`;
- штурм концерта на стадионе (5 000 покупателей, очередь 150 в секунду, как в ADR 026) изнутри кластера, k6 ходит в край;
- каждые 5 секунд — сколько экземпляров хочет HPA, сколько запущено и готово, загрузка процессора;
- после штурма запись идёт ещё 12 минут — видно обратное сжатие.

**Не выполнен в среде разработки этапа.**
- **Почему.** Ни kind, ни k3s не запускают контейнеры в этой песочнице: runc требует отрицательный `oom_score_adj`, а песочница его запрещает (`docker run --oom-score-adj=-998` падает, положительные значения работают).
- **Чем закрыто.** Без живого кластера проверено, что манифесты собираются и соответствуют схемам API Kubernetes 1.34 (`make k8s-validate`, в CI).
- **Что осталось.** Прогон на машине с Docker или на настоящем кластере; результаты — в `docs/experiments/2026-10-k8s-autoscaling`.

**Что ожидаем.**
- api — 2 → 4–6 подов за первые 30–45 секунд после старта продаж.
- Ни один заказ не теряется при добавлении подов. При снятии поды выходят через `preStop` и корректную остановку.
- Возврат к 2 подам — через 5 минут после конца штурма и далее по одному в минуту.
- Двойных броней — ноль.

## Альтернативы

- **HPA по метрикам приложения** (запросы в секунду, задержка p95 через prometheus-adapter). Точнее отражает нагрузку, но это ещё один компонент и правила перевода метрик Prometheus в metrics API. Для api, упирающегося в процессор, загрузка процессора даёт тот же сигнал. Остаётся следующим шагом, если опыт покажет запаздывание.
- **KEDA по длине очереди RabbitMQ для воркера.** Воркер масштабировался бы по реальному отставанию, а не по процессору. Но воркеры не узкое место: билеты выпускаются за доли секунды (ADR 030), и двух экземпляров хватает. Процессор — страховка.
- **Масштабирование заранее, по расписанию продаж.** Время старта продаж известно: можно поднять поды за 5 минут до него. Надёжнее HPA для известных пиков, но требует связи каталога с оркестратором. Вариант на будущее — поверх HPA (`minReplicas` по расписанию).
- **Helm.** Шаблоны и релизы, но для одного приложения с двумя окружениями overlay kustomize проще и читается как обычные манифесты.
- **Ingress-контроллер вместо своего края.** Кэш по `Cache-Control` и `proxy_cache_lock` в nginx-ingress настраиваются сниппетами, которые по умолчанию запрещены. Свой край — тот же конфиг, что в Compose. Ingress остаётся перед краем для TLS и домена.
- **Зависимости внутри кластера на продакшене.** PostgreSQL, Redis и RabbitMQ лучше управляемые или через операторы (CloudNativePG, Redis Operator, RabbitMQ Cluster Operator). StatefulSet в одном экземпляре — только для локального стенда.

## Следствия

- **Манифесты:** `deploy/k8s/base`, `deploy/k8s/overlays/local`.
- **Команды:**
  - `make k8s-images` — образы с тегом `local`;
  - `make k8s-validate` — сборка kustomize и проверка kubeconform;
  - в CI — задача «Kubernetes manifests».
- **Сайт:** DNS-сервер в `web/nginx.conf.template` берётся из `/etc/resolv.conf` контейнера.
- **Нагрузочный стенд:** `loadtest/k8s-storm.sh` — штурм в kind с записью HPA.
- **Открыто:** прогон эксперимента на машине без ограничений песочницы.
