# ADR 011. Бронирование и холды мест — разбор к защите

Неделя 3 (26.10–01.11.2026). ADR: [`docs/adr/011-booking-and-holds.md`](../../adr/011-booking-and-holds.md).

## Суть в трёх фразах

На старте продаж тысячи покупателей одновременно берут одни и те же места, а место нельзя продать дважды ни при какой конкурентности (правило 1). Решение — два уровня захвата: Redis атомарно ставит ключи мест заказа и сразу отказывает проигравшим, а решение о месте принимает PostgreSQL условным `UPDATE` под блокировкой строки, в одной транзакции с заказом. Холд живёт 10 минут, истина о брони — только в базе, поэтому без Redis продажа идёт медленнее, но так же корректно.

Ядро решения действует до сих пор. Позже его дополнили:
- ADR 017: эксперимент со стратегиями, который ADR 011 планировал на январь, проведён 2026-10-01. Redis + БД осталась в продукте. Добавлен предохранитель: бюджет 500 мс на вызов Redis, после ошибки фильтр выключается на 5 секунд (`internal/booking/holds.go:29-39`). ADR 023 сделал его полуоткрытым: проба раз в 100 мс (ADR 023:44-46);
- ADR 013: лимит считается не на заказ, а на покупателя за всё событие с учётом купленных билетов (ADR 013:56-58; `internal/booking/orders.go:223-235`). Заказ с суммой 0 оформляется сразу (`orders.go:444-450`);
- ADR 019: сумма заказа включает сервисный сбор, сбор хранится в позиции (ADR 019:22-24);
- ADR 020: перед захватом проверяются очередь ожидания и лимит на IP (`orders.go:220-240`);
- ADR 024, 026, 031: у занятости появились режимы «сводка» и «сектор», сводка живёт 1 секунду в памяти api, занятость читается с реплик, nginx держит её 2 секунды; для фан-зоны добавлен индекс выбора мест (миграция 00019);
- ADR 028: повтор запроса после потерянного `COMMIT` возвращает тот же заказ (`orders.request_key`, миграция 00018; `orders.go:191-205`).

## Почему так, а не иначе

- **Только база.** Корректно, но тысячи запросов на одно место стоят в очереди на блокировку одной строки. Остаётся режимом работы при отказе Redis. Позже эксперимент это подтвердил: на одном месте при 5 000 покупателях p95 у пессимистичной стратегии 8 071 мс против 3 419 мс у Redis + БД (evidence.md:49).
- **Только Redis, строка сразу `sold`** (так предполагал ADR 005). При потере Redis нужно разбирать рассинхрон, а отменить холд без второго источника истины нельзя. ADR 011 уточнил ADR 005: статус `held` в базе используется всегда.
- **Холд без заказа, заказ при оплате.** Упрощает отмену, но корзина тогда нигде не хранится: её нельзя показать, продлить или связать с платежом.
- **Оптимистичная стратегия** (позже, ADR 017). Не требует Redis, но на пике медленнее Redis + БД в 1,7 раза (ADR 017:79; evidence.md:52).

## Чем подтверждено

Тесты. Первые четыре — с параллельными горутинами. Каждый идёт в двух режимах — с Redis и только база, если не сказано иначе, и проверяет инвариант по данным (`checkNoDoubleBooking`, `internal/booking/env_test.go:155-179`):
- **200 покупателей на одно место:** 1 заказ, 199 `seat_taken`. `TestConcurrentSameSeat`, `internal/booking/orders_test.go:128-163`; evidence.md:86.
- **60 покупателей на случайные наборы по 3 из 12 мест:** ни одно место не попало в два заказа, успешных заказов 1–4, взаимоблокировок нет. `orders_test.go:167-204`; evidence.md:89.
- **Входная зона:** 70 покупателей на 30 мест — 30 успехов, 40 `not_enough_seats`, остаток 0. `orders_test.go:207-245`; evidence.md:90.
- **10 параллельных заказов одного покупателя:** 1 корзина, 1 место в холде. Только режим «база». `orders_test.go:336-362`; evidence.md:91.
- **Истечение:** истёкший холд не мешает другому покупателю до очистки, очистка не трогает перехваченное место, просроченный заказ закрывается при чтении. Только режим «база»: TTL ключей Redis не сдвинуть. `TestExpiry`, `orders_test.go:455-514`.
- **Мёртвый Redis** (клиент на неотвечающем адресе, без горутин): первый вызов укладывается в бюджет, следующие сразу идут в базу; заказ через базу оформляется, повтор того же места получает отказ от базы. `internal/booking/holds_test.go:15-68`.

Нагрузочные эксперименты:
- **0 двойных броней в 63 прогонах** эксперимента со стратегиями, из них 9 — с отказом Redis (evidence.md:39, 42). Всего 146 нагрузочных прогонов в девяти экспериментах, после каждого — проверка по данным в базе, двойных броней 0 (evidence.md:287-289).
- **Redis отсекает проигравших:** в Redis + БД 100 % отказов пришли из Redis, до базы дошёл только победитель (evidence.md:58).
- **Redis потерял все холды — двойных броней нет:** один Redis без журнала после перезапуска потерял 5 250 холдов, двойных броней 0 (evidence.md:171; ADR 029:74).
- **Отказ Redis посреди продажи:** итоговая версия продала 984 места без ошибок (evidence.md:43). До предохранителя покупатели увидели успех у 178 из 864 созданных заказов (evidence.md:299).

## Вопросы комиссии

1. **Как устроена гарантия «место не продаётся дважды»?**
   Ответ: Решение о месте принимает PostgreSQL. Строки мест блокируются `SELECT … FOR UPDATE`, и после получения блокировки условный `UPDATE` переводит место в `held`, только если оно свободно или его холд истёк. Если места достались не все, транзакция откатывается целиком. Redis перед этим только отсекает проигравших.
   Источник: ADR 011, «Решение» (строки 18-21); `internal/booking/queries.sql:13-31`; `internal/booking/orders.go:395-422`.

2. **Зачем тогда Redis, если база и так всё решает?**
   Ответ: Без фильтра все конкуренты за популярное место стоят в очереди на блокировку одной строки. Lua-скрипт в Redis атомарно ставит ключи всех мест заказа или ни одного, и проигравший сразу получает 409. В эксперименте все отказы пришли из Redis, а p95 на одном месте при 5 000 покупателях — 3 419 мс против 8 071 мс у стратегии «только база».
   Источник: ADR 011, п. 1 (строка 20); `internal/booking/holds.go:58-67`; evidence.md:49, 58.

3. **Почему не хранить бронь только в Redis, это же быстрее?**
   Ответ: Тогда истина о брони в Redis, а правило 2 требует держать её в PostgreSQL. Redis может потерять данные: в эксперименте один Redis без журнала после перезапуска потерял все 5 250 холдов. Двойных броней при этом было 0, потому что место продаёт база.
   Источник: ADR 011, «Альтернативы» (строка 43); evidence.md:171; ADR 029:10, 74.

4. **Что будет, если Redis упадёт посреди продажи?**
   Ответ: Захват идёт только через базу, корректность та же. Первая версия ждала таймаутов клиента Redis по 3–4 секунды, и покупатели увидели успех только у 178 из 864 созданных заказов. ADR 017 добавил бюджет 500 мс и выключение фильтра на 5 секунд, ADR 018 — кэш сессий. Итоговая версия при упавшем Redis продала 984 места без ошибок.
   Источник: ADR 011, «Решение» (строка 23); ADR 017:64-67; `holds.go:29-39`; evidence.md:43, 299.

5. **Почему строки блокируются в порядке `id`?**
   Ответ: Два заказа с пересекающимися местами, которые блокируют строки в разном порядке, могут ждать друг друга вечно — это взаимоблокировка. Общий порядок `id` её исключает. Тест на 60 покупателей с пересекающимися наборами проходит без взаимоблокировок. Если база всё же вернёт `40P01` или `40001`, покупатель получит «место занято», а не 500.
   Источник: ADR 011, п. 2 (строка 21); `queries.sql:18-25`; `orders_test.go:167-204`; `orders.go:463-465`.

6. **Как продаётся входная зона без мест?**
   Ответ: Покупатель просит количество, сервер берёт любые свободные виртуальные места через `FOR UPDATE SKIP LOCKED`. Параллельные покупатели получают разные строки и не ждут друг друга. Тест: 70 покупателей на 30 мест — 30 успехов, 40 отказов, остаток 0. На стадионе этот запрос оказался главной нагрузкой ведущего узла; индекс из миграции 00019 сократил его время с 680,9 до 10,5 секунды за прогон.
   Источник: ADR 011, «Входная зона» (строка 27); `queries.sql:53-67`; evidence.md:90, 192; ADR 031:28.

7. **Покупатель не оплатил за 10 минут. Что происходит с местом?**
   Ответ: Истёкший холд места с рядом считается свободным сразу, другой покупатель может его взять до очистки. Воркер раз в 15 секунд закрывает просроченные заказы пачками по 500 с `SKIP LOCKED`, несколько воркеров друг другу не мешают. Чтение или отмена просроченного заказа закрывает его сразу. Ключи в Redis истекают сами.
   Источник: ADR 011, «Истечение» (строки 31-34); `queries.sql:30, 106-116`; `cmd/worker/expire.go:25-26`; `orders.go:529-534`; `orders_test.go:455-514`.

8. **Как держится правило «одна корзина на событие»?**
   Ответ: Частичный уникальный индекс `orders (buyer_id, event_id) WHERE status = 'pending'`. Заказ вставляется до мест, поэтому второй параллельный заказ упирается в индекс раньше, чем тронет места. Прежняя корзина закрывается в той же транзакции, и её места доступны новому заказу. Тест: из 10 параллельных заказов одного покупателя остаётся 1 корзина и 1 место в холде.
   Источник: ADR 011, «Заказ» (строка 29); `migrations/00007_booking_indexes.sql:6-7`; `orders.go:356-382`; evidence.md:91.

9. **Сколько раз инвариант проверен под нагрузкой?**
   Ответ: 146 нагрузочных прогонов в девяти экспериментах, после каждого — проверка по данным в базе, двойных броней ноль. Из них 63 — эксперимент со стратегиями, включая 9 прогонов с отказом Redis. Отдельно идут тесты с горутинами: 200 покупателей на одно место дают ровно один заказ.
   Источник: evidence.md:39, 86, 287-289.

10. **Что в этом решении не доказано?**
    Ответ: Мутационная проверка из ADR, что уровни страхуют друг друга, сделана вручную и в репозитории не зафиксирована. Режим тестов «с Redis» создаётся, только если задан `REDIS_TEST_ADDR`. Проверка в тестах сверяет только заказы `pending`. Все 146 нагрузочных проверок сняты версией проверяльщика до 2026-10-08, а все эксперименты шли на одной машине с 4 vCPU.
    Источник: ADR 011:23; evidence.md:86, 289, 396-397; evidence.md:11.

## Где слабое место

- **Мутационная проверка не в репозитории.** ADR пишет, что без проверки статуса в SQL тест ловит двойную продажу без Redis (строка 23), но эта проверка сделана вручную (evidence.md:397). Почему приемлемо: тесты на горутинах и 146 нагрузочных проверок идут на настоящем коде. Что дальше: зафиксировать мутацию отдельным тестом с подменённым запросом.
- **Во входной зоне истёкший холд не свободен сразу.** `HoldGeneral` берёт только места со статусом `available` (`queries.sql:53-67`), поэтому место истёкшего заказа вернётся после фоновой очистки — до 15 секунд (`cmd/worker/expire.go:25`) — или после чтения заказа. «Свободен сразу» из ADR (строка 32) верно для мест с рядом (`queries.sql:30`). Ответ: места фан-зоны взаимозаменяемы, задержка в секунды не создаёт двойной продажи.
- **Призрачные холды.** Ключ в Redis может пережить заказ, если удаление ключа не удалось: тогда место свободно в базе, но Redis отказывает до конца TTL (`orders.go:506-514`). Частота не измерена: в потоках экспериментов нет отмен (evidence.md:76, 422). Ответ: это недопродажа на минуты, а не двойная продажа.
- **Без Redis медленнее.** При отказе Redis продажа идёт по пути «только база» — самому медленному на пике (evidence.md:49). Ответ: корректность сохраняется, а Sentinel возвращает запись в Redis через 3 секунды (ADR 029; evidence.md:173).
- **Лимит на заказ из ADR устарел.** ADR 011 считал лимит на заказ (строка 51), ADR 013 перенёс его на покупателя за всё событие.
- **Один стенд.** Абсолютные числа описывают машину с 4 vCPU, где k6 и все сервисы делят процессор; доказательную силу имеет сравнение внутри серии (evidence.md:11).

## Проверь себя

1. Холд покупателя A истёк 3 секунды назад, воркер ещё не прошёл. Покупатель B берёт это место, а через секунду обрабатывается оплата A, подтверждённая до истечения. Что получит каждый и где это в коде?
2. Почему без проверки статуса в SQL место не продаётся дважды, пока работает Redis, но продаётся, когда Redis недоступен?
3. Что делает каждый уровень при заказе на два места с рядом, если второе место уже держит прежняя корзина этого же покупателя?
