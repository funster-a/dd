# ADR 010. Кэш публичной страницы события — разбор к защите

Неделя 3 (26.10–01.11.2026). ADR: [`docs/adr/010-public-event-cache.md`](../../adr/010-public-event-cache.md).

## Суть в трёх фразах

Публичную страницу события — карточку, площадку, цены и схему зала — на старте продаж открывают тысячи покупателей в одну секунду, а схема большого зала собирается из нескольких таблиц в сотни килобайт JSON. Решение — готовый JSON страницы лежит в Redis 10 минут, а одновременные промахи кэша по одному событию схлопываются в один запрос к базе (singleflight: остальные запросы ждут результат первого). Смена обложки сразу удаляет ключ, ошибка Redis не ломает страницу, а свободные места в страницу не входят и отдаются отдельным эндпоинтом.

Позже решение дополнили, механизм не меняли:
- ADR 031: страница строится только с ведущего узла PostgreSQL, не с реплики, иначе отстающая реплика вернула бы в кэш старые обложки на 10 минут (ADR 031:45, 87). nginx перед api держит страницу 60 секунд по `Cache-Control` (ADR 031:51-53);
- ADR 024: api сжимает JSON, схема стадиона в странице — 397 КБ, в gzip — 11 КБ (ADR 024:72);
- ADR 014: отмена события тоже сбрасывает кэш (`internal/catalog/cancel.go:47`);
- ADR 023: singleflight склеивает запросы только внутри одного экземпляра api (ADR 023:20).

## Почему так, а не иначе

- **Кэш в памяти процесса.** Быстрее Redis, но при нескольких экземплярах api у каждого своя копия. Сбрасывать все копии при смене обложки пришлось бы через очередь. ADR оставляет его как возможный второй уровень поверх Redis.
- **Своя реализация singleflight.** Около 40 строк на mutex и map. `golang.org/x/sync` поддерживает команда Go, у пакета нет своих зависимостей, и он уже был в графе модулей транзитивно.
- **Только HTTP-кэш или CDN.** Не защищает базу при холодном CDN и не даёт мгновенно сбросить кэш.
- **Страница с реплики** (позже, ADR 031). Отвергнуто: кэш сбрасывается при смене обложек, и отстающая реплика вернула бы в него старую страницу.

## Чем подтверждено

- **Холодный кэш и 200 одновременных открытий — одна сборка из базы.** `TestPublicEventColdCacheStampede`, `internal/catalog/public_test.go:126-162`; [реестр](../evidence.md), строка 198. Ограничения из реестра: кэш в тесте — заглушка в памяти, одна сборка делает несколько SQL-запросов (`public.go:99-114`).
- **«Не найдено» не кэшируется, второй запрос идёт из кэша, смена обложки сбрасывает кэш.** `TestPublicEvent`, `public_test.go:58-124` (строки 64-69, 92-98, 100-123).
- **Заголовок для CDN.** `TestPublicEventHTTP` проверяет `Cache-Control: public, max-age=60` (`public_test.go:164-188`).
- **Штурм стадиона.** Страница события p95 7–11 мс во всех вариантах, хотя сводка занятости без очереди отвечала p95 6 808 и 8 939 мс (stadium-storm/tables.md:16-19; evidence.md:151). Оговорка: в сценарии страницу открывают в последние 30 секунд до старта (stadium-storm/README.md:19), а не на пике заказов.
- **Объём.** Схема стадиона в gzip — 11 КБ вместо 397 КБ; путь покупателя — 13–15 КБ со сжатием (evidence.md:149).
- **Не проверено.** Ветка «Redis вернул ошибку» тестом не покрыта: заглушка кэша ошибок не возвращает. Холодный старт нескольких экземпляров отдельно не мерился.

## Вопросы комиссии

1. **Что кэшируется и почему именно эта страница?**
   Ответ: Кэшируется готовый JSON публичной страницы: карточка, площадка, цены и схема зала. Её открывают все покупатели, больше всего на старте продаж. После публикации схема и цены зафиксированы, поэтому страница почти не меняется. Ключ — `catalog:public-event:{организатор}/{событие}`, срок — 10 минут.
   Источник: ADR 010, «Контекст» (строки 7-9), «Решение» (строка 13); `internal/catalog/public.go:26, 154-156`.

2. **Что такое singleflight и какую проблему он решает?**
   Ответ: Когда ключ пропал из кэша, тысячи запросов разом идут собирать страницу в базу. singleflight пропускает в базу только первый запрос по ключу, остальные ждут его результат. Тест: 200 одновременных открытий при холодном кэше дают одну сборку из базы. Сборка идёт без контекста первого запроса, чтобы его отмена не оборвала ответ для остальных.
   Источник: ADR 010, «Решение» (строка 14); `internal/catalog/public.go:80-92`; `public_test.go:126-162`; evidence.md:198.

3. **Почему не кэш в памяти api, ведь он быстрее?**
   Ответ: Экземпляров api несколько, и у каждого была бы своя копия. При смене обложки пришлось бы сбрасывать все копии через очередь. Redis — один общий кэш, ключ удаляется одной командой. Кэш в памяти может стать вторым уровнем поверх Redis.
   Источник: ADR 010, «Альтернативы» (строка 24); ADR 023:20.

4. **Почему «не найдено» не кэшируется?**
   Ответ: Покупатель может открыть ссылку до публикации. Если запомнить «не найдено» на 10 минут, событие после публикации было бы недоступно до истечения срока. Тест проверяет, что после 404 на черновике кэш пуст.
   Источник: ADR 010, «Решение» (строка 16); `public_test.go:64-69`.

5. **Организатор поменял обложку. Когда покупатель увидит новую?**
   Ответ: Ключ в Redis удаляется сразу, следующий запрос в api собирает страницу заново. Но ответ разрешено кэшировать 60 секунд: столько его может держать nginx перед api, CDN и браузер. Поэтому старая обложка может показываться до минуты. Цены и схема после публикации не меняются, а при появлении их редактирования сброс кэша нужно добавить туда.
   Источник: ADR 010, «Решение» (строки 15, 18), «Следствия» (строка 30); `internal/catalog/media.go:140`; `internal/catalog/http.go:51`; ADR 031:51-53.

6. **Что будет, если Redis упадёт?**
   Ответ: Ошибка чтения кэша не ломает страницу: она строится из базы, а singleflight по-прежнему склеивает одновременные запросы внутри экземпляра. Но у кэша страницы нет предохранителя, как у холдов в ADR 017: зависший Redis заставит каждый запрос ждать таймаута клиента. Для холдов без предохранителя это было 3–4 секунды на вызов. Поведение страницы при отказе Redis не измерялось.
   Источник: ADR 010, «Решение» (строка 17); `internal/catalog/public.go:73-78`; `internal/platform/redis/redis.go:62-91`; ADR 017:65.

7. **Есть ли числа, что кэш помогает под нагрузкой?**
   Ответ: Прямого сравнения «с кэшем и без» нет. Есть штурм стадиона на 33 509 мест: страница события p95 7–11 мс во всех вариантах, хотя сводка занятости без очереди отвечала p95 6 808 и 8 939 мс. Схема стадиона в gzip занимает 11 КБ вместо 397 КБ.
   Источник: stadium-storm/tables.md:16-19; evidence.md:136, 149, 151; ADR 024:72.

8. **Что в этом решении не доказано?**
   Ответ: Тест singleflight идёт с кэшем-заглушкой в памяти, а не с Redis. Ветка ошибки Redis не покрыта тестом. На штурме страницу открывали до старта продаж, а не на пике заказов. При N экземплярах api холодный кэш даёт до N сборок, singleflight общий только внутри экземпляра; это не мерилось.
   Источник: evidence.md:198; `public_test.go:14-44`; stadium-storm/README.md:19; ADR 023:20.

## Где слабое место

- **Нет предохранителя на Redis.** Холды, сессии и очередь обходят зависший Redis через общий предохранитель `redis.Gate` (ADR 017, 018, 023), а кэш страницы — нет (`public.go:73-78`). Почему приемлемо: если Redis отказывает быстро, страница строится из базы. Что дальше: обернуть кэш тем же предохранителем.
- **Сброс «мгновенный» только в Redis.** nginx, CDN и браузер держат ответ до 60 секунд (`http.go:51`; ADR 031:51-53). Ответ: для обложки минута задержки не важна, а цены и схема после публикации не меняются (строка 30).
- **Сброс завязан на код.** Ошибка удаления ключа игнорируется (`public.go:151`), и тогда старая страница живёт до 10 минут. Есть и гонка: сборка, начатая до смены обложки, может записать старую страницу в кэш уже после удаления ключа (`public.go:80-90`; `media.go:134-140`), тогда она тоже живёт до 10 минут; тестом это не проверено. TTL — страховка как раз от таких случаев (строка 15). При появлении редактирования опубликованного события сброс нужно добавить туда (строка 30).
- **singleflight локален.** Холодный кэш при N экземплярах даёт до N сборок (ADR 023:20). Ответ: N — единицы, а не тысячи; база защищена от лавины, а не от каждого лишнего запроса.
- **Нагрузочного сравнения нет.** Есть тест на 200 горутин и косвенное число со штурма. Что дальше: прогон штурма с выключенным кэшем страницы.

## Проверь себя

1. Три экземпляра api, кэш холодный, 1 000 одновременных открытий страницы. Сколько сборок из базы будет в худшем случае и почему не одна?
2. Через какие уровни кэша старая обложка ещё может дойти до покупателя после смены и сколько времени на каждом?
3. Почему страницу события нельзя строить с реплики, а занятость мест можно?
