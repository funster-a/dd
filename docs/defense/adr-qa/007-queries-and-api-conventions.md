# ADR 007. Запросы к базе и соглашения HTTP API — разбор к защите

Неделя 2 (19–25.10.2026). ADR: [`docs/adr/007-queries-and-api-conventions.md`](../../adr/007-queries-and-api-conventions.md).

## Суть в трёх фразах

Когда у модулей появились запросы к базе и HTTP-эндпоинты, понадобились общие правила, иначе каждый модуль писал бы SQL и отвечал на ошибки по-своему. Решение — SQL пишется руками, генератор sqlc проверяет его по схеме из миграций и создаёт типизированный Go-код в отдельном пакете каждого модуля, а API живёт под `/v1`, принимает строгий JSON и токен в заголовке `Authorization: Bearer` и отвечает ошибкой единого формата. Отсюда опечатка в имени колонки ловится при генерации кода и в CI, а не в продакшене, модуль не может вызвать чужой запрос, а фронтенд различает ошибки по машинному коду.

Позже формат ошибок дополнил ADR 028: на недоступность базы все модули отвечают `503 service_unavailable` с `Retry-After: 2`. Вопрос о хранении токена в браузере ADR оставил открытым. Сайт хранит токен в `localStorage` (`web/src/api/client.ts:49-58`) и работает с api с одного origin (ADR 015:54).

## Почему так, а не иначе

- **ORM (GORM, ent).** Скрывает SQL, а для ядра продажи мест важен именно точный SQL: блокировки, условия обновления, уникальные индексы.
- **SQL вручную через pgx.** Нет проверки на этапе сборки: опечатка в имени колонки обнаружится только при выполнении.
- **Один сгенерированный пакет на весь проект.** Проще настроить, но любой модуль сможет вызвать любой запрос в обход границ модулей.
- **Токен в HttpOnly cookie.** Надёжнее против XSS, но требует защиты от CSRF и неудобен для сканера и интеграций. На уровне API оставили Bearer, хранение в браузере отложили до фронтенда.

## Чем подтверждено

- **Сгенерированный код актуален:** шаг CI `sqlc diff` падает, если SQL или схема изменились, а код не перегенерирован. `.github/workflows/ci.yml:27-28`; команда `make sqlc`, `Makefile:70-71`; sqlc закреплён в `tools.mod:110`.
- **Пакет на модуль:** `sqlc.yaml` описывает отдельный блок на каждый модуль (`identitydb`, `idempotencydb`, `catalogdb` и далее). Импорт чужого модуля запрещает depguard (`.golangci.yml:34-113`; ADR 004:11).
- **UUID — строки:** переопределение типа в `sqlc.yaml:8-14`. Неверный id не роняет запрос: catalog отвечает «не найдено» (`internal/catalog/venues_test.go:118`).
- **Строгий JSON:** неизвестное поле, данные после объекта, не-JSON и тело больше 1 МБ отклоняются. `internal/platform/httpx/json.go:33-45`, тест `json_test.go:10-35`.
- **Единый формат ошибки:** `internal/platform/httpx/json.go:21-31`, тест `json_test.go:37-47`.
- **Время в UTC:** `timestamptz` читается в UTC независимо от часового пояса процесса. `internal/platform/db/db.go:20-22, 51`, тест `TestTimestamptzIsUTC`, `db_test.go:11-35`.
- **Точный SQL понадобился:** стратегии захвата держатся на `SELECT … FOR UPDATE` в порядке id и условном `UPDATE … WHERE version = $v` (ADR 017:24-26).
- **Не измерено:** сравнения sqlc с ORM или с ручным pgx по скорости или числу ошибок нет. Решение обосновано свойствами инструментов, а не замером.

## Вопросы комиссии

1. **Что такое sqlc и почему не ORM?**
   Ответ: sqlc берёт SQL, написанный руками, проверяет его по схеме из goose-миграций и генерирует типизированные Go-функции. ORM строит SQL сам и скрывает его. Ядру продажи мест нужен точный SQL: `SELECT … FOR UPDATE` в порядке id, условный `UPDATE` по версии строки, опора на уникальные индексы.
   Источник: ADR 007, «Решение», п. 1 (строка 11); «Альтернативы» (строка 23); ADR 017:24-26.

2. **Почему не писать SQL строками прямо в pgx?**
   Ответ: Тогда опечатка в имени колонки или несовпадение типов обнаружатся только при выполнении запроса. sqlc проверяет запрос по схеме при генерации. CI запускает `sqlc diff`: если SQL или миграции изменились, а сгенерированный код нет, сборка падает.
   Источник: ADR 007, «Альтернативы» (строка 24); п. 1 (строка 11); `.github/workflows/ci.yml:27-28`.

3. **Как sqlc связан с границами модулей?**
   Ответ: У каждого модуля свой файл `queries.sql` и свой сгенерированный пакет, например `internal/booking/bookingdb`. Пакет лежит внутри модуля, а depguard запрещает модулям импортировать друг друга. Поэтому catalog не может вызвать запрос booking. С одним общим пакетом любой модуль вызывал бы любой запрос.
   Источник: ADR 007, п. 2 (строка 12); «Альтернативы» (строка 25); `sqlc.yaml`; `.golangci.yml:34-113`; ADR 004:11.

4. **Почему UUID в Go — строки, а не отдельный тип?**
   Ответ: Код идентификаторы не разбирает, только передаёт. Строки не требуют отдельной зависимости. Цена — компилятор не отличит id от любой строки. Неверный id отклоняется на уровне сервиса: catalog отвечает «не найдено».
   Источник: ADR 007, п. 3 (строка 13); `sqlc.yaml:8-14`; `internal/catalog/venues_test.go:118`.

5. **Почему Bearer-токен, а не HttpOnly cookie? Где токен хранится в браузере?**
   Ответ: Cookie надёжнее против XSS, но требует защиты от CSRF и неудобна для сканера и интеграций. Сканер, например, передаёт свой токен в заголовке `Authorization: Scanner`. В браузере токен лежит в `localStorage`, а сайт и api работают с одного origin, без CORS. Риск XSS при этом остаётся, его снижает CSP `script-src 'self'`.
   Источник: ADR 007, «Альтернативы» (строка 26); ADR 013:24; ADR 015:54, 56; `web/src/api/client.ts:49-58`.

6. **Зачем строгий разбор JSON и единый формат ошибок?**
   Ответ: Неизвестное поле чаще всего означает опечатку клиента, и молча его игнорировать опасно. Лимит тела в 1 МБ отсекает большие запросы. Ошибка всегда имеет вид `{"error": {"code", "message"}}`: по `code` фронтенд выбирает текст на нужном языке, `message` — для разработчика.
   Источник: ADR 007, п. 4 (строки 14-19); `internal/platform/httpx/json.go:21-45`; `json_test.go:10-47`.

7. **Что из этого не доказано?**
   Ответ: Выбор sqlc не подкреплён замером: сравнения с ORM или ручным pgx нет. Версионирование `/v1` ни разу не применялось, второй версии API нет. Хранение токена в `localStorage` не защищено от XSS. Ни один ADR этот выбор не записал: ADR 007 отложил его до фронтенда, ADR 015 его не фиксирует.
   Источник: ADR 007, «Альтернативы»; `cmd/api/main.go:152`; `web/src/api/client.ts:49-58`.

## Где слабое место

- **Токен в `localStorage`.** ADR сам признаёт, что cookie надёжнее против XSS (строка 26). Почему приемлемо: сайт и api на одном origin (ADR 015:54), токен не уходит на чужой домен, а CSP `script-src 'self'` запрещает чужие скрипты (ADR 015:56). От XSS через собственный код это не защищает, и выбор `localStorage` ни в одном ADR не записан. Что дальше: перенести токен сайта в HttpOnly cookie с защитой от CSRF, а Bearer оставить сканеру и интеграциям.
- **Модели всех таблиц в каждом пакете.** `models.go` каждого сгенерированного пакета содержит структуры всех таблиц: sqlc генерирует модели по всей схеме (строка 31). Ответ: запросы чужого модуля при этом недоступны, а структуры без запросов ничего не читают.
- **Граница на уровне таблиц не проверяется.** sqlc проверяет SQL по всей схеме, поэтому запрос модуля может читать чужую таблицу. Это видно в booking, который читает `events` и `tickets` (`internal/booking/queries.sql:3-5, 202-210`). Ответ: общая база даёт одну транзакцию для главного инварианта.
- **Сборка sqlc требует компилятора C.** Первая сборка занимает около минуты (строка 30). Ответ: дальше она берётся из кэша, на разработку это не влияет.
- **UUID как строки.** Компилятор не отличает id заказа от id события. Ответ: внешние ключи в базе и составные ключи ADR 005 не дадут записать перепутанный id.

## Проверь себя

1. Разработчик добавил колонку в миграцию и поправил `queries.sql`, но забыл `make sqlc`. На каком шаге и с каким сообщением это всплывёт?
2. Чем `DisallowUnknownFields` защищает API от ошибок клиента, и в каком случае эта строгость мешает обратной совместимости?
3. Если перенести токен сайта в HttpOnly cookie, что придётся добавить на сервере и что изменится для сканера?
