# ADR 026. Штурм стадиона: сводка занятости в памяти и скорость очереди — разбор к защите

Неделя 7 (23–29.11.2026). ADR: [`docs/adr/026-stadium-storm.md`](../../adr/026-stadium-storm.md).

## Суть в трёх фразах

Первые прогоны штурма стадиона показали, что база тратит силы не только на заказы, но и на чтение занятости: открытие сектора пересчитывало сводку по всем 33 тысячам мест, а сводку для плана стадиона заново считал каждый запрос. Решение — в режиме сектора считать только этот сектор, а сводку для плана держать в памяти каждого экземпляра api одну секунду; эксперимент заодно подтвердил, что скорость очереди надо подбирать по ёмкости: на стенде один экземпляр api комфортно пропускает 150 покупателей стадиона в секунду. План может отставать на секунду, но место всё равно проверяет заказ в базе: в восьми прогонах — ноль двойных броней, ноль ответов 5xx и таймаутов, а с очередью 150 в секунду билеты купили все 5 000 покупателей.

Решение действует. Позже его дополнили:
- ADR 031: профиль ведущего узла нашёл, что режим сектора всё ещё считал все фан-зоны события; теперь считается только открытая зона: `CountGeneralAvailable` — 273,5 → 1,6 с за прогон, новый `CountGeneralAvailableInSection` — 3,3 с (evidence.md:193). Если задан `DATABASE_REPLICA_URL`, чтения занятости, включая сводку, идут с реплик (ADR 031:32-35; `internal/booking/orders.go:33-35, 52`; `internal/booking/strategy.go:47`).
- ADR 031: альтернатива «отдавать сводку через CDN» реализована на стенде как кэш nginx на краю, занятость — 2 секунды (ADR 031:51-53).
- ADR 029: Redis на штурме не был узким местом, поэтому Redis Cluster не нужен (ADR 029:80).

## Почему так, а не иначе

- **Материализованная сводка в базе.** Счётчики по секторам обновлялись бы в той же транзакции, что и холд, и сводка стала бы точной и бесплатной. Но каждый заказ спорил бы за строку счётчика своего сектора — новая горячая точка там, где решается главный инвариант (ADR 026:51). Тот же довод повторён в ADR 031:86.
- **Сводка в Redis по событиям холда.** Быстро, но при отказе Redis её надо сверять с базой. Кроме того, поход в Redis стоит почти столько же, сколько кэш экономит; секунда в памяти проще и даёт почти тот же эффект (ADR 026:22, 52).
- **Отдавать сводку через CDN.** `Cache-Control: public, max-age=2` уже стоит (`internal/booking/http.go:53`). CDN снимет эти запросы на продакшене, а кэш в api защищает базу, когда CDN нет или он промахнулся (ADR 026:53).
- **Поменять скорость очереди по умолчанию.** `QUEUE_ADMIT_PER_SECOND=50` оставлено: 150 в секунду — ёмкость одного стенда, на продакшене её считают по метрикам (ADR 026:31).
- **Больше генератора нагрузки.** 10 000 покупателей не поместились в память k6 на стенде; полная распродажа требует отдельной машины для k6 (ADR 026:54).

## Чем подтверждено

Тесты:
- **Сводка из кэша устаревает, места сектора — нет; без кэша сводка свежая:** после заказа кэшированная сводка показывает 4 свободных, сектор — одно занятое место, при TTL 0 сводка показывает 3. `TestSummaryCache`, `internal/booking/orders_test.go:673-712`.
- **Режим сектора считает только свой сектор:** чужой сектор не получает ни мест, ни счётчиков. `TestAvailabilitySummaryAndSection`, `orders_test.go:626-671`.

Эксперимент ([`docs/experiments/2026-10-stadium-storm`](../../experiments/2026-10-stadium-storm/README.md); концерт на 33 509 мест, 5 000 покупателей, один api, пул 32, стратегия redis, 4 vCPU):
- **Очередь 150 в секунду:** заказ p95 1,06 с (894–1 222 мс), p50 0,48 с (evidence.md:139).
- **Без очереди:** заказ p95 11,0 с; без очереди и без кэша сводки — 14,5 с (evidence.md:140).
- **Очередь против варианта без очереди:** заказ в 10 раз быстрее (11 013 / 1 058 = 10,4), отказов «место заняли» 318 против 2 688, в 8,5 раза меньше (evidence.md:141).
- **Купили все:** 5 000 из 5 000 при очереди 150 в секунду; без очереди ушли 18–22 покупателя (evidence.md:142).
- **Очередь 300 в секунду:** p95 4,5 с, примерно вчетверо выше, чем при 150, — только по p95; «место заняли» 1 890 (evidence.md:143).
- **Кэш сводки:** заказ p95 14,5 → 11,0 с (−24 %), последняя покупка 33,4 → 23,8 с (evidence.md:145); сводка p95 8 939 → 6 808 мс (evidence.md:307).
- **Устойчивость:** 0 ответов 5xx и 0 таймаутов в восьми прогонах (evidence.md:148); 0 двойных броней в восьми прогонах (evidence.md:71).
- **Данные покупателю:** 13–15 КБ на весь путь со сжатием (evidence.md:149).

Не измерено: «около 14 мс процессора базы» на один пересчёт — оценка из текста, сырого замера нет (evidence.md:146). Исправление режима сектора не мерили до и после (evidence.md:306).

## Вопросы комиссии

1. **Какие узкие места нашёл штурм стадиона?**
   Ответ: Оба — в чтении занятости, а не в заказе. Режим `?section=` вместе с местами сектора возвращал сводку по всем секторам: `GROUP BY` по 33 тысячам строк, около 14 мс процессора базы на каждый открытый сектор. Сводку для плана пересчитывал каждый запрос, а singleflight объединял только запросы одной миллисекунды.
   Источник: ADR 026:8-9; evidence.md:146, 306.

2. **Как устроен кэш сводки?**
   Ответ: Каждый экземпляр api хранит последний ответ `?view=summary` по каждому событию на `AVAILABILITY_SUMMARY_TTL`, по умолчанию 1 с; `0` выключает кэш, больше минуты конфигурация не примет. Промах идёт в базу одним запросом через singleflight и кладёт ответ в кэш. При записи кэш удаляет устаревшие записи, поэтому растёт не дальше числа событий, открытых за последнюю секунду.
   Источник: `internal/booking/availability.go:84-143`; `internal/platform/config/config.go:147-154`; ADR 026:19-23.

3. **Не опасно ли показывать покупателю устаревшую сводку?**
   Ответ: Нет: сводка только красит план. Места открытого сектора и сам заказ всегда идут в базу, и место проверяет транзакция заказа. В худшем случае покупатель увидит в секторе меньше свободных мест, чем показал план. Тест это фиксирует: кэшированная сводка старая, а места сектора свежие.
   Источник: ADR 026:20-21; `availability.go:126`; тест `orders_test.go:673-712`.

4. **Почему кэш в памяти, а не в Redis?**
   Ответ: Кэш в памяти даёт одно чтение базы в секунду на экземпляр, при N экземплярах — N. Поход в Redis стоил бы почти столько же, сколько кэш экономит, а сводка в Redis по событиям холда требует сверки с базой при отказе Redis. Секунда в памяти проще и не добавляет зависимость.
   Источник: ADR 026:22, 52.

5. **Почему не держать точные счётчики в базе, обновляя их вместе с холдом?**
   Ответ: Каждый заказ начал бы спорить за строку счётчика своего сектора. В пик продаж это блокировка на горячей строке там, где решается главный инвариант. Приблизительная сводка на секунду безопаснее точной, которая тормозит заказы.
   Источник: ADR 026:51; ADR 031:86.

6. **Что дал кэш сводки в цифрах?**
   Ответ: Без очереди заказ p95 упал с 14,5 до 11,0 секунды, на 24 %. Последняя покупка — с 33,4 до 23,8 секунды, в ADR округлено до «на 9 секунд раньше». Сводка p95 — с 8 939 до 6 808 мс, но всё ещё медленная: без очереди перегружена уже вся машина.
   Источник: evidence.md:145, 307; ADR 026:44; stadium-storm/README.md:66-70.

7. **Что дала очередь на 150 в секунду и почему 300 хуже?**
   Ответ: С очередью 150 заказ p95 — 1,06 с против 11,0 без очереди, в 10 раз быстрее; «место заняли» — 318 раз против 2 688; билет получили все 5 000. Цена — ожидание в очереди, p95 33 секунды. При 300 в секунду путь покупателя даёт больше тысячи запросов в секунду, это выше ёмкости одного экземпляра: p95 4,5 с, 1 890 отказов, 22 покупателя ушли без билета.
   Источник: evidence.md:141-143, 147; stadium-storm/README.md:79-82.

8. **Почему по умолчанию очередь пропускает 50 в секунду, если 150 комфортно?**
   Ответ: 150 — ёмкость одного экземпляра на одной машине с 4 vCPU, где k6 и база делят ядра. Единица здесь — покупатели стадиона, у каждого сводка, сектор и заказ, а не заказы в секунду из ADR 023. На продакшене скорость подбирают по метрикам, как описано в ADR 020 и ADR 023.
   Источник: ADR 026:27-31; evidence.md:144.

9. **Что в этом решении не доказано?**
   Ответ: Распродажу до нуля не проверяли: 5 000 покупателей хотят около 14 тысяч билетов, 42 % стадиона; больше k6 на стенде не тянет. Оплаты не было, места остаются в холде. Эффект кэша измерен только без очереди, варианта «очередь без кэша» нет. Цифра 14 мс — оценка, а не замер; по два прогона на вариант.
   Источник: evidence.md:138, 145-146, 387, 410-413.

## Где слабое место

- **Распродажа до нуля не проверена.** Спрос — 42 % мест, это предел k6 на стенде, а не платформы (evidence.md:138, 410-411). Ответ: почти распроданный стадион — самый тяжёлый случай для отказов «место заняли»; следующий шаг — отдельная машина для k6, это в планах этапа 6 (ADR 026:54).
- **Режим сектора остался неполным.** ADR 026 убрал сводку по секторам, но подсчёт всех фан-зон на каждое открытие сектора остался; его нашёл только профиль в ADR 031 (evidence.md:193). Ответ: поэтому следующий этап начался с профиля `pg_stat_statements`, а не с догадки.
- **Кэш измерен только без очереди** (evidence.md:145). Ответ: с очередью покупатели приходят потоком по 150 в секунду, а не 5 000 сразу, и сводка p95 — 451 мс (evidence.md:151). Кэш нужнее всего событию без очереди: окно очереди у события может отсутствовать (`internal/booking/availability.go:33-35`). Эффект кэша при очереди не измерен.
- **Отставание плана складывается.** Секунда в памяти api и до трёх секунд кэша на краю (ADR 031:53; nginx считает max-age=2 в целых секундах, ADR 031, «Исправление 19.10.2026») — по построению план может отставать дольше секунды. Это вывод из настроек, отдельно не измерялся. Ответ: корректность от этого не зависит, место проверяет заказ; растёт только доля отказов «место заняли».
- **14 мс на пересчёт — оценка** (evidence.md:146). Ответ: эффект кэша подтверждён сравнением вариантов, а не этой цифрой.
- **Один стенд, два прогона на вариант, покупатели k6 решают мгновенно** (evidence.md:385, 387-388). Ответ: сравниваются только варианты одной серии; живые покупатели приходят к заказу равномернее, это снижает пик.

## Проверь себя

1. Три экземпляра api за балансировщиком, TTL сводки 1 с, на старте 5 000 открытий плана в секунду. Сколько запросов сводки дойдёт до базы и от чего это зависит?
2. Покупатель увидел на плане «12 свободных» в секторе 7, открыл его и увидел 3. Объясните, откуда расхождение и почему это не нарушение инварианта.
3. Почему очередь 300 в секунду дала на стенде больше ушедших без билета, чем 150, хотя пропускала покупателей вдвое быстрее?
