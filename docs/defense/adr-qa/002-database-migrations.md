# ADR 002. Миграции базы данных — разбор к защите

Неделя 1 (12–18.10.2026). ADR: [`docs/adr/002-database-migrations.md`](../../adr/002-database-migrations.md).

## Суть в трёх фразах

Схема PostgreSQL меняется весь проект, и одна и та же цепочка изменений нужна на машине разработчика, в CI и при `docker compose up`. Решение — goose: каждое изменение схемы оформлено SQL-файлом с секциями применения (`Up`) и отката (`Down`), сам goose закреплён в отдельном `tools.mod`, а применяет миграции одноразовый сервис `migrate` до старта api. CI на каждый push применяет все миграции, откатывает их до нуля, проверяет, что база пуста, и применяет снова, поэтому миграция с неполным откатом не проходит.

## Почему так, а не иначе

- **golang-migrate.** Возможности похожие, но миграция в нём — два файла вместо одного, и нет миграций на Go. goose проще читать.
- **Применять миграции при старте api.** Несколько экземпляров api начинают гоняться за блокировку схемы. Упавшая миграция роняет api, а не отдельный шаг развёртывания.
- **goose через `go tool` в основном `go.mod`.** Так было в первой версии каркаса. goose тянет драйверы всех СУБД: в `go.mod` добавилось около 70 косвенных зависимостей, `go mod tidy` начал скачивать сотни модулей, включая тестовые зависимости Azure SDK, YDB и sqlite, стал медленным и падал при сетевых сбоях.
- **goose через `go run ...@version`.** `go.mod` остаётся чистым, но версия записана отдельно в Makefile и Dockerfile, а контрольные суммы проверяются только через sumdb.

## Чем подтверждено

- **Полный цикл в CI.** Шаг «Migrations apply and roll back»: `make migrate-up`, `make migrate-reset`, SQL-запрос считает оставшиеся таблицы, схемы, типы, функции и расширения, кроме служебной таблицы goose; если что-то осталось — ошибка; затем снова `up` и `status` (`.github/workflows/ci.yml:100-126`).
- **Тот же цикл в Go-тесте.** `TestMigrationsRoundTrip`: `up`, откат до нуля, снова `up` на временной базе, миграции встроены в бинарь через `embed` (`migrations/schema_test.go:26-43`; `migrations/embed.go`; ADR 005:26). Тест пропускается без `DATABASE_TEST_URL` (`internal/platform/db/dbtest/dbtest.go:52-54`), в CI переменная задана (`Makefile:66-68`).
- **У каждой миграции есть откат.** Во всех файлах `migrations/00001_init.sql` … `00019_general_pick_index.sql` есть секция `-- +goose Down`.
- **Отдельный шаг в Compose.** Сервис `migrate` (`docker-compose.yml:159-170`), api и worker ждут его успешного завершения (`docker-compose.yml:189-191, 265-266`). Задача Compose в CI поднимает проект с нуля (ci.yml:168-169). В Kubernetes миграции — отдельный Job (ADR 032:21; `deploy/k8s/base/migrate.yaml`). Условия «api только после Job» в манифестах нет: порядок держит скрипт выкатки, который ждёт завершения Job (`loadtest/k8s-storm.sh:57-59`).
- **Правило «только новой миграцией» работало на практике.** Ошибки, найденные экспериментами, исправлены новыми миграциями: 00012 (версия места для оптимистичной стратегии), 00017 (владелец ключа идемпотентности), 00018 (ключ запроса заказа), 00019 (индекс входной зоны) ([evidence.md](../evidence.md), «Что нашли эксперименты», :298, :308, :311, :323). В истории git у каждого файла миграции один коммит: после создания ни один не правился (`git log -- migrations/*.sql`).
- **Проверка ловли неполного `Down`** сделана вручную на миграции, которая создаёт таблицу и enum и ничего не удаляет (ADR 002:29). Эта проверка в репозитории не зафиксирована.
- **Измерений нет.** Решение о процессе, нагрузочных чисел к нему нет.

## Вопросы комиссии

1. **Что такое миграция и зачем нужен откат?**
   Ответ: Миграция — пронумерованный SQL-файл, который переводит схему базы из одной версии в следующую. Секция `Up` применяет изменение, `Down` его отменяет. Откат нужен, чтобы вернуть базу к прошлой версии при неудачном выпуске. По правилам проекта каждая миграция должна и применяться, и откатываться.
   Источник: ADR 002, «Контекст» и «Решение», п. 1 (строки 7, 11); `migrations/00019_general_pick_index.sql`.

2. **Почему goose, а не golang-migrate?**
   Ответ: Возможности похожие. В golang-migrate миграция — два файла, `up` и `down`, и нет миграций на Go. В goose обе секции в одном файле, его проще читать.
   Источник: ADR 002:19.

3. **Почему миграции не применяет сам api при старте?**
   Ответ: api работает в нескольких экземплярах, и они начали бы гоняться за блокировку схемы. Упавшая миграция уронила бы api вместо отдельного шага развёртывания. Поэтому миграции применяет одноразовый сервис `migrate`, а api стартует только после его успешного завершения. В Kubernetes миграции применяет Job; там порядок держит не манифест, а скрипт выкатки, который ждёт завершения Job.
   Источник: ADR 002:14, 20; `docker-compose.yml:159-170, 189-191`; ADR 032:21; `loadtest/k8s-storm.sh:57-59`.

4. **Зачем отдельный `tools.mod`?**
   Ответ: goose тянет драйверы всех поддерживаемых СУБД. В основном `go.mod` это дало около 70 косвенных зависимостей, а `go mod tidy` стал скачивать сотни модулей и падать при сетевых сбоях. В `tools.mod` версия и контрольные суммы goose закреплены отдельно, в бинари api и worker драйверы не попадают. В образе миграций лишние драйверы отключены тегами сборки.
   Источник: ADR 002:13, 21, 26; `Dockerfile:18-26`; `Makefile:29-31`.

5. **Как CI понимает, что у миграции неполный `Down`?**
   Ответ: После полного отката SQL-запрос считает в базе таблицы, схемы, типы, функции и расширения, кроме служебной таблицы goose и расширения plpgsql. Если счёт не ноль, шаг падает с сообщением о неполном `Down`. Затем миграции применяются снова, чтобы проверить и повторный `up`.
   Источник: ADR 002:15, 29; ci.yml:100-126.

6. **Почему номера последовательные, а не метки времени?**
   Ответ: Порядок миграций виден сразу. Метки времени нужны, когда несколько человек параллельно создают миграции в разных ветках, а у проекта один разработчик. Новый файл создаёт `make migrate-create name=...`.
   Источник: ADR 002:12; `Makefile:88-90`.

7. **Что будет, если миграция упадёт при `docker compose up`?**
   Ответ: Сервис `migrate` завершится с ошибкой, и api с worker не запустятся: их условие — `service_completed_successfully`. Ошибка видна в логах отдельного шага, а не как падение api. Это и есть довод против применения миграций внутри api.
   Источник: ADR 002:14, 20; `docker-compose.yml:189-191, 265-266`.

8. **Что этой проверкой не доказано?**
   Ответ: CI гоняет цикл на пустой базе. Он не проверяет миграции на больших таблицах с данными: время и блокировки. Неизменность уже применённых миграций держится на правиле, автоматической проверки нет. Ручная проверка с неполным `Down` в репозитории не зафиксирована.
   Источник: ci.yml:100-126; ADR 002:29; CLAUDE.md, «Как работаем».

## Где слабое место

- **Пустая база в CI.** Цикл `up → reset → up` идёт без данных. Миграция, которая на живой базе долго держит блокировку, пройдёт. Пример: 00019 создаёт индекс в `event_seats` обычным `CREATE INDEX` без `CONCURRENTLY`, а такой индекс PostgreSQL строит с блокировкой записи в таблицу (`migrations/00019_general_pick_index.sql`). Почему приемлемо: продакшен-данных у дипломного проекта нет. Что дальше: для больших таблиц — `CREATE INDEX CONCURRENTLY` вне транзакции и прогон миграций на копии с объёмом стадиона.
- **Откат может терять данные.** `Down`, который удаляет колонку или таблицу, по построению удаляет и данные. CI проверяет только, что объекты убраны. Ответ: откат — инструмент для неудачного выпуска сразу после него, а не способ хранения.
- **Неизменность применённых миграций не проверяется.** Правило есть в CLAUDE.md, но CI не сравнивает старые файлы с прошлой версией. Что дальше: шаг CI, который запрещает изменять файлы миграций, уже попавшие в main.
- **`go.mod` уже не совсем чистый.** ADR 002 обещал, что зависимости goose не попадают в `go.mod` (строка 26). ADR 005 добавил в `go.mod` ядро goose и три небольшие зависимости для тестов схемы на временной базе; драйверы других СУБД по-прежнему только в `tools.mod` (ADR 005:26; `go.mod:10`).
- **Ручная проверка не зафиксирована.** Утверждение о пойманной миграции без `Down` (ADR 002:29) опирается на ручной опыт. Ответ: механизм виден в ci.yml:108-124, его можно повторить: удалить `Down` у последней миграции и запустить шаг CI.
