# ADR 001. Модульный монолит и базовый стек

Статус: принято, 2026-09-24

## Контекст

Проект — SaaS для продажи билетов, его ведёт один разработчик до мая 2027. Ядро — корректная продажа мест при конкурентном доступе. В спецификации (`docs/spec.md`) описаны логические сервисы: catalog, booking, payment, ticket и notifications. У них разный профиль нагрузки: каталог в основном читают, бронирование пишет и конфликтует, оплата ждёт внешний шлюз.

Нужно выбрать форму поставки и язык так, чтобы один человек успел сделать MVP. При этом границы сервисов должны остаться видимыми и объяснимыми на защите.

## Решение

1. **Модульный монолит.** Два бинаря из одного репозитория: `cmd/api` (HTTP) и `cmd/worker` (потребитель очереди). Доменные модули лежат в `internal/catalog`, `internal/booking`, `internal/payment` и `internal/ticket` и повторяют сервисы из спецификации. Модули не импортируют друг друга напрямую, а общаются через интерфейсы, объявленные на стороне потребителя. Общая инфраструктура живёт в `internal/platform`.
2. **Бэкенд на Go**, последняя стабильная версия на момент старта — 1.27.1. Версия зафиксирована в `go.mod`.
3. **Фронтенд на Vue с TypeScript и Vite.** Это решение заменяет упоминание React в `docs/spec.md`.

Выбор остальных технологий (хранилища, очередь, наблюдаемость, инструменты тестирования) обсуждается отдельно. По каждой будет свой ADR.

## Альтернативы

- **Микросервисы сразу.** Отдельное развёртывание, сеть и распределённые транзакции между сервисами — большая эксплуатационная нагрузка для одного разработчика. Эксперимент с конкурентным бронированием от этого не выигрывает. Отклонено.
- **Монолит без границ модулей.** Быстрее на старте, но модули быстро сцепляются, и их уже не вынести отдельно. На защите архитектуру тоже сложнее обосновать. Отклонено.
- **React вместо Vue.** Упомянут в спецификации. Разработчику удобнее Vue, а для MVP с кабинетом, покупкой и PWA-сканером существенной разницы нет. Отклонено.

## Следствия

- Один процесс сборки, одна база и простой локальный запуск через Docker Compose.
- Границы модулей держатся дисциплиной и правилом «без прямых импортов между `internal/*`». Нарушения должны ловиться на ревью.
- Модуль под отдельной нагрузкой (например, booking) можно вынести в сервис без переписывания доменной логики.
- API и воркер масштабируются независимо, потому что это разные процессы.
