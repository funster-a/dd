# ADR 003. Проверки состояния и корректная остановка процессов — разбор к защите

Неделя 1 (12–18.10.2026). ADR: [`docs/adr/003-health-checks-and-graceful-shutdown.md`](../../adr/003-health-checks-and-graceful-shutdown.md).

## Суть в трёх фразах

Оркестратору, то есть системе, которая запускает и перезапускает контейнеры, нужно знать, жив ли процесс и можно ли слать ему трафик, а при перезапуске нельзя терять запросы и сообщения в работе. Решение — два эндпоинта с разным смыслом: `/healthz` («процесс жив», зависимости не трогает) и `/readyz` («готов принимать трафик», проверяет зависимости), плюс корректная остановка по SIGTERM: api дорабатывает начатые запросы, worker — текущее сообщение, всё в пределах `SHUTDOWN_TIMEOUT` (15 секунд по умолчанию). Следствие: экземпляр можно вывести из ротации без перезапуска, а выкатка почти незаметна для покупателя, но сообщение очереди может прийти повторно, поэтому обработчики обязаны быть идемпотентными.

Важно: состав проверок `/readyz` позже изменён ADR 030 (см. вопрос 3), а старт api без PostgreSQL с ADR 027 невозможен (см. вопрос 8).

## Почему так, а не иначе

- **Один эндпоинт health с проверкой зависимостей.** Если по нему проверять живость, то при недоступной базе оркестратор начнёт перезапускать здоровые процессы, и они лягут все сразу.
- **Падать при старте без зависимостей.** Порядок запуска становится хрупким, а временная недоступность Redis превращается в перезапуски.
- **Остановка без ограничения по времени.** `pgxpool.Close()` при зависшей базе ждёт бесконечно. Без общего бюджета процесс не завершился бы.

## Чем подтверждено

- **Выкатка почти незаметна.** Эксперимент с отказом экземпляра api, вариант «остановка» (`docker stop`, SIGTERM) при 200 заказах в секунду: по одной неудачной попытке на серию из трёх прогонов, без билета не ушёл никто ([evidence.md](../evidence.md), «Отказоустойчивость», :163; [api-failure/README.md:41,44,69-71](../../experiments/2026-10-api-failure/README.md)). Единственный 502 — запрос, который nginx отправил по keepalive-соединению в момент его закрытия; повтор клиента его закрыл.
- **Для сравнения — падение без остановки.** SIGKILL до исправления ADR 027: 13 из 18 покупателей с оборванными запросами ушли без билета (evidence.md:159). Сравнение не чистое: потери при падении шли в основном от ключа идемпотентности, который оставался «выполняется» минуту (ADR 027:14-16). Корректная остановка до таких обрывов не доводит: начатые запросы доработаны.
- **`/readyz` и `/healthz`.** `TestReadyz` — три случая: всё в порядке (200 `ok`), упала обязательная проверка (503 `unavailable`), упала необязательная (200 `degraded`); `TestHealthz` (`internal/platform/httpx/httpx_test.go:77-113, 115-121`).
- **Таймаут проверок соблюдается.** Тесты против сервера, который принимает соединение и молчит: Redis (`internal/platform/redis/redis_test.go:11-41`) и RabbitMQ (`internal/platform/mq/mq_test.go:42-55`). Ping завершается по дедлайну контекста, а не по своим таймаутам.
- **worker дорабатывает сообщение.** `TestConsumeFinishesInFlightMessageOnCancel`: после отмены обработчик доводит текущее сообщение, его контекст не отменён, остальные сообщения возвращаются в очередь (`internal/platform/mq/consumer_test.go:130-178`).
- **Конфигурация.** `TestLoadInvalid` — неверные значения останавливают загрузку, включая нулевой и отрицательный `SHUTDOWN_TIMEOUT`; `TestLoadDoesNotLeakRabbitMQPassword` и `TestPingInvalidURLDoesNotLeakPassword` — пароль не попадает в текст ошибки (`internal/platform/config/config_test.go:73-108, 110-123`; `internal/platform/mq/mq_test.go:11-20`).
- **Request id.** Генерация, проброс, замена небезопасных значений, поле в логе (`internal/platform/httpx/httpx_test.go:15-75`).
- **Подкоманда `api healthcheck`** для образа distroless: `cmd/api/healthcheck_test.go:10, 35`.
- **Не зафиксировано:** эксперимент с зависанием `pgxpool.Close()` (ADR 003:26) в репозитории не записан. Защита от него видна в коде: `cmd/api/main.go:200-211`.

## Вопросы комиссии

1. **Чем `/healthz` отличается от `/readyz`?**
   Ответ: `/healthz` отвечает 200, пока сервер работает, и зависимости не проверяет. По нему оркестратор решает, перезапускать ли процесс. `/readyz` параллельно проверяет зависимости с общим таймаутом 2 секунды; по нему экземпляр выводят из ротации без перезапуска. В distroless-образе нет curl, поэтому Docker вызывает `api healthcheck`, который сам запрашивает `/healthz`.
   Источник: ADR 003:12-13, 32; `internal/platform/httpx/health.go:11, 16-19, 27-73`; `cmd/api/healthcheck.go:23-25`; `docker-compose.yml:200-201`.

2. **Почему не один эндпоинт health с проверкой базы?**
   Ответ: Если такой эндпоинт служит проверкой живости, то при недоступной базе оркестратор начнёт перезапускать все экземпляры. Перезапуск базу не починит, а здоровые процессы лягут все сразу. Поэтому живость и готовность разделены.
   Источник: ADR 003:24, 30.

3. **Что сейчас проверяет `/readyz`, и совпадает ли это с ADR 003?**
   Ответ: Не совпадает: ADR 030 изменил состав проверок. Сейчас обязательная проверка одна — PostgreSQL, её отказ даёт 503. Redis, хранилище файлов и реплики необязательны, их отказ даёт 200 `degraded`. RabbitMQ из api убран: события публикует воркер. Иначе падение Redis, которое api переживает (ADR 018), вывело бы из ротации все экземпляры сразу.
   Источник: ADR 030:18, 57-65; `cmd/api/main.go:143-148, 222-231`; evidence.md:322.

4. **Что происходит с api при SIGTERM?**
   Ответ: Сервер перестаёт принимать новые соединения и дорабатывает начатые запросы, их контексты сигналом не отменяются. Затем закрываются соединения с зависимостями. Весь выход укладывается в `SHUTDOWN_TIMEOUT`, 15 секунд по умолчанию. С ADR 027 api при остановке ещё и снимает свою отметку в `api_instances`, чтобы его незавершённые ключи идемпотентности сразу освободились.
   Источник: ADR 003:16, 18; `cmd/api/main.go:68, 190-216`; ADR 027:28.

5. **А с worker? Не теряются ли сообщения?**
   Ответ: worker перестаёт брать новые сообщения и дорабатывает текущее. Неподтверждённые сообщения брокер возвращает в очередь. Поэтому сообщение может быть обработано повторно, и все обработчики идемпотентны по правилу 3 из CLAUDE.md.
   Источник: ADR 003:17, 31; `cmd/worker/main.go:98-125`; `internal/platform/mq/consumer_test.go:130-178`.

6. **Как проверено, что остановка не теряет покупателей?**
   Ответ: В эксперименте с отказом экземпляра api при 200 заказах в секунду один из двух экземпляров останавливали через `docker stop`. На серию из трёх прогонов пришлась одна неудачная попытка, без билета не ушёл никто. Для сравнения, падение через SIGKILL до исправления ADR 027 оставило без билета 13 из 18 покупателей с оборванными запросами.
   Источник: evidence.md:159, 163; api-failure/README.md:24, 41, 44, 69-71.

7. **Зачем общий бюджет на остановку? Почему не ждать, сколько нужно?**
   Ответ: `pgxpool.Close()` не принимает контекст и при зависшей базе ждёт бесконечно. Поэтому закрытие зависимостей идёт в отдельной горутине, и процесс ждёт его не дольше остатка бюджета. В Compose `stop_grace_period` больше `SHUTDOWN_TIMEOUT`, в Kubernetes `terminationGracePeriodSeconds: 25` больше 5 секунд `preStop` плюс 15 секунд бюджета.
   Источник: ADR 003:18, 26; `cmd/api/main.go:200-211`; `docker-compose.yml:206-207`; ADR 032:41-44.

8. **Процесс действительно стартует без зависимостей?**
   Ответ: Частично. ADR 003 описывает ленивые подключения: Redis открывает соединение при первом запросе, потребитель RabbitMQ в воркере переподключается сам, сейчас с паузой 1, 2, 4, 5, 5 секунд (ADR 030). Но с ADR 027 api при старте регистрируется в таблице `api_instances`, и без PostgreSQL он завершается с ошибкой. В Compose это не мешает: api стартует после сервиса `migrate`, которому база уже нужна.
   Источник: ADR 003:14; `internal/platform/redis/redis.go:20-27`; `internal/platform/mq/consumer.go:29-55`; ADR 030:46-48; `internal/platform/idempotency/owner.go:35-45`; `cmd/api/main.go:77-81`; ADR 027:22.

9. **Почему неверная настройка останавливает процесс сразу, и почему в ошибках нет строк подключения?**
   Ответ: Иначе ошибка всплыла бы позже бесконечными переподключениями. Все значения проверяются при старте, ошибки собираются вместе. Ошибки разбора URL в Go цитируют строку целиком, вместе с паролем, поэтому проверка возвращает общее сообщение без адреса. Это закреплено тестами.
   Источник: ADR 003:19; `internal/platform/config/config.go:138-143, 237-245`; `config_test.go:73-108, 110-123`.

10. **Что здесь не доказано?**
    Ответ: Эксперимент с зависанием `pgxpool.Close()` в репозитории не записан, есть только защита в коде. Остановка проверена в трёх прогонах на серию на одной машине. В Kubernetes поды снимались без трафика, снятие пода под нагрузкой без ошибок не проверялось. В Compose балансировщик nginx `/readyz` не читает, вывод из ротации по готовности работает только в Kubernetes.
    Источник: ADR 003:26; evidence.md:163, 214; `deploy/nginx/api-lb.conf:19-20, 62`; ADR 032:40.

## Где слабое место

- **В Compose `/readyz` никто не читает.** Docker проверяет `/healthz` через `api healthcheck` (`docker-compose.yml:200-201`), а nginx повторяет запрос на другой экземпляр только при ошибке соединения (`deploy/nginx/api-lb.conf:36, 62`). Следствие ADR 003 «балансировщик выводит экземпляр по `/readyz`» (строка 30) реализовано в Kubernetes: проба готовности читает `/readyz` (ADR 032:40). Почему приемлемо: Compose — локальный запуск и стенд экспериментов. Что дальше: на продакшене это делает проба готовности оркестратора.
- **Ленивый старт api ослаблен.** С ADR 027 api без PostgreSQL не стартует (`internal/platform/idempotency/owner.go:37-44`). Ответ: без PostgreSQL api всё равно не работает, это обязательная зависимость и по ADR 030; в Kubernetes под будет перезапускаться, пока база не появится.
- **Запрос дольше бюджета обрывается.** Если начатый запрос не уложился в `SHUTDOWN_TIMEOUT`, `srv.Shutdown` вернёт ошибку и процесс выйдет (`cmd/api/main.go:195, 213-215`). Ответ: клиент повторяет запрос с тем же ключом идемпотентности, а ключ остановленного экземпляра снимается сразу (ADR 027:28).
- **Повторная обработка сообщений.** Остановка и сбой возвращают неподтверждённые сообщения в очередь (ADR 003:31). Это не дефект, а цена доставки «хотя бы один раз»; её закрывает идемпотентность обработчиков (ADR 008, ADR 012).
- **«Готов» не значит «тот самый процесс».** Первая серия эксперимента со стратегиями прошла целиком на одной стратегии: порт занимал тестовый процесс api, и `/readyz` отвечал от него. Серию выбросили, скрипты теперь отказываются работать при занятом порте (evidence.md:297; ADR 017:91).
- **Мало прогонов.** Остановка — три прогона на серию, одна машина, падение процесса, а не разделение сети (evidence.md, «Границы доказательства», :385, :387, :419).

## Проверь себя

1. Почему `/readyz` с обязательным Redis остановил бы продажу целиком при падении одного Redis, хотя каждый экземпляр api без него работает?
2. Зачем в Kubernetes `preStop: sleep 5` перед SIGTERM, если api и так дорабатывает начатые запросы?
3. Как middleware request id защищает логи от подстановки текста клиентом, и что nginx делает с этим заголовком перед api (`internal/platform/httpx/requestid.go:27-41, 59-71`; `deploy/nginx/api-lb.conf:35, 57`)?
