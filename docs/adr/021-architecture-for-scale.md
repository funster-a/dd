# ADR 021. Направление архитектуры: масштаб и отказоустойчивость

Дата: 2026-10-03. Статус: принято.

## Контекст

Бизнес-решение от 2026-10-03: платформа идёт сразу в два сегмента — МСБ и крупные организаторы. Первое, что нужно крупным, — большие площадки: стадионы и арены на 30–50 тысяч мест, сотни тысяч билетов за минуты после старта продаж.

Сейчас система — модульный монолит (ADR 001, 004) в одном экземпляре api. Эксперименты (ADR 017, 020) показали:
- на одной машине предел — общий путь запроса;
- с очередью ожидания один экземпляр продаёт зал на 1000 мест без ошибок и с p95 в десятки миллисекунд.

Для стадиона и для требования «не падать» этого мало. Нужен ответ: как растёт архитектура.

## Решение

### Масштабируемый монолит, а не микросервисы ради количества

Система остаётся модульным монолитом и масштабируется горизонтально:
- **Один бинарь — много экземпляров.** api не хранит состояния, которое нельзя потерять. Истина — в PostgreSQL, холды, очередь и сессии — в Redis. Локальное у экземпляра — только кэши, которые можно потерять: кэш проверенных сессий (ADR 018), объединение одинаковых запросов занятости.
- **Модуль выносится в отдельный сервис, только когда у его нагрузки своя граница и это видно в метриках.** Кандидаты уже понятны:
  - **читающий контур** — публичные страницы и схемы залов: их читают все, они кэшируются, им не нужна основная база;
  - **уведомления и выпуск билетов** — уже в воркере.

  Граница проходит там, где её показали измерения, а не там, где её можно нарисовать.
- **Отказоустойчивость — у каждого звена:**
  - несколько экземпляров api и воркера;
  - PostgreSQL с репликой и автоматическим переключением;
  - Redis Sentinel;
  - кластер RabbitMQ с кворумными очередями.

  Корректность при отказах уже держится на базе. Отказ Redis не останавливает продажу (ADR 017, 018, 020).

### Каждый шаг доказывается экспериментом

Этапы — в spec.md, «План развития после MVP». У каждого этапа свой измеримый результат:
- график «экземпляры → пропускная способность»;
- штурм стадиона на 50 тысяч мест;
- хаос-эксперименты посреди продажи.

Первый этап — наблюдаемость. Без неё остальные нечем доказывать.

## Альтернативы

- **Микросервисы сразу** — каталог, бронирование, оплата, билеты, уведомления и шлюз отдельными сервисами.
  - Больше квадратиков на схеме, но у одного разработчика это пять деплоев, сетевые отказы между сервисами и распределённые транзакции там, где сейчас одна транзакция PostgreSQL.
  - Главный инвариант — место не продаётся дважды — сейчас держит одна транзакция. В микросервисах ему понадобилась бы сага.
  - Крупного клиента убеждают не сервисы на схеме, а продажа без падений на графиках.
- **Масштабирование вверх: одна большая машина.** Проще, но это не отказоустойчивость. И предел виден заранее: ядра одной машины.
- **Шардирование базы по событиям.** Нужно на порядки больших объёмах. Одно событие на 50 тысяч мест помещается в одну базу; горячая точка там — строки мест, и её уже снимают очередь и холды в Redis.

## Следствия

- Этапы развития и их эксперименты записаны в spec.md.
- Раздел «Архитектура» в spec.md приведён к фактическому устройству: Vue, nginx, модульный монолит, воркер. Прежняя схема с API Gateway и отдельными сервисами описывала намерение, которое этот ADR пересматривает.
- Любой новый общий ресурс (локальный кэш, планировщик, блокировка) проверяется на работу при нескольких экземплярах api. Если он не переживает это, ему место в Redis или PostgreSQL.
