# ADR 022. Наблюдаемость: метрики, дашборд, алерты

Дата: 2026-10-03. Статус: принято.

## Контекст

Первый этап плана развития (spec.md, ADR 021): без наблюдаемости следующие этапы — масштабирование, большие площадки, хаос-эксперименты — нечем доказывать и нечем эксплуатировать.

Что было:
- у api — метрики бронирования (ADR 017) и сессий (ADR 018), Prometheus и Grafana в Compose;
- дашбордов не было;
- у воркера метрик не было вовсе;
- состояние PostgreSQL, Redis и RabbitMQ не собиралось.

## Решение

### Что собираем

| Источник | Метрики | Зачем |
|---|---|---|
| api, все запросы | `dd_http_requests_total{route,method,code}`, `dd_http_request_duration_seconds`, `dd_http_requests_in_flight` | частота, ошибки и длительность по маршрутам; маршрут — шаблон chi, а не путь, чтобы id не плодили ряды |
| api, бронирование и очередь | `dd_booking_*` (ADR 017, 019, 020) | продажи, отказы, очередь, предохранитель Redis |
| api, сессии | `dd_identity_*` (ADR 018) | проверка сессий без Redis |
| worker, очереди | `dd_mq_messages_total{queue,result}`, `dd_mq_handle_seconds` | обработка событий между модулями, сообщения в очереди недоставленных |
| worker, outbox | `dd_outbox_pending`, `dd_outbox_oldest_pending_seconds`, `dd_outbox_published_total` | вставший outbox — оплаты проходят, а билеты не выпускаются |
| worker, заказы | `dd_booking_orders_expired_total` | закрытые неоплаченные заказы |
| PostgreSQL | `postgres-exporter` | соединения по состоянию, транзакции, взаимоблокировки |
| Redis | `redis_exporter` | команды, клиенты, память |
| RabbitMQ | встроенный плагин `rabbitmq_prometheus` | сообщения в очередях, соединения, потребители |

**Метрики воркера.** У воркера отдельный HTTP-сервер только для `/metrics` (`METRICS_ADDR`, `:9091`), порт открыт только внутри сети Compose.

**Отставание outbox** считается при каждом сборе метрик одним запросом по частичному индексу неопубликованных событий, с таймаутом 2 секунды. Отдельного счётчика, который мог бы разойтись с базой, нет.

**api на машине разработчика.** Prometheus собирает и api, запущенный на машине разработчика (задания `api-local` и `worker-local` через `host.docker.internal`). Нагрузочные эксперименты запускают api вне Docker, и их прогоны видны на дашборде сразу.

### Дашборд как код

Дашборд «Партер: продажи и система» лежит в репозитории (`deploy/grafana/dashboards/dd-overview.json`) и подключается провижинингом Grafana.
- **Правки — через JSON.** Изменения в интерфейсе не сохраняются: дашборд правится в JSON и проходит ревью.
- **Разделы:**
  - продажи: заказы в секунду, время оформления p50/p95/p99, отказы и кто отказал, очередь, предохранители Redis;
  - HTTP по маршрутам;
  - воркер: outbox, обработка сообщений, RabbitMQ;
  - хранилища и процессы.
- **Источник данных** создаётся с постоянным uid `prometheus`, на него ссылаются панели. Провижининг удаляет и пересоздаёт источник: иначе Grafana со старым томом не стартует, потому что источник с тем же именем, но другим uid уже существует. Это поймано при проверке на существующем стенде.

### Алерты

Правила — в `deploy/prometheus/alerts.yml`, проверяются `promtool`. Каждое правило — симптом, который видит покупатель или организатор, или явный предвестник:

| Алерт | Условие | Что значит |
|---|---|---|
| `DDTargetDown` | цель недоступна минуту | упал api, worker или хранилище |
| `DDHighErrorRate` | больше 5% ответов 5xx за 5 минут | покупатели получают ошибки |
| `DDSlowBooking` | оформление заказа p95 дольше секунды | пик без очереди или нехватка экземпляров |
| `DDOutboxStuck` | событие ждёт публикации больше минуты | билеты не выпускаются, возвраты не идут |
| `DDDeadLetters` | сообщения уходят в очередь недоставленных | обработчик события падает |
| `DDRedisDegraded` | сработал предохранитель Redis | продажа идёт без фильтра или без проверки сессий |
| `DDQueueBypassed` | очередь пропускает без проверки | пик без сглаживания |

Alertmanager и доставка уведомлений не входят в этап: алерты видны в Prometheus и Grafana. Доставка понадобится вместе с продакшен-окружением.

## Альтернативы

- **OpenTelemetry с трассировкой.** Трассы показали бы путь одного запроса через модули. Для монолита в одном процессе это меньше, чем дают метрики по маршрутам и модулям, а коллектор и хранилище трасс — ещё два сервиса. Вернёмся к этому, когда модули начнут выноситься в отдельные сервисы (ADR 021).
- **Метрики через промежуточный агент (Grafana Agent, Alloy).** Нужен при многих машинах. В Compose Prometheus собирает цели напрямую.
- **Готовые дашборды экспортёров из каталога Grafana.** Подробнее по каждой системе, но это десятки панелей, которые никто не смотрит. Наш дашборд показывает то, что важно в пик продаж, на одном экране.

## Следствия

- **Код.** Новые метрики api (HTTP) и воркера, `/metrics` у воркера, настройка `METRICS_ADDR`.
- **Compose.** Сервисы `postgres-exporter`, `redis-exporter`. Конфигурация Prometheus, алерты и дашборд — файлами в `deploy/`.
- **CI.** Тест Compose проверяет, что Prometheus видит api, worker и хранилища, правила алертов загружены, а дашборд есть в Grafana.
- **Проверено вживую.** Серия «без очереди / очередь 200 в секунду» на 2000 покупателях видна на дашборде целиком. Снимок — `docs/observability/grafana-overview.png`.
