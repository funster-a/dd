# ADR 006. Идентификация и доступ — разбор к защите

Неделя 2 (19–25.10.2026). ADR: [`docs/adr/006-identity-and-access.md`](../../adr/006-identity-and-access.md).

## Суть в трёх фразах

Администратору платформы, организатору, контролёру на входе и покупателю нужен вход без паролей и мгновенный отзыв доступа. Решение — вход по одноразовому коду (покупателю по SMS, организатору и администратору по email), сессия — случайный токен, хеш которого лежит в Redis вместе с ролью и арендатором, а контролёр получает отдельную ссылку на одно событие. Отсюда выход действует сразу и роль с арендатором берутся только из сессии, но вход и проверка сессий зависят от Redis.

Зависимость от Redis позже смягчили:
- ADR 018: при отказе Redis знакомая сессия проверяется по кэшу в памяти api;
- ADR 029: Redis пишет журнал на диск и работает с репликами под Sentinel;
- ADR 020: лимиты по IP считаются по настоящему адресу клиента за прокси;
- ADR 013 реализовал ссылки сканера: хеш токена хранится в PostgreSQL, отзыв ставит отметку `revoked_at`, а не удаляет запись (`migrations/00010_scanner_links.sql:13`; `internal/ticket/queries.sql:48-50`).

## Почему так, а не иначе

- **JWT.** Хранилище не нужно, но токен нельзя отозвать до истечения срока. Для организатора с доступом к деньгам это существенно. Для отзыва понадобился бы чёрный список в Redis, и выигрыш исчезает.
- **Пароли.** Хранение, сброс и утечки паролей плюс лишний шаг для покупателя.
- **Внешний провайдер идентификации** (Keycloak, Auth0 и подобные). Лишний сервис или внешняя зависимость ради четырёх простых сценариев входа.
- **Учётные записи для контролёров.** Организатору пришлось бы управлять пользователями ради одного вечера на входе. Ссылка сканера проще и отзывается так же.

## Чем подтверждено

- **Код одноразовый даже при одновременных входах:** 20 параллельных входов с одним верным кодом, сессию получает ровно один. `TestCodeIsSingleUseUnderConcurrency`, `internal/identity/identity_test.go:168-211`. Атомарность даёт Lua-скрипт в Redis: `internal/identity/codes.go:34-52`.
- **Попытки ограничены:** после 5 неверных попыток не принимается даже верный код. `identity_test.go:213-235`; константы `codes.go:19-25`.
- **Лимит запросов кода с одного IP:** `identity_test.go:237-250`.
- **Неизвестному организатору код не уходит, ответ тот же:** перебрать email по ответам нельзя. `identity_test.go:272-287`; администратору — только из списка, `identity_test.go:289-313`.
- **Отзыв мгновенный:** после выхода токен не проходит (`identity_test.go:315-332`). Выход на другом экземпляре api тоже действует сразу, даже если сессия есть в кэше, пока Redis отвечает (`internal/identity/cache_test.go:33-55`).
- **Роль проверяется на уровне HTTP:** 401 без сессии, 403 при чужой роли. `internal/platform/auth/auth.go:47-64`, тест `auth_test.go:9`.
- **Арендатор из сессии:** middleware кладёт участника в контекст (`internal/identity/http.go:63`), catalog берёт `organizer_id` оттуда (`internal/catalog/http.go:219-222`); изоляцию проверяет `internal/catalog/venues_test.go:89-139`.
- **Отказ Redis в эксперименте со стратегиями:** после предохранителя холдов все оставшиеся ошибки были на входе — 6 118 ошибок `load session`. После кэша сессий (ADR 018): 984 успеха, 0 ошибок (evidence.md:300, 43). Оговорка: серия с отказом шла с прогревом сессий `WARMUP=1`, без прогрева незнакомые сессии получают 503 (evidence.md:43).
- **Перезапуск Redis без журнала:** все сессии пропали, без билета ушли 12 130 из 17 907 покупателей. С журналом и Sentinel — 0 (evidence.md:170, 314).
- **Холодный старт без очереди:** 4 866 из 5 000 покупателей получили 503 `session_store_unavailable` (evidence.md:119). Защита — очередь ожидания (ADR 020).
- **Не измерено:** вход по коду под нагрузкой. Сидер экспериментов выдаёт сессии без кода (`IssueBuyerSession`, ADR 017:46). Отдельного замера стоимости проверки сессии нет. ADR 017:58 относит её к общему пути запроса, который ограничивает все стратегии.

## Вопросы комиссии

1. **Почему вход без паролей?**
   Ответ: Пароль нужно хранить, сбрасывать и защищать от утечек, а покупателю это лишний шаг перед покупкой. Одноразовый код приходит на телефон или почту, которыми человек уже владеет. Код — 6 цифр, живёт 5 минут и даёт не больше 5 попыток.
   Источник: ADR 006, «Решение», п. 1 (строки 18-22); «Альтернативы» (строка 35); `internal/identity/codes.go:19-25, 94-110`.

2. **Почему не JWT, ведь это стандарт?**
   Ответ: JWT нельзя отозвать до истечения срока, а у организатора доступ к деньгам. Для отзыва понадобился бы список отозванных токенов в Redis, то есть то же хранилище. Непрозрачный токен проверяется одним запросом в Redis, а выход удаляет ключ и действует сразу.
   Источник: ADR 006, п. 2 (строки 23-26); «Альтернативы» (строка 34); `internal/identity/sessions.go:74-79`.

3. **Что лежит в Redis и что получит злоумышленник, если прочитает Redis?**
   Ответ: Ключ сессии — SHA-256 от токена, значение — участник, роль, арендатор и срок. Сам токен в Redis не хранится, поэтому по дампу Redis войти нельзя. Код входа тоже хранится как хеш вместе с адресом. Токен — 32 случайных байта, срок жизни — 30 дней у покупателя и 12 часов у организатора и администратора.
   Источник: ADR 006, п. 2 (строка 24); `internal/identity/sessions.go:22-34, 40-57, 81-84`; `codes.go:129-133`.

4. **Как организатор A не увидит данные организатора B?**
   Ответ: Middleware кладёт в контекст `organizer_id` из сессии, и все запросы к данным организатора фильтруются по нему. Идентификатор организатора из URL или тела запроса для авторизации не используется. Тест проверяет, что чужая площадка отвечает «не найдено», как несуществующая. Так закрывается следствие ADR 005: от чтения чужих данных защищает код.
   Источник: ADR 006, п. 3 (строка 27); `internal/identity/http.go:35-63`; `internal/platform/auth/auth.go:29-31`; `internal/catalog/http.go:219-222`; `internal/catalog/venues_test.go:89-139`.

5. **Что будет, если Redis упадёт?**
   Ответ: По исходному решению вход и проверка сессий перестают работать. В эксперименте это дало 6 118 ошибок `load session`. ADR 018 добавил кэш успешных проверок в памяти api: знакомая сессия проходит до 10 минут, незнакомая получает 503 с `Retry-After`. После этого при упавшем Redis продано 984 места без ошибок. Новый вход без Redis по-прежнему невозможен: коды тоже живут в нём.
   Источник: ADR 006, «Следствия» (строка 41); ADR 018:9-13, 19-24; evidence.md:300, 43.

6. **А если Redis не просто недоступен, а перезапустился пустым?**
   Ответ: Это хуже простоя. Redis со снимками на диск потерял все сессии, api отвечал `401 invalid_session`, и без билета ушли 12 130 из 17 907 покупателей. ADR 029 включил журнал AOF с записью раз в секунду и Sentinel с двумя репликами. В той же серии без билета не ушёл никто, запись снова доступна через 3 секунды.
   Источник: ADR 029:21-24, 28-47; evidence.md:170, 314.

7. **Как защищены от перебора кода и от разорения на SMS?**
   Ответ: Проверка кода атомарна: Lua-скрипт считает попытку и сжигает код после пятой неудачи. Запросы кода ограничены по адресату и по IP. Этот лимит сначала работал неверно: за nginx api видел адрес nginx, и лимит был общим на всех. ADR 020 исправил это: адрес клиента берётся из `X-Forwarded-For` только от доверенного прокси.
   Источник: ADR 006, п. 1 (строка 21); `internal/identity/codes.go:34-91`; ADR 020:11, 15-20; evidence.md:302.

8. **Как работает доступ контролёра без учётной записи?**
   Ответ: Организатор создаёт ссылку сканера на одно событие. Токен — 256 случайных бит, в базе хранится только SHA-256, сам токен лежит во фрагменте адреса и не попадает в логи сервера. Ссылка разрешает только список билетов и сканирования этого события. Отзыв ставит отметку `revoked_at`, и отозванная ссылка не принимается.
   Источник: ADR 006, п. 5 (строка 29); ADR 013:21-24; `migrations/00010_scanner_links.sql:6-16`; `internal/ticket/queries.sql:48-50`; `internal/ticket/scanner.go:131-150`.

9. **Почему администраторы заданы списком в конфигурации, а не таблицей?**
   Ответ: Администраторов один-два человека, и таблица с интерфейсом управления ради них не нужна. Список берётся из `ADMIN_EMAILS`, элемент без `@` конфигурация отклоняет при старте. Код уходит только адресу из списка.
   Источник: ADR 006, п. 4 (строка 28); `internal/platform/config/config.go:197-207`; `internal/identity/identity_test.go:289-313`.

10. **Что в этом решении не проверено?**
    Ответ: SMS и email не подключены: код пишется в лог через заглушку. Стоимость SMS не посчитана, это отдельное будущее решение. Вход по коду под нагрузкой не мерился: сидер экспериментов выдаёт сессии без кода. Кэш сессий даёт окно, в котором отозванная сессия может пройти при отказе Redis.
    Источник: ADR 006, «Следствия» (строка 43); `internal/identity/sender.go:16-27`; ADR 017:46; ADR 018:38-45.

## Где слабое место

- **Redis — обязательная зависимость входа.** Ограничение записано в «Следствиях» (строка 41). Почему приемлемо: без Redis не работают и холды. Что сделано дальше: кэш знакомых сессий (ADR 018) и Sentinel с журналом (ADR 029). Новый вход без Redis по-прежнему невозможен.
- **Отзыв не всегда мгновенный.** После ADR 018 отозванная сессия может пройти, если одновременно: Redis недоступен, выход был на другом экземпляре api и этот экземпляр проверял сессию не больше 10 минут назад (ADR 018:38-45). Это бизнес-цена, её подтвердил владелец (ADR 018:15). Пока Redis отвечает, отзыв действует сразу (`cache_test.go:33-55`).
- **Кэш живёт в процессе.** api, перезапущенный во время отказа Redis, отвечает 503 на все запросы с токеном до восстановления Redis (ADR 018:71). На холодном старте без очереди 503 получили 4 866 из 5 000 покупателей (evidence.md:119). Ответ: от этого защищает очередь ожидания, сессии попадают в кэш до покупки.
- **SMS-провайдера нет.** Вход покупателя работает через заглушку (`sender.go:16-27`). Стоимость SMS и выбор провайдера — будущее решение (строка 43).
- **Один вход на организатора.** `organizer_members` хранит только владельца, роли `manager` и `controller` зарезервированы (строка 42). Ответ: для MVP организатор — один человек; сотрудники — отдельная задача.
- **Лимит по IP грубый.** С одного IP — не больше 20 запросов кода в час (`internal/identity/codes.go:24`). За NAT мобильного оператора одним адресом выходят сотни абонентов: ADR 020:28 пишет это про лимит билетов на IP, к лимиту кодов это относится так же. Под нагрузкой лимит кодов не проверялся: сидер выдаёт сессии без кода (ADR 017:46).

## Проверь себя

1. Почему в Redis хранится SHA-256 токена, а не сам токен, и почему для токена хватает SHA-256 без соли, хотя для паролей так делать нельзя?
2. Организатор вышел из кабинета на одном экземпляре api ровно в момент отказа Redis. Где и как долго его токен ещё может пройти?
3. Чем ссылка сканера отличается от сессии организатора по месту хранения, способу отзыва и зависимости от Redis?
