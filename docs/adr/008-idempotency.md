# ADR 008. Идемпотентность изменяющих запросов

Статус: принято, 2026-09-28

## Контекст

Правило 3 из `CLAUDE.md`: все изменяющие эндпоинты идемпотентны по ключу запроса, и повтор возвращает прежний результат. Для продажи билетов это критично: покупатель жмёт «купить» при плохой связи, фронтенд повторяет запрос, и второй заказ появляться не должен. Таблица `idempotency_keys` заложена в ADR 005, здесь описан механизм.

## Решение

1. **Общее middleware** `internal/platform/idempotency`, которое подключается к любому изменяющему маршруту. Клиент передаёт заголовок `Idempotency-Key` (1–255 символов), без него — 400.
2. **Область ключа** — «кто вызывает + метод + шаблон маршрута». Одинаковые ключи разных пользователей и разных эндпоинтов не пересекаются.
3. **Ключ занимается атомарно**: `INSERT … ON CONFLICT DO NOTHING`. Из одновременных запросов с одним ключом обработчик выполняет ровно один, остальные получают 409 `request_in_progress`. Это проверено тестом на 20 параллельных запросов.
4. **Повтор** с тем же ключом и тем же запросом (хеш метода, адреса и тела) получает сохранённый ответ байт в байт, с тем же кодом и `Content-Type`, и заголовком `Idempotent-Replayed: true`. Тот же ключ с другим телом — 422 `idempotency_key_reused`.
5. **Ответ хранится как `bytea`**, а не `jsonb`: `jsonb` нормализует пробелы и порядок ключей, и повтор отличался бы от оригинала. Это поймал тест, исправлено миграцией `00004`.
6. **Сохраняются только 2xx и 4xx.** На 5xx ключ снимается, чтобы клиент мог повторить запрос после сбоя. Ответ больше 1 МБ тоже не сохраняется: целиком его не повторить.
7. **Брошенный ключ** (процесс упал посреди запроса) через минуту можно занять заново.
8. **Исключение — вход** (`/v1/auth/*`). Ответ содержит токен сессии, хранить его в таблице нельзя. Повтор безопасен и так: код одноразовый.

## Альтернативы

- **Ключи в Redis.** Быстрее, но Redis может потерять данные, и после сбоя повтор создал бы вторую сущность. Для денег и заказов нужна надёжность PostgreSQL, запросов с ключами немного. Отклонено.
- **Идемпотентность внутри каждого обработчика** (например, уникальный ключ в таблице заказов). Надёжно для одной таблицы, но каждый эндпоинт пришлось бы делать отдельно, а правило требует одинакового поведения везде. Такая защита остаётся дополнительной там, где она естественна, например уникальность платежа у шлюза.
- **Держать блокировку до конца запроса, а не отвечать 409.** Второй запрос ждал бы первого и получал его ответ, но висящие соединения под нагрузкой хуже быстрого 409, на который клиент отвечает повтором.

## Следствия

- Фронтенд генерирует ключ на каждое действие пользователя (UUID) и повторяет запрос с тем же ключом.
- Таблица растёт. Записи старше суток можно удалять фоновой задачей: индекс по `created_at` для этого уже есть, задача появится вместе с worker-задачами.
