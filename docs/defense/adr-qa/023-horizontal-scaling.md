# ADR 023. Горизонтальное масштабирование api и воркера — разбор к защите

Неделя 6 (16–22.11.2026). ADR: [`docs/adr/023-horizontal-scaling.md`](../../adr/023-horizontal-scaling.md).

## Суть в трёх фразах

Этап 2 плана развития должен был проверить, что api и воркер можно запустить в нескольких экземплярах, и показать, как от этого растёт пропускная способность. Каждый ресурс в памяти экземпляра проверили, состояние уже жило в PostgreSQL и Redis, поэтому в Compose api и воркер стали репликами, а перед api встал nginx, который находит экземпляры через DNS Docker. Эксперимент дал рост ёмкости с 200 до 500 заказов в секунду при переходе с одного экземпляра на два, на четырёх узким местом стали база и общая машина стенда, а ещё нашёлся дефект предохранителя Redis, который исправили полуоткрытым режимом.

Позже часть решений уточнили:
- **ADR 027.** «Повтор — дело клиента, с тем же ключом» (ADR 023:31) при падении экземпляра не работал: ключ упавшего экземпляра минуту оставался «выполняется», и 13 из 18 покупателей с оборванными запросами ушли без билета. У ключа появился владелец, после исправления без билета не ушёл никто (ADR 027:14-31; evidence.md:159-160). Балансировщик не менялся (ADR 027:51).
- **ADR 026.** В памяти экземпляра появился ещё один ресурс — сводка занятости на 1 секунду (`AVAILABILITY_SUMMARY_TTL`). Устаревание безвредно: место проверяет заказ (ADR 026:19-22).
- **ADR 031.** Сайт ходит в api не напрямую по имени сервиса (ADR 023:32), а через `api-lb`: там кэш на краю (ADR 031:59; `docker-compose.yml`, `web`, `API_UPSTREAM`).
- **ADR 032.** Альтернатива «Kubernetes уже сейчас» реализована этапом 6. Край в кластере находит поды тем же приёмом — DNS, перечитываемый каждые 10 секунд (ADR 032:75-79).

## Почему так, а не иначе

- **Kubernetes уже сейчас.** Это этап 6. Compose с репликами и nginx проверяет главное — что api не хранит состояния — без кластера на ноутбуке (ADR 023:70).
- **Липкие сессии на балансировщике.** Нужны, когда состояние в памяти, а его нет. Липкость мешала бы ровной нагрузке и переживанию отказа экземпляра (ADR 023:71).
- **Общий кэш сессий в Redis вместо локального.** Локальный кэш нужен именно на случай отказа Redis (ADR 018); кэш в том же Redis этот случай не закрывает (ADR 023:72).
- **Лидер среди воркеров** для релея outbox и закрытия заказов. `FOR UPDATE SKIP LOCKED` даёт то же без выборов лидера и без простоя при его отказе (ADR 023:73).
- **Предохранитель с фиксированным временем без проб.** Проще, но эксперимент показал, что он превращает короткую задержку в 5 секунд отказов (ADR 023:74).

## Чем подтверждено

Эксперимент [`docs/experiments/2026-10-scaling`](../../experiments/2026-10-scaling/README.md): экземпляры по четверть ядра, пул 20 на экземпляр, ступени 50–1200 заказов в секунду по 20 с, зал 6 000 мест, 5 000 покупателей, одна машина 4 vCPU (evidence.md:130).
- **Ёмкость при 1 / 2 / 4 экземплярах:** 200 / 500 / 500 заказов в секунду; ёмкость — наибольший поток при p95 < 500 мс и ошибках < 1 % (evidence.md:120).
- **p95 на пределе ёмкости:** 105 / 277 / 194 мс (evidence.md:121).
- **Загрузка на пределе:** CPU экземпляра 104 % / 101 % / 69 % лимита, PostgreSQL 0,57 / 1,08 / 1,00 ядра (evidence.md:122).
- **Один экземпляр упирается в процессор:** p95 105 мс на 200/с, 1,7 с на 250, 3,9 с на 300; больше ≈265 успешных заказов в секунду он не отдаёт (evidence.md:124).
- **На четырёх роста нет:** экземпляры загружены на 69 %, PostgreSQL до 1,4 ядра, `vmstat` показывал 4–7 % простоя машины (evidence.md:125).
- **Полуоткрытый предохранитель:** один экземпляр, пол-ядра, 400 заказов в секунду — p95 3 623 → 127 мс, не выпущено k6 471 → 0 (evidence.md:128).
- **Тест предохранителя:** из 100 одновременных запросов в открытый предохранитель пробой проходит ровно один. `TestGateSingleProbe`, `internal/platform/redis/gate_test.go:44-69`; evidence.md:129.
- **Двойных броней 0:** по итоговой проверке после каждой конфигурации, 3 проверки (evidence.md:70, 279).
- **CI:** Prometheus видит 2 экземпляра api и 2 воркера (`.github/workflows/ci.yml:210-213`).

## Вопросы комиссии

1. **Что проверял этот этап и что пришлось переделать?**
   Ответ: Проверяли, что api и воркер работают в нескольких экземплярах, и мерили ёмкость при 1, 2 и 4 экземплярах. Каждый ресурс в памяти экземпляра разобран в таблице ADR. Переделывать архитектуру не пришлось: состояние уже жило в базе и Redis. Исправлен один дефект — предохранитель Redis.
   Источник: ADR 023:7, 13-24, 36-51.

2. **Как nginx находит экземпляры и как добавить экземпляр на ходу?**
   Ответ: Адрес api записан в переменную, и nginx разрешает имя через DNS Docker с `valid=10s`. DNS отдаёт адреса всех реплик, запросы идут по кругу. Команда `docker compose up -d --scale api=4 --no-recreate` добавляет экземпляры, и они попадают в балансировку за 10 секунд без перезапуска nginx.
   Источник: ADR 023:28-30; `deploy/nginx/api-lb.conf:17, 49-51`; `docker-compose.yml`, `deploy.replicas: ${API_REPLICAS:-2}`.

3. **Что лежит в памяти экземпляра и почему это не ломает корректность?**
   Ответ: Кэш проверенных сессий — читается только при отказе Redis. Склейка одновременных одинаковых запросов — живёт, пока запрос выполняется. Состояние предохранителя — у каждого экземпляра своё, потому что каждый сам видит свою связь с Redis. Брони, заказы, холды, очередь и сессии — в PostgreSQL и Redis, общих для всех. Позже ADR 026 добавил сводку занятости на 1 секунду: она может устареть на секунду, но место проверяет заказ.
   Источник: ADR 023:15-22; ADR 026:19-22.

4. **Как два воркера не обрабатывают одну строку outbox или один заказ? Почему не выбрать лидера?**
   Ответ: Пачка выбирается `FOR UPDATE SKIP LOCKED`: строку, которую уже взял другой воркер, запрос пропускает. Это даёт то же, что лидер, без выборов и без простоя, если лидер упал. Воркеров можно запускать сколько угодно, в Compose их два.
   Источник: ADR 023:22, 73; `internal/platform/outbox/queries.sql:5-10`; `internal/booking/queries.sql:107-114`.

5. **Почему не липкие сессии на балансировщике?**
   Ответ: Липкость нужна, когда состояние покупателя в памяти экземпляра, а его нет: сессии и холды в Redis, заказы в PostgreSQL. Любой экземпляр обслужит любой запрос. Липкость только мешала бы делить нагрузку поровну и переживать отказ экземпляра.
   Источник: ADR 023:71.

6. **Назовите числа: как растёт ёмкость с числом экземпляров?**
   Ответ: Один экземпляр — 200 заказов в секунду, два — 500, четыре — тоже 500. p95 на пределе — 105, 277 и 194 мс. Рост в 2,5 раза с одного на два — отношение ступеней: предел одного между 200 и 250, двух — между 500 и 600. Экземпляр ограничен четвертью ядра, это модель небольшого узла.
   Источник: ADR 023:57-63; evidence.md:120-121, 123.

7. **Почему на четырёх экземплярах роста нет?**
   Ответ: Экземпляры загружены только на 69 % лимита, запас у api есть. PostgreSQL на 500 заказах в секунду занимает целое ядро и до 1,4 ядра выше, рядом k6 и nginx, и машина уходит почти в ноль простоя: 4–7 % по `vmstat`. Узкое место — база вместе с общей машиной стенда, а не api.
   Источник: ADR 023:61, 64; evidence.md:122, 125.

8. **Что за дефект предохранителя нашёл эксперимент и как его исправили?**
   Ответ: На перегруженной машине одна медленная команда Redis открывала предохранитель на 5 секунд при здоровом Redis. Всё это время сессии вне кэша получали 503, а захват шёл без фильтра холдов. Теперь, пока предохранитель открыт, раз в 100 мс один запрос проходит пробой, и удачная проба сразу закрывает его. На одном экземпляре с пол-ядра при 400 заказах в секунду p95 упал с 3 623 до 127 мс.
   Источник: ADR 023:38-49; `internal/platform/redis/gate.go:55-86`; evidence.md:128, 303.

9. **Что будет, если экземпляр упадёт посреди продажи?**
   Ответ: nginx повторяет запрос на другом экземпляре, только если соединение не установилось: POST, дошедший до api, мог уже создать заказ. Повтор — дело клиента с тем же ключом идемпотентности. Эксперимент ADR 027 показал, что ключ упавшего экземпляра минуту оставался «выполняется», и 13 из 18 покупателей с оборванными запросами ушли без билета. После того как у ключа появился владелец, без билета не ушёл никто.
   Источник: ADR 023:31; `deploy/nginx/api-lb.conf:58-62`; ADR 027:14-31; evidence.md:159-160.

10. **Что в этом эксперименте не доказано?**
    Ответ: Всё шло на одной машине с 4 vCPU, лимит в четверть ядра — модель узла, сеть локальная. Один прогон на ступень, разброс не оценён. Нагружался только заказ, очередь и лимит на IP были выключены. Инвариант проверялся один раз после всех ступеней конфигурации, коды ошибок за пределом ёмкости не разбирались.
    Источник: evidence.md:70, 385-387, 404-405.

## Где слабое место

- **Стенд, а не серверы.** k6, nginx, api и PostgreSQL на одной машине, экземпляр — четверть ядра (evidence.md:20, 385-386). Ответ: доказывается форма графика — рост 1 → 2 и перенос узкого места в базу; абсолютная ёмкость на отдельных серверах не мерилась (evidence.md:30).
- **Один прогон на ступень.** Разброс не оценён (evidence.md:387). Ответ: соседние ступени согласуются между собой (scaling/README.md:91); следующий шаг — повторы.
- **«В 2,5 раза» и «вдвое» — отношения ступеней.** Предел одного экземпляра между 200 и 250, двух — между 500 и 600 (evidence.md:120, 123). Для предохранителя надёжно измерен только p95 на 400/с (evidence.md:128). Ответ: называть именно ступени и p95.
- **ADR 032 называет 250 заказов в секунду на экземпляр** (ADR 032:11). В ADR 023 этого числа нет: там 200 / 500 / 500 и 400 с предохранителем при пол-ядра (evidence.md:216). Ответ: цитировать ADR 023.
- **Проверка инварианта одна на конфигурацию.** Кратковременная двойная бронь на промежуточной ступени, если корзину потом заменили, в итоговой проверке не видна (evidence.md:70). Ответ: инвариант держит транзакция с `FOR UPDATE`, она одинакова при любом числе экземпляров; ступенчатая проверка — следующий шаг.
- **Аудит не нашёл проблему с ключами идемпотентности.** Таблица ADR 023 разбирала состояние в памяти, а не незавершённые ключи в базе упавшего экземпляра; это нашёл эксперимент ADR 027 (ADR 027:14-16). Ответ: этап 4 для того и нужен, исправление — владелец ключа и отметка экземпляра раз в секунду (ADR 027:20-29).
- **Предохранитель — общий код, но не общий экземпляр.** `redis.Gate` один тип, а экземпляров три: сессии (бюджет 300 мс), холды и очередь (500 мс), `Cooldown` у всех 5 секунд (`internal/identity/service.go:58, 67-70`; `internal/booking/holds.go:32-38`; `internal/booking/queue.go:90`). Ответ: исправление в типе действует на все три.

## Проверь себя

1. Почему `proxy_next_upstream error`, а не `non_idempotent`? Что изменилось бы для покупателя, если бы nginx сам повторял POST, и почему ADR 027 тоже от этого отказался?
2. Один экземпляр отдаёт не больше ≈265 успешных заказов в секунду при любом потоке. Почему при 300 заказах в секунду p95 3,9 с, а не просто часть ошибок?
3. При отказе Redis старая сессия после выхода пользователя может жить на другом экземпляре. Сколько и почему это принято?
