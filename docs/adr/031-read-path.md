# ADR 031. Читающий контур: сначала профиль, потом реплики и кэш на краю

Дата: 2026-10-06. Статус: принято.

## Контекст

Этап 5 плана развития — читающий контур: публичные страницы и схемы через кэш и CDN, чтения с реплики. Цель — снизить нагрузку на ведущий узел PostgreSQL при старте продаж: он один, все заказы идут через него, и на штурме стадиона именно он упирался первым (ADR 023, ADR 026). Разбор — [`docs/experiments/2026-10-read-path`](../experiments/2026-10-read-path/README.md).

До этого этапа:
- публичная страница события уже жила в Redis (ADR 010);
- сводка занятости по секторам — секунду в памяти api (ADR 026);
- все остальные чтения шли в ведущий узел: занятость открытого сектора, опрос очереди, список событий.

**Сначала профиль.** Штурм концерта на Центральном стадионе (5 000 покупателей, очередь 150 в секунду) на кластере из ADR 028 с `pg_stat_statements`. Профиль показал не то, что предполагал план. Больше всего времени ведущего узла уходило на два запроса:

| Запрос | Время за прогон | Вызовов | Что делал |
|---|---:|---:|---|
| `HoldGeneral` | 689 с | 2 138 | Брал N свободных мест фан-зоны: сортировал все свободные места зоны по `id`, потому что индекс не покрывал порядок |
| `CountGeneralAvailable` | 277 с | 1 808 | Считал свободные места всех фан-зон события на каждое открытие сектора, хотя нужна только открытая |

Время — суммарное время выполнения, вместе с ожиданием блокировок. Остальные чтения — занятые места сектора, сводка, событие для очереди — около 40 секунд вместе. Реплики без исправления этих запросов дали бы немного: один из двух тяжёлых запросов — запись.

## Решение

### Два запроса

- **Счётчик фан-зон.** В режиме сектора считается только открытая зона, по частичному индексу свободных мест (`CountGeneralAvailableInSection`). Сводка для плана по-прежнему считает все зоны: она секунду живёт в памяти api. Сайт помнит счётчики зон из последней сводки, как уже помнил сводку по секторам.
- **Индекс под выбор мест в фан-зоне** (миграция 00019). Частичный индекс свободных мест зоны — `(event_id, section, id)` вместо `(event_id, section)`. Первые N мест по `id` читаются по порядку индекса, без сортировки всей зоны.

### Чтения с реплик

`DATABASE_REPLICA_URL` — реплики для чтений, которым не нужна свежесть до миллисекунды:
- занятость мест — сводка, сектор, счётчики;
- событие для опроса очереди;
- список предстоящих событий.

Источник чтений — `db.Reader`:
- **Отказ реплик.** Если реплики недоступны, чтение идёт с ведущего узла: отказ реплик возвращает нагрузку, но не ломает страницы.
- **Разные реплики.** Порядок хостов перемешивается при старте экземпляра, поэтому экземпляры api читают с разных реплик. pgx подключается к первому подходящему хосту, и без перемешивания все читали бы с одной.
- **`/readyz`.** Реплика — необязательная зависимость (ADR 030).

Что остаётся на ведущем:
- **Проверки и запись заказа** — решение о месте принимает только ведущий, в транзакции.
- **Свой заказ** покупателя — реплика отстаёт на миллисекунды, и только что созданный заказ мог бы «пропасть».
- **Публичная страница события.** Её кэш в Redis сбрасывается при смене обложек; построенная с отстающей реплики, страница вернула бы в кэш старые обложки на 10 минут. Промах кэша редок и схлопывается singleflight (ADR 010).

Реплика может показать место свободным на миллисекунды дольше, чем на самом деле. Это не опасно: заказ проверяет место на ведущем, и покупатель получит «место занято», как получил бы, если бы место заняли через секунду после загрузки сектора.

### Кэш на краю

nginx-балансировщик api (`deploy/nginx/api-lb.conf`) держит публичные GET — страницу события, список событий, занятость — столько, сколько разрешает `Cache-Control` ответа api:
- страница — 60 секунд;
- занятость — 2 секунды.

Так он стоит на месте CDN:
- **Одинаковый ответ для всех.** За секунду в api приходит один запрос на адрес, сколько бы покупателей ни открыли сектор.
- **Одновременные промахи** идут в api одним запросом (`proxy_cache_lock`).
- **Пока свежий ответ обновляется**, отдаётся устаревший (`proxy_cache_use_stale updating`).
- **Сайт тоже идёт через балансировщик**, а не напрямую в api, поэтому кэш один для всех клиентов.

Лимит соединений балансировщика поднят до 16 384 на процесс (`deploy/nginx/nginx.conf`). Стандартных 1 024 на старте продаж не хватало: каждое проксируемое соединение занимает два, и nginx рвал соединения раньше, чем уставал api. Тот же урок, что в ADR 029.

## Результаты эксперимента

_Заполняется по итогам серии._

## Альтернативы

- **Только реплики, без профиля.** Так предполагал план этапа. Профиль показал, что главная нагрузка — не чтения, а сортировка мест фан-зоны при заказе.
- **Материализованные счётчики свободных мест** (таблица счётчиков по зонам, обновляемая в транзакции заказа). Подсчёт стал бы бесплатным, но каждый заказ спорил бы за строку счётчика своей зоны — новая горячая точка там, где решается главный инвариант (то же, что в ADR 026).
- **Реплики для публичной страницы события.** Отказались: кэш страницы сбрасывается при смене обложек, и отстающая реплика вернула бы старую страницу в кэш.
- **Настоящий CDN.** На продакшене — да. Ту же роль на стенде играет nginx с `proxy_cache`: решение то же — кэшировать по `Cache-Control`, который ставит api. Подключение CDN не требует изменений в коде.
- **Чтения с реплик через прокси** (pgpool-II, HAProxy). Ещё один компонент и точка отказа. Список хостов в клиенте с перемешиванием даёт то же самое.

## Следствия

- **Код:**
  - счётчик одной фан-зоны в режиме сектора;
  - `db.Reader` и `db.NewReplicaPool`;
  - `DATABASE_REPLICA_URL`;
  - `booking.WithReader`, `catalog.WithReader`;
  - сайт помнит счётчики фан-зон из сводки.
- **Схема:** миграция 00019 — индекс выбора мест фан-зоны.
- **Compose:**
  - кэш на краю и лимит соединений в балансировщике api;
  - сайт ходит в api через балансировщик.
- **Нагрузочный стенд:** серия `loadtest/readpath.sh`, отчёт `loadseed readpath-report`; в кластере PostgreSQL из ADR 028 включён `pg_stat_statements`.
- **Тесты:**
  - счётчик одной зоны в режиме сектора;
  - чтение с ведущего при недоступной реплике;
  - перемешивание хостов сохраняет все хосты.
