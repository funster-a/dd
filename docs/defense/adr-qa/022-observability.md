# ADR 022. Наблюдаемость: метрики, дашборд, алерты — разбор к защите

Неделя 6 (16–22.11.2026). ADR: [`docs/adr/022-observability.md`](../../adr/022-observability.md).

## Суть в трёх фразах

До этого этапа у системы были только метрики бронирования и сессий, дашбордов не было, воркер и хранилища не измерялись, поэтому следующие этапы — масштабирование, стадион, отказы — нечем было доказывать. Решение — собирать в Prometheus метрики HTTP по маршрутам, метрики воркера и outbox, экспортёры PostgreSQL, Redis и RabbitMQ, держать дашборд Grafana и правила алертов файлами в репозитории. Отсюда следует, что каждый прогон эксперимента виден на одном экране, а алерты описывают симптомы, которые видит покупатель или организатор; доставка алертов отложена до продакшена.

Более поздние ADR этот не пересматривают. ADR 023 добавил сбор метрик с каждой реплики через `dns_sd_configs` (ADR 023:33; `deploy/prometheus/prometheus.yml:15-28`). ADR 032 масштабирует поды по загрузке процессора из metrics-server, а не по метрикам Prometheus (ADR 032:62-65).

## Почему так, а не иначе

- **OpenTelemetry с трассировкой.** Трасса показывает путь одного запроса через сервисы. В монолите в одном процессе метрики по маршрутам и модулям дают больше, а коллектор и хранилище трасс — ещё два сервиса. Возврат к этому — когда модули начнут выноситься в сервисы (ADR 022:66).
- **Промежуточный агент (Grafana Agent, Alloy).** Нужен, когда машин много. В Compose Prometheus собирает цели напрямую (ADR 022:67).
- **Готовые дашборды экспортёров из каталога Grafana.** Подробнее, но это десятки панелей, которые никто не смотрит. Свой дашборд показывает на одном экране то, что важно в пик продаж (ADR 022:68).

## Чем подтверждено

- **Метка маршрута.** Тест: запросы `/v1/orders/1` и `/v1/orders/2` дают один ряд `route="/v1/orders/{orderID}"`, неизвестный путь — `unmatched`, рядов длительности ровно 3. `TestHTTPMetrics`, `internal/platform/observability/httpmetrics_test.go:14-38`.
- **CI на каждый push.** Шаг Compose ждёт, пока Prometheus увидит 2 экземпляра api, 2 воркера, PostgreSQL, Redis и RabbitMQ; проверяет, что правило `DDOutboxStuck` загружено, а дашборд `dd-overview` есть в Grafana. `.github/workflows/ci.yml:203-220`.
- **Проверено вживую.** Серия «без очереди / очередь 200 в секунду» на 2 000 покупателях видна на дашборде целиком, снимок — `docs/observability/grafana-overview.png` (ADR 022:75). Чисел этой серии в реестре нет.
- **Эксперименты читают те же метрики, что дашборд.** Отчёт `loadseed report` берёт гистограмму `dd_booking_attempt_seconds` (`cmd/loadseed/report.go:193`), эксперимент со стратегиями — счётчик предохранителя `dd_booking_redis_gate_opened_total` (evidence.md:61). Загрузку процессора в масштабировании снимал `docker stats`, а не Prometheus (scaling/README.md:17).
- **Что не измерялось.** Алерты ни разу не проверялись срабатыванием в эксперименте; пороги в `alerts.yml` помечены как пороги для MVP (`deploy/prometheus/alerts.yml:1-3`).

## Вопросы комиссии

1. **Что собирает система наблюдаемости и почему это первый этап?**
   Ответ: Метрики HTTP по маршрутам, бронирования и сессий в api, обработку сообщений и отставание outbox в воркере, экспортёры PostgreSQL и Redis, встроенный плагин RabbitMQ. Prometheus собирает их каждые 5 секунд, Grafana показывает дашборд, правила алертов лежат рядом. Первым этапом — потому что без этого масштабирование, стадион и отказы нечем доказывать.
   Источник: ADR 022:7, 19-29; `deploy/prometheus/prometheus.yml:3-5`; ADR 021:41.

2. **Почему метка маршрута — шаблон chi, а не путь запроса?**
   Ответ: Путь содержит id заказа или события, и каждый id стал бы отдельным рядом в Prometheus. Число рядов росло бы без предела, и база метрик разрасталась бы. Middleware берёт шаблон маршрута из контекста chi после обработки запроса; это закреплено тестом.
   Источник: ADR 022:21; `internal/platform/observability/httpmetrics.go:12-15, 52-57`; `httpmetrics_test.go:14-38`.

3. **Как считается отставание outbox и почему не отдельным счётчиком?**
   Ответ: При каждом сборе метрик воркер одним запросом считает неопубликованные события и возраст самого старого, с таймаутом 2 секунды. Запрос фильтрует по условию частичного индекса неопубликованных событий. Счётчик в памяти мог бы разойтись с базой, а этот запрос читает саму базу. Если запрос не удался, `dd_outbox_backlog_up` равен 0.
   Источник: ADR 022:33; `internal/platform/outbox/metrics.go:46-61`; `migrations/00008_payments_outbox.sql:14`.

4. **Почему не OpenTelemetry с трассировкой?**
   Ответ: Трассировка полезна, когда запрос проходит через несколько сервисов. Здесь монолит в одном процессе: маршрут, модуль и результат уже видны в метриках. Коллектор и хранилище трасс добавили бы два сервиса. Возврат к трассировке — вместе с выносом модулей в сервисы.
   Источник: ADR 022:66; ADR 021:21-25.

5. **Почему дашборд лежит в JSON и что за история с uid источника данных?**
   Ответ: Дашборд подключается провижинингом, правки в интерфейсе не сохраняются: изменение идёт через JSON и ревью, как код. Панели ссылаются на источник данных с постоянным uid `prometheus`. Grafana со старым томом не стартовала: источник с тем же именем, но другим uid уже существовал. Поэтому провижининг удаляет источник и создаёт заново.
   Источник: ADR 022:39-46; `deploy/grafana/dashboards.yml:1-11`; `docker-compose.yml:304-318`.

6. **По какому принципу выбраны алерты? Приведите пример.**
   Ответ: Каждое правило — симптом, который видит покупатель или организатор, или явный предвестник. Пример: `DDOutboxStuck` — событие ждёт публикации больше 60 секунд: оплаты проходят, а билеты не выпускаются. Ещё `DDHighErrorRate` — больше 5 % ответов 5xx за 5 минут, `DDSlowBooking` — оформление заказа p95 дольше секунды. Всего семь правил.
   Источник: ADR 022:50-60; `deploy/prometheus/alerts.yml:15-39`.

7. **Что увидит дежурный, если встанет воркер?**
   Ответ: Через минуту недоступности цели сработает `DDTargetDown`. Если воркер жив, но не публикует, растёт `dd_outbox_oldest_pending_seconds`, и при значении больше 60 секунд, державшемся 2 минуты, срабатывает `DDOutboxStuck`. Падения обработчиков видны как `result="error"` в `dd_mq_messages_total` и алерт `DDDeadLetters`.
   Источник: `deploy/prometheus/alerts.yml:7-13, 33-45`; `internal/platform/mq/metrics.go:10-27`.

8. **Чем подтверждено, что наблюдаемость работает?**
   Ответ: CI на каждый push поднимает Compose и проверяет, что Prometheus видит оба экземпляра api, оба воркера и три хранилища, правило `DDOutboxStuck` загружено, а дашборд есть в Grafana. Метка маршрута закреплена модульным тестом. Серия на 2 000 покупателях проверена вживую, снимок дашборда лежит в репозитории.
   Источник: `.github/workflows/ci.yml:203-220`; `httpmetrics_test.go:14-38`; ADR 022:74-75.

9. **Что здесь не сделано или не доказано?**
   Ответ: Доставки алертов нет: Alertmanager отложен до продакшена, алерты видны только в Prometheus и Grafana. Пороги не откалиброваны на реальной нагрузке, ни один алерт не проверялся срабатыванием в эксперименте. ADR пишет, что правила проверяются `promtool`, но в CI этой проверки нет: CI только убеждается, что правило загружено.
   Источник: ADR 022:50, 62; `deploy/prometheus/alerts.yml:1-3`; `.github/workflows/ci.yml:219`.

## Где слабое место

- **Нет доставки уведомлений.** Алерт без Alertmanager никого не будит (ADR 022:62). Ответ: на стенде алерты видны в Grafana, этого хватает для экспериментов. Доставка нужна вместе с продакшен-окружением.
- **Пороги не откалиброваны.** 5 % ошибок, секунда на заказ, минута в outbox — значения для MVP (`deploy/prometheus/alerts.yml:1-3`). Ответ: пороги уточняются по метрикам реальной нагрузки; данные для этого дашборд уже собирает.
- **`promtool` не автоматизирован.** В репозитории нет вызова `promtool`, CI проверяет только загрузку правила `DDOutboxStuck` (`.github/workflows/ci.yml:219`). Ответ: следующий шаг — `promtool check rules` и модульные тесты правил (`promtool test rules`) в CI.
- **`/metrics` api на общем порту.** api отдаёт `/metrics` на том же порту 8080, что и API (`cmd/api/main.go:142`), а балансировщик проксирует все пути (`deploy/nginx/api-lb.conf:49`). В Compose порт открыт только на 127.0.0.1 (`docker-compose.yml`, `api-lb`). Ответ: на продакшене путь закрывается на краю или выносится на отдельный порт, как у воркера (`METRICS_ADDR`, ADR 022:31).
- **Нет трасс.** Путь одного медленного запроса по метрикам не восстановить. Ответ: для монолита метрики по маршрутам дают нужную картину; трассировка — при выносе модулей (ADR 022:66).

## Проверь себя

1. Почему `DDOutboxStuck` срабатывает не через минуту после того, как событие застряло, а позже? Посчитайте по `alerts.yml` и `prometheus.yml`.
2. Чем опасна метка с id заказа в `dd_http_requests_total`, и что произошло бы с запросом `/nowhere`, если бы middleware брал путь вместо шаблона?
3. При двух экземплярах api `DDSlowBooking` считает p95 по сумме гистограмм. Почему суммировать бакеты корректно, а усреднять p95 экземпляров — нет?
