# ADR 018. Проверка сессий при отказе Redis — разбор к защите

Неделя 5 (09–15.11.2026). ADR: [`docs/adr/018-session-check-without-redis.md`](../../adr/018-session-check-without-redis.md).

## Суть в трёх фразах

Сессии покупателей живут в Redis, поэтому при его отказе вошедший покупатель не мог купить билет, хотя захват мест после ADR 017 от Redis уже не зависел: эксперимент дал 6 118 ошибок `load session`. Решение — кэш последних успешных проверок в памяти процесса, который читается только при отказе Redis: знакомая сессия, проверенная не больше 10 минут назад, проходит, незнакомая получает быстрый ответ 503. Цена — отозванная незадолго до отказа сессия может какое-то время действовать на другом экземпляре api; зато в повторе эксперимента при упавшем Redis продано 984 места без единой ошибки (3 прогона, покупатели заранее открывали профиль).

Ядро решения действует до сих пор. Позже его изменили:
- ADR 023: предохранитель стал полуоткрытым — пока он открыт, раз в 100 мс одна проверка проходит в Redis пробой, удачная проба закрывает его сразу (ADR 023:36-49; `internal/platform/redis/gate.go:21-25`). Без этого перегруженный экземпляр отвечал 503 незнакомым сессиям все 5 секунд при здоровом Redis (ADR 023:38-42);
- ADR 029: `Retry-After` в ответе 503 сокращён с 5 до 2 секунд: с Sentinel простой Redis — 2–3 секунды (ADR 029:49-51; `internal/identity/http.go:47-52`). Реплики Redis, которые ADR 018 называл «правильным ходом для эксплуатации», сделаны там же, в стенде `deploy/ha` с Sentinel (ADR 029:40-45); кэш остаётся нужен на время переключения;
- ADR 030: `/readyz` больше не выводит экземпляр из ротации при отказе Redis, который api переживает благодаря этому решению (ADR 030:18, 65).

## Почему так, а не иначе

- **Кэш на 30–60 с всегда, до похода в Redis** (так предлагал ADR 017:72-75). Снижает нагрузку на Redis, но отзыв сессии задерживается всегда, а не только при отказе. Redis не узкое место (ADR 017), выигрыш не нужен (ADR 018:51).
- **Самоподписанные токены (JWT) без хранилища.** Проверка без Redis вообще, но для отзыва нужен список отозванных — в том же Redis. Это переделка входа и формата токенов ради редкого сценария (ADR 018:52).
- **Сессии в PostgreSQL.** Одним источником отказа меньше, но лишний запрос в базу на каждый запрос — к той самой базе, которая под нагрузкой при старте продаж (ADR 018:53; позже повторено в ADR 029:83).
- **Реплика Redis (Sentinel).** Правильный ход для эксплуатации, но это инфраструктура, а не код, и она не защищает на время переключения (ADR 018:54). Сделана позже в ADR 029, кэш остался.

## Чем подтверждено

Тесты (тесты с Redis идут только с `REDIS_TEST_ADDR`, иначе пропускаются — `internal/identity/identity_test.go:61-64`; `TestStaleCacheLimits` и тесты Gate Redis не требуют):
- **Отзыв при работающем Redis действует сразу:** выход на другом экземпляре, следующая проверка получает `ErrNoSession`, кэш пуст. `TestRevokedSessionFailsImmediatelyWhenRedisIsUp`, `internal/identity/cache_test.go:33-52`.
- **При отказе знакомая сессия проходит, незнакомая получает `ErrUnavailable`** быстрее 20 мс, ожидание таймаута — один раз. `TestSessionsSurviveRedisOutage`, `cache_test.go:54-85`.
- **Лимиты кэша:** проверка старше срока и истёкшая сессия не принимаются, размер не превышает лимит. `TestStaleCacheLimits`, `cache_test.go:87-110`.
- **Выход забывает сессию** даже при последующем отказе Redis. `TestLogoutForgetsCachedSession`, `cache_test.go:112-128`.
- **HTTP:** без Redis и без кэша — 503 с `Retry-After`, а не 500. `TestMiddlewareReturns503WhenStoreIsDown`, `cache_test.go:130-143`.
- **Предохранитель:** из 100 одновременных запросов в открытый Gate проходит ровно одна проба; отмена запроса Gate не открывает. `internal/platform/redis/gate_test.go:44-79`.

Эксперимент (повтор прогона с отказом Redis из ADR 017, 2 000 покупателей, зал, 3 прогона):
- **984 места, 0 ошибок, p50 1 609 мс, p99 4 894 мс**; при работающем Redis — 984 места, p50 1 472 мс (evidence.md:43; booking-strategies/README.md:105-107).
- **До кэша:** 659 успехов, 1 341 ошибка, p99 25 052 мс (evidence.md:300).
- **Около 2 200 запросов за прогон прошли по кэшу** — метрика `dd_identity_session_stale_hits_total` (evidence.md:62).

## Вопросы комиссии

1. **Какую проблему решает этот ADR?**
   Ответ: После предохранителя ADR 017 захват мест от Redis не зависел, а вход зависел: сессии хранятся в Redis. В эксперименте с отказом Redis все оставшиеся ошибки были на проверке сессии — 6 118 ошибок `load session`. Новые входы без Redis невозможны в любом случае, коды тоже в нём. Но покупатель, который уже вошёл и открыл страницу события, должен суметь купить.
   Источник: ADR 018:9-13; booking-strategies/README.md:122; evidence.md:300.

2. **Как работает проверка сессии сейчас?**
   Ответ: Пока Redis отвечает, каждая проверка идёт в Redis, успешная запоминается в памяти процесса вместе с моментом проверки. Если Redis не ответил за 300 мс, предохранитель открывается и запрос пускается по запомненной проверке, если ей не больше 10 минут и сама сессия не истекла. Незнакомая или слишком старая сессия получает `503 session_store_unavailable`. Ответ Redis «сессии нет» удаляет её из кэша.
   Источник: ADR 018:21-29; `internal/identity/service.go:65-77, 171-204`; `internal/identity/cache.go:43-57`.

3. **ADR 017 предлагал кэш на 30–60 секунд. Почему выбрали другое?**
   Ответ: Кэш перед Redis задерживал бы отзыв сессии всегда, при любой работе Redis. Выбранный кэш читается только при отказе, поэтому выход на любом экземпляре действует сразу, пока Redis жив. Выигрыш в нагрузке на Redis не нужен: он не узкое место.
   Источник: ADR 018:19-21, 45, 51; ADR 017:72-75; тест `cache_test.go:33-52`.

4. **Значит, отозванная сессия может пройти? Когда именно?**
   Ответ: Только при трёх условиях сразу: Redis сейчас недоступен, выход был сделан на другом экземпляре api, а этот экземпляр проверял сессию не больше 10 минут назад. Во время самого отказа выход нигде не записывается: ключ в недоступном Redis не удалить. Поэтому окно риска — сессии, отозванные незадолго до отказа. Выход на своём экземпляре удаляет сессию из кэша сразу.
   Источник: ADR 018:38-45; `service.go:206-210`; тест `cache_test.go:112-128`.

5. **Почему 10 минут?**
   Ответ: Это значение по умолчанию, оно перекрывает время от открытия страницы события до оплаты. Срок — бизнес-параметр: короче — безопаснее, но больше покупателей увидят «вход временно недоступен» при отказе. Пользователь подтвердил, что задачу решаем с этой ценой.
   Источник: ADR 018:15, 47; `service.go:71-73`.

6. **Почему не JWT и не сессии в PostgreSQL?**
   Ответ: JWT проверяется без хранилища, но отзыв требует списка отозванных токенов, а он лежал бы в том же Redis. Это переделка входа ради редкого сценария. Сессии в PostgreSQL добавили бы запрос в базу на каждый запрос, к той самой базе, которая нагружена на старте продаж.
   Источник: ADR 018:52-53; ADR 029:83.

7. **Что показал повтор эксперимента? Назовите числа.**
   Ответ: При упавшем Redis — 984 проданных места в среднем, ни одной ошибки, p50 1 609 мс. При работающем Redis в том же сценарии — 984 места и p50 1 472 мс. Около 2 200 запросов за прогон прошли по кэшу. До кэша было 659 успехов и 1 341 ошибка.
   Источник: ADR 018:58-62; evidence.md:43, 62, 300.

8. **Что будет, если api перезапустится во время отказа Redis или если на свежий api придут сразу 5 000 покупателей?**
   Ответ: Кэш живёт в процессе: после перезапуска он пуст, и все запросы с токеном получают 503 до восстановления Redis. Похожее случилось в эксперименте с очередью: на только что запущенном api 5 000 проверок не уложились в бюджет 300 мс, предохранитель открылся при пустом кэше, и 97 % покупателей (4 866 из 5 000) получили 503. Redis при этом был жив. Защищает очередь ожидания: сессии попадают в кэш до покупки. Полуоткрытый предохранитель ADR 023 закрывается первой удачной пробой, а не через 5 секунд, но холодный старт с ним не перемеряли.
   Источник: ADR 018:71; evidence.md:119, 301; ADR 023:36-49.

9. **Что в этом решении не доказано?**
   Ответ: База сравнения в эксперименте разная: прогон «при работающем Redis» — серия без прогрева, а прогон с отказом шёл с `WARMUP=1`, когда покупатель открывает профиль до старта. Без прогрева незнакомые сессии получают 503. «Столько же мест» верно для средних: по прогонам 980–990 против 983–985. Мутационные проверки сделаны вручную.
   Источник: evidence.md:43, 397; ADR 018:69-70; `loadtest/redis-failure.sh:14`.

## Где слабое место

- **Окно для отозванной сессии.** До 10 минут на другом экземпляре api, если Redis упал вскоре после выхода (ADR 018:40-45). Ответ: это осознанная цена, согласованная как бизнес-параметр; при работающем Redis отзыв мгновенный, и это закреплено тестом (`cache_test.go:33-52`). Следующий шаг при ужесточении требований — сократить `sessionStaleMaxAge` (`service.go:73`).
- **Кэш пуст после перезапуска.** Все запросы с токеном получают 503 до восстановления Redis (ADR 018:71). Ответ: перезапуск api именно во время отказа Redis — совпадение двух отказов. В стенде с Sentinel из ADR 029 простой Redis — 2–3 секунды, запись снова доступна через 3 секунды (ADR 029:51; evidence.md:173).
- **Холодный старт без очереди.** Один прогон: 97 % покупателей получили 503 при живом Redis (evidence.md:119). Ответ: это перегрузка общего пути, а не отказ Redis; очередь ожидания убирает её по построению, полуоткрытый предохранитель ADR 023 закрывается первой удачной пробой, не дожидаясь 5 секунд. Холодный старт снят одним прогоном, до ADR 023, с полуоткрытым предохранителем его не перемеряли (evidence.md:23, 119).
- **Разные базы сравнения в эксперименте.** Прогрев был только в прогоне с отказом (evidence.md:43). Ответ: прогрев моделирует покупателя, который заранее открыл страницу события; без него проверено только, что незнакомая сессия быстро получает 503 (тест `cache_test.go:54-85`).
- **Память и вытеснение.** До 200 000 сессий на процесс, около 60 МБ, вытесняется произвольная запись (ADR 018:32; `cache.go:30-41`). Ответ: в нагрузочных экспериментах покупателей с сессиями были тысячи, например 5 000 в штурме стадиона (evidence.md:138), до лимита 200 000 далеко; вытеснение под нагрузкой не проверялось. Вытесненная сессия при отказе получит 503, а не чужой доступ (`service.go:199-203`).
- **Новый вход без Redis невозможен.** Коды тоже в Redis (ADR 018:13). Ответ: решение защищает только уже вошедших; новый вход ждёт Redis.

## Проверь себя

1. Покупатель вышел на экземпляре A, через минуту Redis упал, а следующий запрос пришёл на экземпляр B. Пройдёт ли он и почему? А если бы запрос пришёл на A?
2. Почему ответ Redis «сессии нет» не открывает предохранитель, а таймаут открывает? Найдите это место в `service.go`.
3. Чем отличается холодный старт из эксперимента с очередью от отказа Redis, и почему кэш сессий во втором случае помогает, а в первом нет?
