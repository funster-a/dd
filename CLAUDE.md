# CLAUDE.md

Правила работы над проектом. Читать перед любой задачей.

## Что строим

SaaS для организаторов мероприятий: организатор заводит событие и схему зала, продаёт билеты со своего сайта. Дипломный проект, один разработчик, срок — до мая 2027.

Ядро проекта — корректная продажа мест при конкурентном доступе. Всё остальное обслуживает это ядро.

Полная спецификация — `docs/spec.md`. Если задача противоречит спецификации, останавливайся и спрашивай.

## Стек

- Go, последняя стабильная версия
- HTTP: chi
- БД: PostgreSQL, доступ через pgx, запросы через sqlc, миграции через goose
- Кэш и холды: Redis
- Очередь: RabbitMQ
- Логи: log/slog, структурные, в JSON
- Метрики: Prometheus
- Фронтенд: Vue с TypeScript, Vite (см. ADR 001)
- Локальный запуск: Docker Compose
- Нагрузочные тесты: k6
- Линтер: golangci-lint

Стандартная библиотека — первый выбор. Новую зависимость добавляет Claude, если без неё решение заметно хуже, и записывает причину в ADR.

## Структура

```
cmd/api/          — HTTP-сервер
cmd/worker/       — потребитель очереди
internal/catalog/ — события, залы, схемы мест
internal/booking/ — холды, брони, статусы заказа
internal/payment/ — платёжный шлюз, вебхуки, возвраты
internal/ticket/  — QR, валидация, отчёты
internal/identity/— вход по одноразовому коду, сессии (ADR 006)
internal/platform/— db, redis, mq, config, http, observability
migrations/       — goose-миграции
web/              — Vue-приложение
loadtest/         — сценарии k6
docs/             — спецификация, ADR, результаты экспериментов
```

Архитектура — модульный монолит. Пакеты в `internal/` не импортируют друг друга напрямую: только через интерфейсы, объявленные на стороне потребителя. Общий код живёт в `internal/platform/`.

## Доменные правила, которые нельзя нарушать

1. Место не может быть продано дважды ни при какой конкурентности. Это главный инвариант, на него нужен тест.
2. Холд места живёт в Redis с TTL 10 минут. Истина о брони и оплате — только в PostgreSQL.
3. Все изменяющие эндпоинты и все обработчики вебхуков идемпотентны по ключу запроса. Повторный вызов возвращает прежний результат, а не создаёт новую сущность.
4. Заказ живёт по статусной модели, переходы описаны в спецификации. Никаких булевых флагов вместо статусов.
5. Деньги и суммы — целые числа в минорных единицах (тиын). Никаких float.
6. Время хранится и передаётся в UTC. Локальное время только на фронтенде.
7. Внешний платёжный шлюз — только песочница. Реальные ключи и карточные данные в репозитории не появляются никогда.

## Как работаем

- **Разделение ролей** (с 2026-09-28): все технические решения — архитектура, схема БД, API, зависимости, инфраструктура — принимает Claude и фиксирует в ADR. От меня — только бизнес-решения: что продаём, кому, по каким правилам, сколько стоит. Если техническое решение упирается в бизнес-вопрос, Claude задаёт вопрос, а пока ответа нет, берёт разумное значение по умолчанию и помечает его.
- Работа идёт этапами по плану из спецификации. Каждый этап — отдельный PR с зелёным CI и коротким отчётом.
- Изменение схемы БД — только новой миграцией, уже применённые не правятся.
- Каждое архитектурное решение записывай коротким ADR в `docs/adr/NNN-название.md`: контекст, решение, альтернативы, следствия. Это нужно для защиты.
- Коммиты мелкие, сообщения в стиле Conventional Commits.
- Не рефактори код, о котором не просили.

## Definition of Done

Задача считается сделанной, когда:

- код проходит `golangci-lint run` без замечаний;
- есть тесты на бизнес-логику, а на конкурентные сценарии — тест с параллельными горутинами;
- миграции применяются и откатываются;
- `docker compose up` поднимает проект с нуля;
- README обновлён, если менялся способ запуска.

## Что за рамками MVP

Мультиязычность, Apple и Google Wallet, перепродажа билетов между покупателями, сплит-платежи, аппаратные сканеры, маркетинговая аналитика и рассылки. Если задача тянет туда — скажи об этом, не реализуй.
