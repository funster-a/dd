# ADR 016. Кабинет организатора и сканер контролёра

Дата: 2026-09-30. Статус: принято.

## Контекст

API кабинета (ADR 007–014) и API сканера (ADR 013) готовы, сайт покупателя — ADR 015. Организатору нужен веб-кабинет:
- площадки и схемы залов;
- события: основное, цены, обложка, публикация и отмена;
- продажи и выгрузка;
- ссылки для контролёров.

Контролёру нужен экран, который сканирует QR камерой телефона и работает без сети (spec.md, ADR 013).

## Решение

### Где живёт

Кабинет и сканер — в том же Vue-приложении, что и сайт покупателя (ADR 015). Сборка одна, дизайн-система одна, раздача одна (nginx).

| Маршрут | Экран |
|---|---|
| `/org/login` | вход по коду на email |
| `/org` | события: в продаже, черновики, прошедшие; сводка продаж |
| `/org/events/new` | новое событие (черновик) |
| `/org/events/{id}` | черновик: Основное → Цены → Обложка → Публикация; опубликованное: Продажи, Контроль входа, О событии |
| `/org/venues`, `/org/venues/{id}` | площадки и их схемы залов |
| `/org/venues/{id}/seat-maps/new` | конструктор схемы зала |
| `/scan#{токен}` | сканер контролёра |

Каждая часть загружается лениво. Покупатель не скачивает код кабинета, контролёр — код сайта.

### Сессии

Сессия организатора хранится отдельно от сессии покупателя (`dd.org.session` и `dd.session`). Один человек может быть и организатором, и покупателем в одном браузере, и выход из одного не выбрасывает из другого.

Истёкшая сессия кабинета (401 `invalid_session`) возвращает на экран входа с возвратом на ту же страницу.

### Два небольших изменения API

- `GET /v1/organizer/profile` отдаёт название и slug организатора. Кабинету нужна публичная ссылка на событие `/e/{slug}/{событие}`, а в сессии есть только id.
- В ответах кабинета о событии появились `cover_image_url` и `cover_video_url`: превью обложки по публичному адресу хранилища. Ключи остаются, они нужны для `PUT /media`.

### Время и деньги в формах

- **Время.** Организатор вводит дату и время по местному времени площадки, в API уходит UTC (правило 6). Перевод «время на стене в поясе → UTC» сделан через `Intl` без библиотек, в два шага, чтобы корректно пройти переход на летнее время. Покрыт тестами.
- **Деньги.** Организатор вводит тенге («5 000», «4 999,50»). В тиыны строка разбирается без float: `19.99 × 100` во float дало бы 1998,999… (правило 5). Покрыт тестами.

### Конструктор схемы зала

Организатор описывает сектор параметрами, а не рисует каждое место:
- места с рядами: число рядов, мест в первом ряду, на сколько мест каждый следующий ряд шире («веер»), ряды цифрами или буквами (без Ё, Й, Ъ, Ы, Ь);
- входная зона: вместимость.

Три шаблона — театр, клуб, концертный зал. Превью строится той же функцией, что схема для покупателя, поэтому организатор видит ровно то, что увидят покупатели. Результат — `Layout` из ADR 005, его проверяет сервер.

Редактор координат мест (drag-and-drop) отложен. Сервер координаты уже принимает (ADR 005), а для залов MVP параметрического описания хватает.

### Цены

- Категории с названием, ценой и секторами. Сектор принадлежит ровно одной категории.
- Для новой схемы категории по умолчанию создаются по одной на сектор, организатору остаётся вписать цены.
- Рядом превью схемы, окрашенное по категориям так же, как у покупателя.
- Цена 0 — бесплатные билеты, это видно подписью.

### Публикация и отмена

- Перед публикацией — чек-лист: дата в будущем, цены на все сектора, обложка. Непройденный пункт ведёт на нужную вкладку.
- Подтверждение напоминает, что схема, цены и даты после публикации фиксируются (бизнес-правило).
- Отмена события требует явного подтверждения («Понимаю…»): она необратима, все заказы возвращаются (ADR 014).

### Обложка

Файл уходит из браузера прямо в хранилище по подписанной ссылке (ADR 009). Прогресс загрузки — через `XMLHttpRequest`, у `fetch` нет события прогресса при отправке.

В CSP сайта `connect-src` дополнен адресом хранилища (`MEDIA_ORIGIN`). SeaweedFS отвечает на CORS-запросы по умолчанию. Проверено вживую из собранного сайта под nginx и CSP.

### Продажи и контроль входа

- **Продажи** — отчёт из ADR 014: заполняемость (продано, в корзинах сейчас, свободно), выручка, возвраты, итог, проходы, категории. Обновляется раз в 30 секунд, пока вкладка видима. CSV качается через `fetch` с токеном в заголовке, потому что обычная ссылка токен не передаёт.
- **Контроль входа** — ссылки сканера по входам. Новая ссылка показывается один раз: с QR-кодом, чтобы открыть её телефоном контролёра, и кнопкой «Скопировать». Ссылку можно отозвать.

### Сканер

- Токен приходит во фрагменте ссылки (`#…`): браузер не отправляет фрагмент на сервер. Сканер сохраняет токен и сразу убирает его из адреса.
- **Камера.** Используется встроенный `BarcodeDetector` (Chrome, Android), а где его нет — `jsQR` по кадрам с canvas (Safari, Firefox). `jsQR` загружается только в этом случае.
- **Повторы.** Билет, который остаётся в кадре, проверяется один раз. Повторно — если его убрали из кадра на 5 секунд или контролёр закрыл итог. Это найдено на сквозном тесте: без правила сканер каждые 3 секунды показывал «уже прошёл».
- **Итог** — на весь экран, цветом: зелёный «Проходите» с местом, жёлтый «Уже прошёл» с временем первого прохода, красный «Билет возвращён», «Не билет» или «Другое событие». Звук и вибрация разные для каждого случая. Экран не гаснет (Wake Lock).
- **Онлайн** решает сервер (ADR 013).
- **Без сети** сканер достаёт id билета из токена и ищет его в списке билетов (`/manifest`), учитывая проходы, засчитанные на этом устройстве. Сканирование встаёт в очередь.
- **Хранение.** Очередь, список и проходы лежат в `localStorage` и переживают перезагрузку.
- **Синхронизация** — пачками до 500, при появлении сети и раз в 15 секунд. Повторная отправка безопасна благодаря `client_scan_id`. Если сервер счёл офлайн-проход повторным (билет прошёл раньше на другом входе), сканер это показывает.
- **PWA.** Манифест подключается только на экране сканера. Service worker кэширует оболочку приложения: HTML страницы `/scan` и файлы сборки, включая лениво загруженный декодер. Проверено: после перезагрузки без сети сканер открывается и работает. `/v1` service worker не кэширует никогда.

### Зависимости

| Пакет | Размер (gzip) | Зачем |
|---|---|---|
| `qrcode-generator` | ~7 КБ | QR ссылки сканера в кабинете. SVG, без зависимостей |
| `jsqr` | ~48 КБ, лениво | распознавание QR, где нет `BarcodeDetector` (Safari, Firefox) |

Встроенного распознавания QR в Safari нет. Своя реализация декодера — неоправданный объём работы.

## Альтернативы

- **Отдельное приложение для кабинета.** Более чистое разделение, но две сборки, две дизайн-системы и два деплоя на одного разработчика. Ленивая загрузка и так не отдаёт покупателю код кабинета.
- **Нативное приложение сканера.** Надёжнее камера и работа в фоне, но нужна установка из магазина приложений. У контролёров чужие телефоны и одна смена: ссылка лучше.
- **Секрет подписи на сканере для офлайн-проверки** — отвергнут в ADR 013.
- **Рисование схемы мышью.** Нагляднее для сложных залов, но это большой отдельный компонент. Параметрический конструктор закрывает залы MVP, а координаты API уже принимает.
- **UI-библиотека для форм и таблиц** — отклонена по той же причине, что в ADR 015.

## Следствия

- Кабинет покрывает весь путь организатора без curl: площадка → схема → событие → цены → обложка → публикация → продажи → контроль входа → отмена.
- Юнит-тесты фронтенда: перевод времени, разбор денег, транслитерация адреса, форма события, конструктор схемы, логика сканера (разбор токена, офлайн-решение).
- Сквозной прогон в Chromium с поддельной камерой, которая показывает QR настоящего билета:
  - путь организатора;
  - покупки через мок провайдера;
  - проход по камере; повтор; проход без сети; синхронизация;
  - перезагрузка сканера без сети.
- В CSP nginx добавлен адрес хранилища в `connect-src`.
