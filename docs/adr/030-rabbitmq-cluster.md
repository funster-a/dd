# ADR 030. Отказ RabbitMQ: кластер из трёх узлов и кворумные очереди

Дата: 2026-10-06. Статус: принято.

## Контекст

Этап 4 плана развития — отказоустойчивость. Последняя зависимость после api, PostgreSQL и Redis (ADR 027–029) — RabbitMQ. Разбор — [`docs/experiments/2026-10-mq-failover`](../experiments/2026-10-mq-failover/README.md).

Через RabbitMQ идут события между модулями: оплата → подтверждение заказа → выпуск билетов, возвраты, отмена события (ADR 012). Доставку держит transactional outbox:
- событие пишется в PostgreSQL в одной транзакции с изменением данных;
- релей воркера публикует его с подтверждением брокера и только потом помечает опубликованным;
- обработчики идемпотентны.

Так что отказ брокера не теряет события — он их задерживает. Но до этого этапа:
- **Очереди были классическими.** Классическая очередь живёт на одном узле. В кластере её узел пропал — пропала и очередь до его возвращения.
- **Клиент знал один адрес брокера.**
- **Пауза переподключения потребителя росла до 30 секунд.** После простоя потребитель возвращался позже брокера.
- **`/readyz` api проверял RabbitMQ**, хотя api его не использует: события публикует воркер. И Redis, без которого api работает (ADR 018).

## Решение

### Кластер из трёх узлов

`deploy/ha/docker-compose.rabbitmq-ha.yml` — три узла RabbitMQ 4.3, находят друг друга по списку (`deploy/ha/rabbitmq.conf`).
- **`pause_minority`.** Узел в меньшинстве при разделении сети останавливается, а не продолжает принимать сообщения сам по себе.
- **Три узла, а не два.** Кворумной очереди нужно большинство копий; из двух узлов после потери одного большинства нет.

### Кворумные очереди

Все очереди объявляются кворумными (`x-queue-type: quorum`, `internal/platform/mq`):
- **Копии.** У каждой очереди ведущая копия на одном узле и реплики на двух других.
- **Подтверждение.** Сообщение подтверждается издателю, когда его записало большинство.
- **Узел пропал** — оставшиеся двое выбирают новую ведущую копию.
- **Очереди `.dead`** тоже кворумные. Перекладывание в них — `at-least-once`: сообщение не теряется, даже если узел упал посреди перекладывания.

**Переход с классических очередей.** Аргументы очереди должны совпадать при каждом объявлении, поэтому очередь, объявленная раньше классической, при объявлении кворумной даёт ошибку.
- **Пустая** классическая очередь удаляется и объявляется заново кворумной.
- **Непустая** — ошибка с понятным текстом: её сообщения нужно сначала обработать прежней версией.

На одном узле кворумная очередь работает так же, поэтому Compose для разработки не меняется.

### Клиент знает все узлы

`RABBITMQ_URL` принимает адреса узлов через запятую. Соединение идёт к первому доступному, а после обрыва — начиная со следующего узла, чтобы не ждать упавший. Прокси перед брокером не нужен.

### Пауза переподключения — до 5 секунд

Потребитель переподключается с паузой 1, 2, 4, 5, 5… секунд вместо 1, 2, 4, 8, 16, 30. Попытка подключения дешёвая, а каждая лишняя секунда после возвращения брокера — задержка выпуска билетов.

### Таймаут потребителя на недоступном узле — 15 секунд

Сообщения, которые потребитель на пропавшем узле уже взял в работу, кворумная очередь держит за ним `consumer_disconnected_timeout`. Так она защищается от разделения сети: отрезанный узел мог успеть их обработать.
- **По умолчанию — минута.** В эксперименте с потерянным узлом 10–20 оплат ждали билеты 67,6 секунды.
- **Теперь 15 секунд** (`rabbitmq.conf`). Обработчики идемпотентны (ADR 012), поэтому повторная обработка после короткого разделения безопасна. Худшая задержка — 22,5 секунды.
- **Меньше — не стоит.** Короткий сбой сети начнёт порождать повторные обработки там, где их можно было избежать.

### `/readyz` api: только обязательные зависимости

`httpx.Readyz` делит проверки на обязательные и необязательные:
- **Обязательная** (PostgreSQL для api) не прошла — `503`, и балансировщик или оркестратор выводит экземпляр из ротации.
- **Необязательная** (Redis, хранилище файлов) не прошла — `200` со статусом `degraded`: api работает хуже, но работает.

RabbitMQ из api убран совсем.

Иначе отказ общей зависимости вывел бы из ротации все экземпляры сразу. Например, падение Redis, которое api переживает (ADR 018), остановило бы продажу целиком. Это важно для этапа 6: проба готовности Kubernetes читает `/readyz`.

## Результаты эксперимента

100 оплат в секунду, два воркера, узел RabbitMQ убит на 20-й секунде.

| Вариант | Без билета | Задержка билета: медиана / p95 / max |
|---|---:|---:|
| Один узел, без отказа | 0 | 0,3 / 0,4 / 0,5 с |
| Один узел, падение на 20 с | 0 | 7,7 / 25,7 / 30,1 с |
| Кластер, падение узла | 0 | 0,5 / 2,9 / 23,0 с |
| Кластер, узел не вернулся | 0 | 0,4 / 5,1 / 22,5 с |

Ни одна из 90 000 оплат не потерялась, в очереди `.dead` не ушло ни одного сообщения.

## Альтернативы

- **Классические очереди с зеркалированием.** В RabbitMQ 4 зеркалирование классических очередей удалено. Кворумные очереди — его замена.
- **Streams.** Журнал с повторным чтением и большим объёмом. Нужен для аналитики и повторной обработки истории, а не для команд «подтверди заказ». Подтверждение обработки и очередь `.dead` в кворумных очередях есть из коробки.
- **Балансировщик перед кластером** (HAProxy). Один адрес для клиента, но ещё одна точка отказа, которую надо резервировать. Список узлов в клиенте проще.
- **Управляемый брокер** (облачный RabbitMQ или аналог). На продакшене предпочтительнее, если доступен. Код тот же: список адресов или один адрес, который провайдер переносит сам.
- **Без брокера: воркеры читают outbox напрямую.** Меньше компонентов, но очередь, подтверждения, повторы и `.dead` пришлось бы писать самим поверх PostgreSQL — к той же базе, которая под нагрузкой в момент продаж.

## Следствия

- **Код:** кворумные очереди и переход с классических, несколько узлов в `RABBITMQ_URL`, пауза переподключения до 5 с, `httpx.Readyz` с необязательными проверками. api больше не подключается к RabbitMQ.
- **Стенд:** `deploy/ha/docker-compose.rabbitmq-ha.yml`, `deploy/ha/rabbitmq.conf`.
- **Нагрузочный стенд:**
  - поток оплат `loadseed paystream` и проверка билетов `loadseed tickets-check`;
  - серия `loadtest/mqchaos.sh`, отчёт `loadseed mqchaos-report`.
- **Тесты:** замена пустой классической очереди и отказ заменить непустую; `/readyz` с необязательной зависимостью; несколько адресов RabbitMQ в настройках.
- **Этап 4 закрыт.** Все четыре зависимости — api, PostgreSQL, Redis, RabbitMQ — проверены отказом посреди продажи. Дальше — этап 5, читающий контур.
