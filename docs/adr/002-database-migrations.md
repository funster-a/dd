# ADR 002. Миграции базы данных

Статус: принято, 2026-09-28

## Контекст

Схема PostgreSQL будет меняться весь проект. По правилам (`CLAUDE.md`) каждое изменение схемы оформляется отдельной миграцией, уже применённые миграции не правятся, и каждая миграция должна и применяться, и откатываться. Одна и та же цепочка миграций нужна в трёх местах: на машине разработчика, в CI и в `docker compose up`.

## Решение

1. **Инструмент — goose** (`pressly/goose/v3`), миграции на чистом SQL в `migrations/`, у каждой есть секции `Up` и `Down`.
2. **Нумерация последовательная** (`00001_init.sql`, `00002_...`), а не по времени. Порядок миграций виден сразу, а у одного разработчика не бывает параллельных веток, ради которых нужны метки времени. Новая миграция создаётся командой `make migrate-create name=...`.
3. **goose подключён через `go tool`, но в отдельном файле `tools.mod`** (`go tool -modfile=tools.mod goose`). Версия и контрольные суммы закреплены в `tools.mod` и `tools.sum`, отдельно ставить ничего не нужно. `make migrate-up` локально, те же команды в CI, тот же исходник в Docker-образе. Обновление: `go get -modfile=tools.mod -tool github.com/pressly/goose/v3/cmd/goose@<версия>`.
4. **Миграции применяет отдельный одноразовый сервис** `migrate` в Docker Compose. api стартует только после его успешного завершения (`service_completed_successfully`). Сам api миграции не применяет.
5. **CI проверяет полный цикл:** `up`, затем `reset` (откат всех миграций), затем проверка, что в базе не осталось ни таблиц, ни типов, ни функций, ни схем, ни расширений, кроме служебной таблицы goose, и снова `up`.

## Альтернативы

- **golang-migrate.** Похожие возможности, но миграция в нём — два файла вместо одного и нет Go-миграций. goose проще читать. Отклонено.
- **Применять миграции при старте api.** Когда api запущен в нескольких экземплярах, они начинают гоняться за блокировку схемы. Кроме того, упавшая миграция роняет api, а не отдельный шаг развёртывания. Отклонено.
- **goose через `go tool` в основном `go.mod`.** Так было в первой версии каркаса. goose тянет драйверы всех поддерживаемых СУБД: в `go.mod` добавилось около 70 косвенных зависимостей, а `go mod tidy` начал скачивать сотни модулей, включая тестовые зависимости Azure SDK, YDB и sqlite. Каждый tidy локально и в CI стал медленным и падал при сетевых сбоях. Отклонено.
- **goose через `go run ...@version`.** `go.mod` чистый, но версия была бы записана в Makefile и Dockerfile отдельно, а контрольные суммы проверялись бы только через sumdb. Отклонено.

## Следствия

- `go.mod` содержит только зависимости приложения. Зависимости goose, в том числе драйверы ClickHouse, MySQL и MSSQL, живут в `tools.mod` и не попадают ни в `go.mod`, ни в бинари api и worker. В Docker-образе миграций лишние драйверы отключены build-тегами.
- `tools.mod` не приводится в порядок через `tidy`: это скачало бы тестовые зависимости всех драйверов. Он обновляется только через `go get -modfile=tools.mod -tool ...`.
- Пустая первая миграция позволяет с первого дня проверять всю цепочку до появления модели данных.
- Откат должен реально работать. Миграцию с пустым или неполным `Down` CI не пропустит: после `reset` в базе останутся её объекты. Проверено на миграции, которая создаёт таблицу и enum, но ничего не удаляет.
