# ADR 029. Отказ Redis: Sentinel с репликами и журнал на каждом узле — разбор к защите

Неделя 8 (30.11–06.12.2026). ADR: [`docs/adr/029-redis-failover.md`](../../adr/029-redis-failover.md).

## Суть в трёх фразах

В Redis лежат холды мест, сессии покупателей, коды входа и очередь ожидания; один Redis с настройками по умолчанию после падения поднимался пустым, и в эксперименте 12 130 из 17 907 покупателей ушли без билета, потому что сайт выкинул их из аккаунта. Решение — журнал операций (AOF) на каждом узле, чтобы перезапуск терял не больше секунды записей, и три узла под присмотром Sentinel: если ведущий не отвечает 2 секунды, Sentinel повышает реплику, а api сам находит новый ведущий. Простой сократился с 20 до 3 секунд, без билета не ушёл никто, а потеря последних миллисекунд записей допустима, потому что истина о бронях и оплате — в PostgreSQL.

Решение действует, позже не пересматривалось. Его дополнили:
- ADR 030: отказ Redis больше не выводит api из ротации — `/readyz` отвечает 200 `degraded` (ADR 030:59-65; `cmd/api/main.go:146-148`, `:222-230`).
- ADR 031: тот же урок про лимит соединений nginx, что нашёл эксперимент с Redis (ADR 031:61; redis-failover/README.md:82).
- ADR 032: на продакшене Redis управляемый или через оператор, а не StatefulSet в кластере (ADR 032:32, 112).

## Почему так, а не иначе

- **Redis Cluster.** Шардирование нужно, когда данные не помещаются в один узел или узел не справляется с нагрузкой. У проекта ни то, ни другое; ключи холдов заказа и так лежат в одном слоте благодаря `{eventID}` (ADR 029:80).
- **Управляемый Redis с репликой.** На продакшене предпочтительнее, если доступен. Код не меняется: тот же `FailoverClient` или один адрес, который переносит провайдер (ADR 029:81).
- **Только журнал, без реплик.** Корректно, но простой длится, пока узел не поднимут: в эксперименте 20 секунд, ожидание покупателя до 27,6 секунды из 30 (ADR 029:34-38, 82).
- **Сессии в PostgreSQL.** Убирает потерю сессий совсем, но добавляет запрос в базу на каждый запрос — к той самой базе, которая под нагрузкой при старте продаж (ADR 029:83; ADR 018:53).
- **Синхронная репликация (`WAIT 1`) для сессий.** Каждый вход ждал бы реплику. Потеря нескольких входов раз в много месяцев дешевле (ADR 029:84).

## Чем подтверждено

Эксперимент [`docs/experiments/2026-10-redis-failover`](../../experiments/2026-10-redis-failover/README.md): два api за nginx, 100 заказов в секунду 60 секунд, ведущий Redis убит на 20-й секунде, без Sentinel поднят на 40-й; по 3 прогона на вариант.
- **Один Redis без журнала:** без билета ушли 12 130 из 17 907, пропали все 5 250 холдов (evidence.md:170-171).
- **Один Redis с журналом:** без билета 0, восстановление 14,9 с по медиане и 27,6 с в худшем случае, пропал 1 холд (evidence.md:172).
- **Sentinel:** запись доступна через 3 с, без билета 0; 830 покупателей, которым понадобились повторы, ждали 2,8 с по медиане и 6,4 с в худшем случае; неудачных попыток 1 475 — в 24 раза меньше, чем у одного Redis с журналом (evidence.md:173).
- **Асинхронные реплики:** после переключения пропадало 0–2 холда на прогон, сессии не пропадали (evidence.md:174).
- **Пауза 2 с вместо 5:** медиана восстановления с Sentinel 5,4 → 2,8 с; прогонов «до» в данных нет, 5,4 — только в тексте (evidence.md:175).
- **Разброс пауз:** без него около 2 000 покупателей повторяли в одну секунду; в итоговой серии без билета 0 (evidence.md:316).
- **Корректность:** 0 двойных броней, 0 двойных выполнений, 0 призрачных холдов в 15 прогонах, даже когда пропали все холды (evidence.md:76, 285).

Тесты:
- **Настройки Sentinel:** список `REDIS_SENTINELS` чистится от пробелов, `REDIS_MASTER` по умолчанию `dd` (`internal/platform/config/config_test.go:54-64`); адрес без порта отклоняется (`config_test.go:81`).
- **Разброс пауз:** пауза 2 с превращается в 1 000–2 998 мс (`web/src/lib/retry.test.ts:27-30`).
- **Без Redis и без кэша — 503 с `Retry-After`, а не 500** (`internal/identity/cache_test.go:131-143`). Тест проверяет, что заголовок есть, но не его значение 2.
- **Сверка холдов Redis с базой** различает призрачные и пропавшие холды (`cmd/loadseed/check_test.go:399`; evidence.md:100).

Само переключение Sentinel модульным тестом не покрыто: его проверяет только эксперимент.

## Вопросы комиссии

1. **Что хранится в Redis и почему его отказ вообще опасен, если место продаёт база?**
   Ответ: Холды мест, сессии, одноразовые коды входа и очередь ожидания. Продажу мест отказ не ломает: холды — только фильтр перед базой. Опасно другое: пустой Redis после перезапуска не знает сессий, api отвечает `401 invalid_session`, и сайт выкидывает покупателя из аккаунта.
   Источник: ADR 029:9-24; redis-failover/README.md:55-59.

2. **Что именно произошло с одним Redis без журнала?**
   Ответ: Redis по умолчанию пишет только снимки (RDB), а снимок старше, чем вход покупателей перед продажей. После подъёма каждая проверка сессии давала «сессии нет». Без билета ушли 12 130 из 17 907 покупателей, пропали все 5 250 холдов. Доля 68 % задана сценарием: после 20-й секунды не прошёл ни один заказ.
   Источник: ADR 029:21-24, 74; evidence.md:170-171.

3. **Почему журнала недостаточно, раз с ним никто не ушёл без билета?**
   Ответ: Журнал спасает данные, но не время. Простой длится, пока узел не поднимут; в эксперименте 20 секунд, и покупатель ждал до 27,6 секунды при бюджете повторов сайта 30 секунд. Новый вход и очередь ожидания всё это время не работали.
   Источник: ADR 029:34-38; evidence.md:172.

4. **Как работает переключение с Sentinel?**
   Ответ: Три узла Redis с журналом и три Sentinel. Если ведущий не отвечает 2 секунды и это подтверждают двое из трёх Sentinel, они повышают реплику; вернувшийся ведущий становится репликой. api спрашивает адрес ведущего у Sentinel через go-redis `FailoverClient` и сам переходит на новый. В эксперименте запись снова доступна через 3 секунды.
   Источник: ADR 029:40-47; `deploy/ha/docker-compose.redis-ha.yml:37-38`; `internal/platform/redis/redis.go:33-47`.

5. **Реплики асинхронные. Что теряется при падении ведущего и почему это допустимо?**
   Ответ: Последние миллисекунды записей. Пропавший холд ослабляет фильтр, конкурента отсечёт база; пропавшая сессия — человек войдёт снова; пропавшее место в очереди — встанет снова. Ни один случай не продаёт место дважды и не теряет деньги: истина в PostgreSQL. В эксперименте пропадало 0–2 холда на прогон.
   Источник: ADR 029:59-66; evidence.md:174.

6. **Почему не Redis Cluster?**
   Ответ: Cluster решает шардирование, а это нужно, когда данные не помещаются в узел или узел не справляется. У проекта ни того, ни другого. Ключи холдов одного заказа и так должны лежать в одном слоте, `{eventID}` в ключе это обеспечивает, так что переход возможен без смены модели данных.
   Источник: ADR 029:80.

7. **Зачем менять `Retry-After` с 5 на 2 секунды и добавлять разброс пауз?**
   Ответ: Пауза 5 секунд осталась от одного Redis; с Sentinel простой 2–3 секунды, и покупатель ждал уже работающий Redis. После снижения медиана восстановления 5,4 → 2,8 с. Разброс 0,5–1,5 нужен, потому что без него около 2 000 ждущих повторяли в одну секунду, и сразу после подъёма шли обрывы и 502.
   Источник: ADR 029:49-57; `internal/identity/http.go:50`; `web/src/lib/retry.ts:23-26`; evidence.md:175, 316.

8. **Что будет при разделении сети, а не при падении?**
   Ответ: Бывший ведущий, отрезанный от Sentinel, но видимый клиентам, принимал бы записи, которые потом пропадут. Защита — `min-replicas-to-write 1` и `min-replicas-max-lag 10`: ведущий без реплик перестаёт принимать запись. Это продакшен-настройка, на стенде она не включена, и разделение сети не проверялось.
   Источник: ADR 029:89; redis-failover/README.md:89; evidence.md:419, 422.

9. **Что в этом решении не доказано?**
   Ответ: Частота призрачных холдов: в потоке нет отмен и замен корзины, поэтому снятий холдов, которые могли бы пропасть, почти нет. Разделение сети не проверялось. Всё на одной машине, по 3 прогона на вариант. Медианы восстановления и пропавшие холды в results.csv не хранятся.
   Источник: ADR 029:93; evidence.md:76, 422, 424.

## Где слабое место

- **Призрачные холды не измерены.** Лишний холд, у которого пропало снятие, отказывает «место занято» до конца своего срока, хотя место в базе свободно (ADR 029:62, 93). Ответ: корректность от этого не страдает, страдает конверсия на одно место до 10 минут. Метрика для продакшена названа: отказы Redis «место занято» при свободном месте в базе; самовосстановление — следующий шаг, если они появятся.
- **`min-replicas-to-write` не включён на стенде** (evidence.md:422). Ответ: на стенде только падение процесса, при нём настройка не нужна; для продакшена она записана в «Следствиях» (ADR 029:89).
- **Разделение сети не проверялось нигде в этапе 4** (evidence.md:419). Ответ: проверено падение процесса — самый частый отказ; разделение — отдельный эксперимент с сетевыми правилами, следующий шаг.
- **«Redis не был узким местом на штурме» — вывод без отдельного замера Redis.** В ADR 026 и его эксперименте нагрузку Redis не мерили отдельно, а в read-path на перегруженной машине Redis иногда не укладывался в бюджет 300 мс (read-path/README.md:83). Ответ: это свойство общей машины на 4 vCPU, а не нехватка одного узла Redis; довод против Cluster держится на том, что данных мало.
- **Числа «до» для паузы 5 секунд есть только в тексте** (evidence.md:175). Ответ: главный эффект решения — 20 → 3 секунды простоя и 12 130 → 0 ушедших — подтверждён сравнением вариантов одной серии.
- **Одна машина, три прогона на вариант** (evidence.md:387). Ответ: сравниваются только варианты одной серии; разница 0 против 12 130 ушедших не объясняется разбросом.

## Проверь себя

1. Покупатель встал в очередь ожидания за 50 мс до падения ведущего Redis, Sentinel повысил реплику. Что он увидит и почему инвариант при этом не нарушен?
2. Объясните, почему с Sentinel ушедших без билета 0, а неудачных попыток всё же 1 475, и кто из покупателей их видел.
3. Ведущий Redis отрезан сетью от Sentinel, но api до него достаёт. Опишите, что произойдёт с холдами и сессиями без `min-replicas-to-write` и с ним.
