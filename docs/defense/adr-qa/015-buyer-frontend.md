# ADR 015. Сайт покупателя — разбор к защите

Неделя 4 (02–08.11.2026). ADR: [`docs/adr/015-buyer-frontend.md`](../../adr/015-buyer-frontend.md).

## Суть в трёх фразах

Бэкенд MVP был готов, но покупателю нужен сайт: афиша, схема зала, оформление, оплата, билеты и возврат, причём заказчик просил современный дизайн без шаблонного вида. Решение — одностраничное приложение на Vue 3 и TypeScript без UI-библиотеки, схема зала в SVG с управлением с клавиатуры, раздача через nginx, который проксирует `/v1` в api, так что браузер работает с одним адресом. Отсюда нет CORS и лишнего Node-процесса, истина о местах и деньгах остаётся на сервере, а SEO и отрисовка очень больших залов отложены.

Что изменили позже:
- [ADR 024](../../adr/024-stadium-plan.md), строки 9–13, 25–31: для стадиона схема одной картинкой не годится. Выбор стал двухшаговым: план секторов, затем места одного сектора. Вместо полного списка занятых мест план опрашивает сводку — в 60 раз меньше даже со сжатием (ADR 024:54).
- [ADR 019](../../adr/019-service-fee.md), строки 48–52: корзина показывает сервисный сбор той же формулой, что сервер.
- [ADR 020](../../adr/020-waiting-room-and-ip-limit.md), строки 50–57: очередь ожидания на странице события.
- [ADR 028](../../adr/028-postgres-failover.md), строки 71–77, и [ADR 029](../../adr/029-redis-failover.md), строки 53–57: клиент сайта повторяет чтения и запросы с ключом идемпотентности при обрыве и 502/503/504, не дольше 30 секунд, пауза со случайным разбросом.
- [ADR 031](../../adr/031-read-path.md), строки 51–59, 102: сайт ходит в api через nginx-балансировщик, который кэширует публичные GET по `Cache-Control` (страница — 60 секунд, занятость — 2 секунды). Прокси `/v1` остался, сменился адрес за ним.
- [ADR 032](../../adr/032-kubernetes.md), строка 81: nginx сайта берёт DNS-сервер из `/etc/resolv.conf`, чтобы тот же образ работал в Kubernetes.
- [ADR 016](../../adr/016-organizer-cabinet-and-scanner.md): кабинет организатора и сканер живут в этом же приложении.

## Почему так, а не иначе

- **Nuxt с SSR.** SEO-выигрыш для афиши есть, но нужен ещё один Node-процесс в проде. Страница события и так кэшируется на бэкенде (ADR 010). Отложено до появления требования к SEO.
- **UI-библиотека (Vuetify, PrimeVue).** Формы собирались бы быстрее, но узнаваемый «библиотечный» вид противоречит требованию к дизайну. Компонентов мало, они свои.
- **Canvas для схемы зала.** Быстрее на десятках тысяч мест, но без доступности и с ручной обработкой кликов. Для залов MVP не нужен; для стадиона ADR 024 решил задачу двумя шагами, а не canvas.
- **Раздача SPA из api на Go.** На один контейнер меньше, но сборка фронтенда смешалась бы со сборкой бэкенда. nginx даёт кэш статики и заголовки без кода.
- **Шрифты с Google Fonts.** Лишний запрос к третьей стороне и ослабление CSP. Шрифты собираются вместе с сайтом через `@fontsource`.

## Чем подтверждено

- **CI на каждый push:** задача Web — проверка типов `vue-tsc`, юнит-тесты vitest, сборка (`.github/workflows/ci.yml:142-161`). Compose-тест с нуля проверяет, что nginx отдаёт SPA на маршрутах `/`, `/e/…`, `/org/login`, проксирует `/v1/public/events` и ставит заголовок CSP (`ci.yml:176-184`).
- **Логика схемы и корзины — чистые функции с тестами:** раскладка мест и категории, координаты из редактора, корзина с занятыми местами и лимитом билетов, остаток входной зоны, сервисный сбор той же формулой, что на сервере. `web/src/lib/seatmap.test.ts:23-93`.
- **Повтор запросов (после ADR 028/029):** какие ошибки повторяются, пауза по `Retry-After`, рост паузы, разброс 0,5–1,5. `web/src/lib/retry.test.ts:4-31`.
- **Найденная фронтендом ошибка бэкенда:** после возврата место освобождалось в базе, но холд оплаченного заказа в Redis не давал его купить. `ApplyRefund` снимает ключи холдов (`internal/booking/refunds.go:48-50`), тест `TestRefundedSeatIsBookableAgain` (`internal/booking/payments_test.go:332-355`).
- **Эксперименты нашли пробелы сайта:** при переключении PostgreSQL сайт не повторял запросы, хотя эксперимент моделировал повторяющего клиента — добавлен `web/src/lib/retry.ts` (evidence.md:312). При отказе Redis около 2 000 покупателей повторяли в одну секунду — добавлен случайный разброс паузы (evidence.md:316).
- **Не измерено.** Размер сборки (~45 КБ основного JS, ~7 КБ страницы события) записан только в ADR, CI его не проверяет. Нагрузочные сценарии k6 идут путём сайта запросами к API (`docs/experiments/2026-10-stadium-storm/README.md:17`), браузер и отрисовку не мерили. Тестов компонентов и сквозного сценария в репозитории нет.

## Вопросы комиссии

1. **Что это за приложение и почему без UI-библиотеки и менеджера состояний?**
   Ответ: Vue 3 с `<script setup>`, vue-router и TypeScript в строгом режиме. Общего состояния мало — сессия и уведомления, его держат модульные `reactive` в `composables/`, корзина живёт на странице события. UI-библиотека дала бы узнаваемый шаблонный вид, а заказчик просил обратного. Экраны грузятся лениво по маршрутам.
   Источник: ADR 015, «Приложение» (строки 15–19), «Альтернативы» (строка 81); `web/src/router.ts:15-20`.

2. **Почему nginx проксирует `/v1` в api, а не CORS?**
   Ответ: Браузер работает с одним origin: сайт и API на одном адресе. CORS не нужен, cookie и токен не уходят на чужой домен. nginx заодно отдаёт статику с вечным кэшем для файлов с хешем и `no-cache` для `index.html`. Раздавать SPA из Go отказались, чтобы не смешивать сборки фронтенда и бэкенда.
   Источник: ADR 015, «Развёртывание» (строки 54–56), «Альтернативы» (строка 83); `web/nginx.conf.template:24-49`; `web/Dockerfile:1-16`.

3. **Почему схема зала в SVG, а не на canvas?**
   Ответ: В SVG каждое место — отдельный элемент с `role="button"`, подписью для экранного диктора, фокусом и выбором по Enter и пробелу. На canvas доступность и клики пришлось бы делать вручную. Для залов MVP на сотни и тысячи мест SVG хватает. Для стадиона на 23 804 места позже сделали выбор в два шага: в секторе 200–600 мест (ADR 024).
   Источник: ADR 015, «Схема зала» (строка 39), «Альтернативы» (строка 82); `web/src/components/SeatMap.vue:89-96`; ADR 024:7, 25-31.

4. **Место заняли, пока покупатель выбирал. Что он увидит?**
   Ответ: Занятость обновляется раз в 15 секунд, пока вкладка видима, и занятое место уходит из корзины. Если место заняли в последний момент, сервер отвечает `seat_taken`: схема обновляется, покупатель видит объяснение. Истина о занятости только на сервере, сайт её не решает.
   Источник: ADR 015, строка 44; `web/src/views/EventView.vue:179, 190-191, 243, 289-292`.

5. **Покупатель нажал «Оформить», связь оборвалась. Не появится ли второй заказ?**
   Ответ: Ключ идемпотентности создаётся на одну попытку оформления и уходит в заголовке `Idempotency-Key`. Повтор с тем же ключом получает тот же ответ, второй заказ не создаётся (ADR 008). После ADR 028 клиент сам повторяет такой запрос при обрыве и 502/503/504 не дольше 30 секунд. Новый ключ берётся при открытии оформления и после ошибки, когда повторы закончились, — для новой попытки.
   Источник: ADR 015, строка 49; `EventView.vue:32, 228, 273, 294`; `web/src/api/client.ts:85, 106-131`; ADR 028:71-77.

6. **Почему не Nuxt с SSR, ведь афише нужно SEO?**
   Ответ: SSR требует ещё один Node-процесс в проде, а это лишняя инфраструктура для одного разработчика. Страница события и так кэшируется на бэкенде. Требования к SEO в MVP нет, поэтому решение отложено, а не отвергнуто.
   Источник: ADR 015, «Альтернативы» (строка 80); ADR 010.

7. **Какая защита стоит в заголовках и зачем шрифты локально?**
   Ответ: CSP разрешает скрипты только со своего адреса, картинки — свои и из хранилища `MEDIA_ORIGIN`, запрещает встраивание страницы во фрейм. Плюс `nosniff` и `Referrer-Policy`. Шрифты собраны вместе с сайтом через `@fontsource`: нет запроса к третьей стороне, и CSP не нужно ослаблять ради Google Fonts.
   Источник: ADR 015, строки 56, 63; `web/nginx.conf.template:7-11`.

8. **Сколько весит сайт и чем это подтверждено?**
   Ответ: По ADR основной JS около 45 КБ gzip, страница события около 7 КБ: экраны грузятся лениво. Это замер при сборке, записанный в ADR; CI размер не проверяет, отдельного эксперимента нет. Для стадиона важнее объём данных: сводка занятости в 60 раз меньше полного списка даже со сжатием (ADR 024).
   Источник: ADR 015, строка 19; ADR 024:45-54.

9. **Что сайт дал бэкенду?**
   Ответ: Два читающих эндпоинта в модулях, которые владеют таблицами: `GET /v1/public/events` в catalog (до 60 событий, `Cache-Control: max-age=30`) и `GET /v1/me/orders` в booking (до 100 заказов). И найденную ошибку: после возврата холд оплаченного заказа в Redis ещё до 10 минут не давал купить освободившееся место. Теперь `ApplyRefund` снимает ключи холдов, это проверяет тест.
   Источник: ADR 015, «Два новых эндпоинта» (строки 30–35), «Следствия» (строка 89); `internal/catalog/http.go:35-42`; `internal/catalog/public.go:176`; `internal/booking/queries.sql:279`; `internal/booking/refunds.go:48-50`; `payments_test.go:332-355`.

## Где слабое место

- **Тесты покрывают только чистые функции.** Все тесты сайта лежат в `web/src/lib/*.test.ts`; `@vue/test-utils` объявлен в зависимостях, но компонентных тестов нет. Сквозного сценария в репозитории тоже нет. Почему приемлемо: решения о местах и деньгах принимает сервер, а логика схемы, корзины и сбора вынесена в функции с тестами. Что дальше: сквозной сценарий в CI с браузером.
- **Нет SEO.** SPA отдаёт пустой `index.html`, страницы событий поисковику без JS не видны. Отложено осознанно (ADR 015:80).
- **Схема одной картинкой не годилась для стадиона.** ADR 024:9-13 перечисляет причины: 24 тысячи кружков на телефоне, около мегабайта JSON на каждый опрос, нет геометрии, нет сжатия. Исправлено двухшаговым выбором и сводкой занятости.
- **До ADR 028 сайт не повторял запросы:** любая ошибка сразу показывалась покупателю (ADR 028:73; evidence.md:312). Теперь повтор есть, но только для чтений и запросов с ключом: повтор без ключа мог бы выполнить действие дважды.
- **CSP допускает `'unsafe-inline'` для стилей.** Это нужно привязкам Vue `:style` (`web/nginx.conf.template:7-9`). Скрипты при этом только свои.
- **Размер сборки и скорость в браузере не измерялись** экспериментом; число в ADR — замер при сборке.
