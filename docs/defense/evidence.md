# Реестр доказательств

Реестр собирает числа для колоды, спецификации и пояснительной записки в одном месте. Правило простое: число на слайд или в записку берётся только отсюда, а здесь у каждого числа есть ссылка на источник (файл:строка). Если источник и реестр расходятся, верен источник, а реестр нужно исправить. Если два источника расходятся между собой, ниже указано, какому верить и почему.

Сверено с репозиторием на 2026-10-08 (ветка `claude/gracious-gauss-0qt523`, коммит a3980f6). Пути `docs/experiments/2026-10-…/` сокращены до имени эксперимента: `booking-strategies/README.md:48` значит `docs/experiments/2026-10-booking-strategies/README.md:48`.

## Стенд и абсолютные числа

Одна формулировка для всех слайдов и записки:

> Все нагрузочные эксперименты шли на одной машине с 4 vCPU. Генератор нагрузки k6, api, PostgreSQL, Redis и RabbitMQ работали на ней вместе и делили процессор. Поэтому абсолютные числа описывают стенд, а не платформу: на отдельных серверах они будут лучше. Доказательную силу имеет сравнение вариантов внутри одной серии.

Следствия для цитирования:

- Числа из разных серий не смешиваются, даже если сценарий похож. Пример: p95 заказа «без очереди» на зале 1 000 мест и 5 000 покупателях — 5 391 мс в эксперименте с очередью (waiting-room/tables.md:4) и 5 632 мс у Redis + БД в эксперименте со стратегиями (booking-strategies/tables.md:29). Это разные серии: во второй нет прогрева сессий.
- Заказ p95 при очереди 150/с — 1,06 с в штурме (один api), 1,0 с в read-path (два api, три узла PostgreSQL) и 526 мс в k8s (другая машина, 2–3 пода). Это три разных стенда, сравнивать их напрямую нельзя.
- Ёмкость в заказах в секунду — свойство стенда с четвертью ядра на экземпляр. Ёмкость на отдельных серверах не измерялась.

## Тезис 3. Бизнес-модель

Финмодель (docs/business/finmodel.py, finmodel.xlsx, README) считает только сегмент МСБ: рынок задан как «МСБ-организаторы» (docs/business/README.md:10; finmodel.py:423), цена билета — «МСБ-сегмент дешевле крупных концертов» (finmodel.py:100). Решение от 2026-10-03 добавило второй сегмент — крупных организаторов и площадки (spec.md:17-20; ADR 021:7). **Крупный сегмент в деньгах не посчитан:** ни выручки, ни юнит-экономики, ни рынка по нему в финмодели нет. Для него есть только инженерные доказательства (тезис 2).

Все числа модели, кроме решений владельца (сбор 5 %, 0 % с организатора, правила возврата сбора, команда, рынок), — допущения (README.md:5-12; spec.md:297). Значения из xlsx — сохранённый кэш формул, сверенный независимым пересчётом формул finmodel.py.

## Границы доказательства

Стенд и повторы:

- Все Compose-эксперименты — на одной машине с 4 vCPU, где генератор нагрузки, api, PostgreSQL, Redis и RabbitMQ делят ядра. Абсолютные числа зависят от стенда, сравниваются только варианты в одной серии. Повтора на отдельных машинах не было: «у дипломного проекта один стенд» (booking-strategies/README.md:135; ADR 017:83; waiting-room/README.md:85; scaling/README.md:87; stadium-storm/README.md:95; read-path/README.md:82; pg-failover/README.md:97; redis-failover/README.md:88; mq-failover/README.md:84).
- Лимит процессора — модель небольшого узла, а не настоящий узел; сеть локальная, без задержек настоящей сети (scaling/README.md:88).
- Повторов мало: 3 на точку в стратегиях, очереди и отказах; 2 в штурме и read-path; 1 на ступень в масштабировании и на вариант в k8s. Разброс количественно не оценивался (booking-strategies/README.md:137; scaling/README.md:91; stadium-storm/README.md:99; read-path/README.md:92; k8s-autoscaling/README.md:101; redis-failover/README.md:92; mq-failover/README.md:88).
- Покупатели k6 решают мгновенно, живые выбирают места десятки секунд (waiting-room/README.md:86; stadium-storm/README.md:98).

Ядро и стратегии:

- Один процесс api и пул 32 соединения; поведение с большим пулом не измерялось (booking-strategies/README.md:136).
- Сценарий one-seat крайний, к реальности ближе hall (booking-strategies/README.md:138).
- Уровень изоляции SERIALIZABLE не измерялся (ADR 017:82).
- Отказ Redis в эксперименте со стратегиями — только Redis + БД, hall, 2 000 покупателей; повтор клиента с тем же ключом k6 не делал (booking-strategies/README.md:97,114).
- Опубликованные проверки инварианта сняты версией проверяльщика до 2026-10-08 и новой версией не перепроверялись. Проверяльщик корректен только после разбора очереди событий; у отменённого события он сверяет только двойные брони (cmd/loadseed/check.go:54-59,87-91).
- Интеграционные тесты и режимы с Redis пропускаются без DATABASE_TEST_URL и REDIS_TEST_ADDR (cmd/loadseed/check_test.go:26-27; internal/booking/env_test.go:58-59; strategy_test.go:15). Мутационные проверки сделаны вручную и в репозитории не зафиксированы.

Очередь и масштабирование:

- Лимит на IP в экспериментах выключен; холодный старт снят одним прогоном (waiting-room/README.md:27,30; ADR 020:90).
- Скорость пропуска по умолчанию — 50/с; мерились только 100, 150, 200 и 300/с. Значение 50 надо подбирать на реальном железе (ADR 020:35,74).
- «Около 11 опросов на покупателя» при опросе раз в 3 с — расчёт (waiting-room/README.md:69).
- Масштабирование нагружало только заказ; чтение схем и страниц — в read-path (scaling/README.md:89). Очередь и лимит на IP при этом выключены (scaling/README.md:19).
- Коды ошибок за пределом ёмкости не разбирались (scaling/README.md:90).
- Ёмкость отдельного 8-ядерного сервера PostgreSQL и «10 подов — 2 500 заказов/с» — экстраполяции (scaling/README.md:57; ADR 032:11,73).

Большие площадки:

- Распродажу стадиона до нуля не проверяли: спрос 5 000 покупателей — 42 % мест (stadium-storm/README.md:96; ADR 026:54).
- Больше 5 000 покупателей не запускали: k6 упирается в память стенда (stadium-storm/README.md:30).
- Цель этапа 3 в spec — 50 тысяч мест; нагрузкой проверено 33 509 (spec.md:272; ADR 024:9).
- Оплата в штурмах не участвовала: места остаются в холде (stadium-storm/README.md:97).
- В read-path время ответа в вариантах с репликами и кэшем на краю нельзя сравнивать с первыми двумя: срабатывал предохранитель Redis (read-path/README.md:41,83-90).
- Настоящий CDN не мерили, кэш на краю — nginx (read-path/README.md:91; ADR 031:88).

Отказоустойчивость:

- Нигде не проверялось разделение сети: только падение процесса. Для PostgreSQL два ведущих не воспроизводились, repmgr от них не защищает (api-failure/README.md:80; ADR 027:43-45; pg-failover/README.md:99; ADR 028:100-108; redis-failover/README.md:89; mq-failover/README.md:85).
- Клиент в экспериментах — скрипт; живой покупатель может закрыть вкладку раньше (api-failure/README.md:81).
- PostgreSQL: только 100 заказов/с, рост окна потери асинхронной репликации под нагрузкой не измерен; по 5 прогонов на вариант — потеря редкое событие; circuit breaker на время простоя не сделан; бывший ведущий возвращался через 20 с, быстрый возврат не проверялся (pg-failover/README.md:82,98,100,102).
- Redis: min-replicas-to-write не включён; частота призрачных холдов не измерена — в потоке нет отмен (redis-failover/README.md:89-90; ADR 029:89,93).
- RabbitMQ: поток минует модуль оплаты и вебхук; results.csv нет; инвариант мест не проверялся (mq-failover/README.md:86).
- Медианы восстановления (PostgreSQL, Redis), пропавшие холды и медианы времени заказа в results.csv не хранятся — проверить их по данным нельзя.

Kubernetes:

- Один узел kind; кластер с отдельными узлами не проверяли (k8s-autoscaling/README.md:99).
- Запрос CPU 200m вместо 500m из base (k8s-autoscaling/README.md:14,100).
- Край и воркер не масштабировались (k8s-autoscaling/README.md:102).
- Подъём подов по расписанию продаж не реализован; HPA по метрикам приложения и KEDA не пробовали (ADR 032:107-109,124).
- kind и k3s не запускаются в песочнице разработки, поэтому стенд — раннер GitHub (ADR 032:89).

Бизнес-модель:

- Финмодель считает только МСБ; крупный сегмент (решение 2026-10-03) в деньгах не посчитан (spec.md:17-20; docs/business/README.md:10).
- Цифры юнит-экономики — собственные допущения; всё, кроме решений владельца, — допущения Claude (spec.md:297; docs/business/README.md:12).
- Базовый сценарий надо подтвердить первыми клиентами; численности рынка — допущения; реальных клиентов и интервью нет (docs/business/README.md:119,126; finmodel.py:424; spec.md:287).
- Не выяснено, нужен ли статус платёжной организации или сплит-платёж эквайера (docs/business/README.md:123; finmodel.py:476-479).
- Налог 4 % верен только при агентской схеме, она не оформлена (docs/business/README.md:124; finmodel.py:480-482).
- Влияние сбора на цену и отказы в корзине не измерено (docs/business/README.md:125).
- Выплаты основателю помечены «уточнить» (finmodel.py:92).
