# ADR 023. Горизонтальное масштабирование api и воркера

Дата: 2026-10-03. Статус: принято.

## Контекст

Этап 2 плана развития (spec.md): несколько экземпляров api за балансировщиком. Нужно проверить, что состояние живёт только в базе и Redis, и показать график «экземпляры → пропускная способность». Основание — ADR 021: система растёт как масштабируемый монолит.

## Решение

### Что лежит в памяти экземпляра

Каждый общий ресурс проверен на работу при нескольких экземплярах:

| Где | Что в памяти | Почему это безопасно |
|---|---|---|
| Холды, очередь ожидания, сессии | ничего, всё в Redis | общий источник для всех экземпляров |
| Брони, заказы, оплаты | ничего, всё в PostgreSQL | инвариант держит транзакция с `FOR UPDATE` (ADR 017) |
| Кэш проверенных сессий (ADR 018) | сессии, проверенные в Redis | читается, только когда Redis недоступен. Выход на одном экземпляре другие узнают через Redis сразу; при отказе Redis старая сессия живёт на другом экземпляре не дольше срока кэша — так и было принято в ADR 018 |
| Объединение одинаковых запросов (singleflight) | запрос, который сейчас выполняется | только склеивает одновременные запросы внутри экземпляра; на корректность не влияет |
| Предохранитель Redis | открыт он или закрыт | у каждого экземпляра свой — так и нужно: каждый сам видит свою связь с Redis |
| Воркер: релей outbox, закрытие просроченных заказов | ничего | пачки выбираются `FOR UPDATE SKIP LOCKED`: два воркера не берут одну строку |

Переделывать ничего не пришлось: состояние уже жило там, где требует ADR 021.

### Балансировщик

- **В Docker Compose** api и воркер запускаются репликами: `API_REPLICAS` и `WORKER_REPLICAS`, по умолчанию 2.
- **Порт 8080 слушает `api-lb`** — nginx. Он находит экземпляры через DNS Docker (`resolver 127.0.0.11 valid=10s`, адрес в переменной) и раскладывает запросы по кругу.
- **Масштабирование на ходу:** `docker compose up -d --scale api=4 --no-recreate`. Новые экземпляры попадают в балансировку за 10 секунд, перезапуск не нужен.
- **Отказ экземпляра:** `proxy_next_upstream error` повторяет запрос на другом экземпляре, только если соединение не установилось. Запрос, который уже дошёл до api, не повторяется: заказ мог быть создан. Повтор — дело клиента, с тем же ключом идемпотентности.
- **Сайт** (`web`) ходит в api так же, через DNS-имя сервиса.
- **Prometheus** собирает метрики с каждого экземпляра через `dns_sd_configs`. Метка `instance` различает экземпляры, панели дашборда суммируют.
- **Вебхуки** платёжного провайдера идут через балансировщик (`PAYMENT_CALLBACK_URL=http://api-lb:8080/...`): любой экземпляр примет любой вебхук, обработка идемпотентна.

### Полуоткрытый предохранитель Redis

Эксперимент нашёл ошибку предохранителя (ADR 017, 018). Под нагрузкой на перегруженном процессоре одна медленная команда Redis открывала предохранитель на 5 секунд. Все эти 5 секунд:
- проверка сессии, которой нет в локальном кэше, отвечала `503 session_store_unavailable`;
- захват мест шёл без холдов в Redis, только через базу, то есть медленнее.

Redis при этом был здоров: тормозил сам экземпляр.

Теперь предохранитель полуоткрытый:
- пока он открыт, раз в `ProbeInterval` (100 мс) один запрос проходит в Redis пробой;
- удачная проба сразу закрывает предохранитель;
- остальные запросы, как и раньше, сразу получают отказ, чтобы не ждать таймаута.

Этот предохранитель общий для проверки сессий, холдов и очереди ожидания, поэтому исправление действует на все три.

Тест: из 100 одновременных запросов в открытый предохранитель пробой проходит ровно один.

## Результаты эксперимента

Серия `loadtest/scale.sh`: постоянный поток заказов ступенями, экземпляры api по четверть ядра за nginx, всё на одной машине с 4 vCPU. Разбор — в [`docs/experiments/2026-10-scaling`](../experiments/2026-10-scaling/README.md).

| Экземпляров api | Ёмкость, заказов в секунду (p95 < 500 мс, ошибок < 1%) | Узкое место |
|---:|---:|---|
| 1 | 200 | процессор экземпляра: 100% лимита |
| 2 | 500 | процессор экземпляров и PostgreSQL, 1 ядро |
| 4 | 500 | PostgreSQL и общая машина; экземпляры загружены на 69% |

- **1 → 2 экземпляра:** ёмкость растёт в 2,5 раза. Экземпляры не мешают друг другу, нагрузка делится поровну.
- **2 → 4:** роста нет, узкое место переехало в базу и общую машину стенда. Следующие рычаги — читающий контур (этап 5) и компактная занятость (этап 3).
- **Предохранитель.** Полуоткрытый предохранитель вдвое поднял ёмкость одного экземпляра (200 → 400 при пол-ядра). При 400 заказах в секунду p95 упал с 3,6 с до 127 мс.
- **Корректность.** Двойных броней — ноль во всех конфигурациях и на всех ступенях, включая перегрузку.

## Альтернативы

- **Kubernetes уже сейчас.** Это этап 6. Compose с репликами и nginx проверяет главное — что api не хранит состояния, — без кластера на ноутбуке.
- **Липкие сессии на балансировщике** (покупатель всегда на одном экземпляре). Нужны, когда состояние в памяти, а у нас его нет. Липкость мешала бы равномерной нагрузке и переживанию отказа экземпляра.
- **Общий кэш сессий в Redis вместо локального.** Локальный кэш нужен именно на случай отказа Redis (ADR 018), общий в Redis этот случай не закрывает.
- **Лидер среди воркеров** для закрытия заказов и релея. `SKIP LOCKED` даёт то же без выборов лидера и без простоя при его отказе.
- **Предохранитель с фиксированным временем без проб.** Проще, но, как показал эксперимент, превращает короткую задержку в 5 секунд отказов.

## Следствия

- **Запуск:** `docker compose up` поднимает по два экземпляра api и воркера; CI проверяет, что Prometheus видит оба.
- **Новые настройки:** `API_REPLICAS`, `WORKER_REPLICAS`.
- **Нагрузочный стенд:** сценарий k6 `capacity.js`, серия `loadtest/scale.sh`, отчёт `loadseed scale-report`.
- **Правило ADR 021 остаётся:** любой новый общий ресурс проверяется на несколько экземпляров. Таблица выше — образец такой проверки.
