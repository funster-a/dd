# ADR 004. Контроль границ модулей и CI — разбор к защите

Неделя 1 (12–18.10.2026). ADR: [`docs/adr/004-module-boundaries-and-ci.md`](../../adr/004-module-boundaries-and-ci.md).

## Суть в трёх фразах

Модульный монолит (ADR 001) держится на правиле «доменные модули не импортируют друг друга», а у одного разработчика правило, которое проверяют только глазами, нарушится при первом дедлайне. Решение — проверять границы линтером: depguard в `.golangci.yml` запрещает такие импорты, а CI в GitHub Actions на каждый push собирает код, гоняет линтер, миграции и тесты с детектором гонок и поднимает весь проект через `docker compose up` с нуля. Следствие: нарушение архитектуры или пункта Definition of Done обнаруживается в момент push, а не на защите.

## Почему так, а не иначе

- **Разнести модули по отдельным Go-модулям.** Границы стали бы жёсткими на уровне компилятора, но появились бы версии модулей, директивы `replace` и сложная сборка. Для одного бинаря это лишнее.
- **Проверять границы только на ревью.** Без второго человека ненадёжно. Именно так было записано в ADR 001, и ADR 004 это заменил.
- **Интеграционные тесты на testcontainers.** Понадобилась бы новая зависимость и Docker внутри тестов. Service-контейнеры CI и `make infra-up` локально дают то же проще. Отклонено на текущем этапе.

## Чем подтверждено

- **Правила depguard.** Каждый доменный модуль не может импортировать остальные, `internal/platform` не может импортировать ни один из них (`.golangci.yml:34-113`). Сейчас в `internal/` нет ни одного импорта между доменными модулями.
- **Версия линтера одна.** golangci-lint v2.14.0 в `Makefile:28` и в `.github/workflows/ci.yml:40`.
- **CI на каждый push.** `ci.yml:3-5`; тесты идут через `make test-integration` с `-race` (`Makefile:66-68`). Оговорка: CI проверяет последний коммит каждого push, а при `cancel-in-progress` новый push той же ветки отменяет незавершённый прогон предыдущего; промежуточные коммиты могут остаться непроверенными ([evidence.md](../evidence.md), «Тесты: горутины и проверяльщик инварианта», :80; ci.yml:10-12).
- **Задачи CI.** Build (`go mod tidy -diff`, сборка), Lint, Test (миграции `up → reset` с проверкой пустой базы → `up`, затем все тесты), Compose (`docker compose up --build --wait` с нуля, `/healthz`, `/readyz`, доставка тестового сообщения до worker) — `ci.yml:15-28, 30-40, 42-128, 163-212`.
- **Пример зелёного прогона.** Исправление ошибки в booking (PR #26) прошло CI, run 37757141072 (evidence.md:331). Саму ошибку нашёл проверяльщик инварианта, а не CI.
- **Не зафиксировано:** намеренное нарушение границы, на котором depguard сломал бы сборку, в репозитории не записано. Длительность задач CI не измерялась.

## Вопросы комиссии

1. **Что проверяет CI и зачем?**
   Ответ: CI проверяет Definition of Done автоматически на каждый push. В ADR 004 четыре независимые задачи: Build, Lint, Test и Compose. Сейчас их шесть: добавились проверка манифестов Kubernetes (ADR 032) и сборка с тестами сайта (ADR 015), а Build ещё сверяет сгенерированный код sqlc (ADR 007).
   Источник: ADR 004:13-17; `ci.yml:15-28, 130-140, 142-161`; ADR 007:11; ADR 015:87; ADR 032:120.

2. **Как линтер узнаёт, что граница нарушена?**
   Ответ: depguard проверяет импорты. Для файлов каждого модуля задан список запрещённых пакетов — остальные доменные модули. Для `internal/platform` запрещены все доменные модули. Импорт из запрещённого списка — замечание линтера, `make lint` и CI падают.
   Источник: ADR 004:11; `.golangci.yml:34-113`.

3. **Модулей в ADR четыре, а в коде больше. Правила обновлялись?**
   Ответ: Да. С ADR 006 появился модуль identity, и в depguard добавлены правила для него и запрет на импорт identity из остальных модулей. С ADR 012 отдельное правило запрещает продуктовому коду импортировать мок платёжного провайдера; тестам и самому моку можно.
   Источник: `.golangci.yml:48-56, 66-67, 77-78, 88-100, 112-113`; ADR 012:31.

4. **Почему не разнести модули по отдельным Go-модулям? Тогда границы держал бы компилятор.**
   Ответ: Да, границы стали бы жёсткими. Но у каждого модуля появились бы свои версии, директивы `replace` и сложная сборка. Бинарь один, и линтер даёт ту же гарантию по импортам без этой цены.
   Источник: ADR 004:21.

5. **Почему не testcontainers?**
   Ответ: Это новая зависимость и Docker внутри тестов. В CI зависимости уже подняты service-контейнерами, локально их поднимает `make infra-up`. Решение принято «на текущем этапе» и может быть пересмотрено.
   Источник: ADR 004:23; `ci.yml:45-79`; `Makefile:48-49`.

6. **Что проверяет задача Compose и почему она нужна отдельно от тестов?**
   Ответ: Она поднимает весь проект с нуля через `docker compose up --build --wait`, проверяет `/healthz` и `/readyz` и доставку тестового сообщения до worker. Сейчас она ещё проверяет сайт, Prometheus и Grafana. Только эта задача проверяет пункт DoD «`docker compose up` поднимает проект с нуля». Она самая долгая: сборка образов и старт всех сервисов.
   Источник: ADR 004:17, 29; `ci.yml:163-236`.

7. **Что будет, если запустить `make test` без инфраструктуры?**
   Ответ: Интеграционные тесты пропустятся, остальные пройдут. Поэтому `make test` работает без инфраструктуры, а полную проверку дают `make test-integration` и CI. В ADR упомянут `RABBITMQ_TEST_URL`; сейчас так же пропускаются тесты без `DATABASE_TEST_URL`, `REDIS_TEST_ADDR` и `S3_TEST_ENDPOINT`.
   Источник: ADR 004:28; `Makefile:63-68`; evidence.md, «Границы доказательства», :397.

8. **Что линтер и CI не гарантируют?**
   Ответ: depguard видит только Go-импорты. Запросы booking читают таблицы `events` и `tickets` напрямую, база общая. `cmd/api` и `cmd/worker` импортируют все модули: это точка сборки, правила на неё не распространяются. Промежуточные коммиты могут остаться непроверенными: CI берёт последний коммит push, а `cancel-in-progress` отменяет прогон предыдущего push той же ветки.
   Источник: `.golangci.yml:38-113`; `internal/booking/queries.sql:3-5, 202-210`; `cmd/api/main.go:27-39`; evidence.md:80; ci.yml:10-12.

## Где слабое место

- **Граница только по импортам.** SQL-запросы модуля могут читать чужие таблицы, и линтер этого не видит (`internal/booking/queries.sql:3-5, 202-210`). ADR 007 пишет, что границы действуют и на уровне SQL, потому что у каждого модуля свой сгенерированный пакет (ADR 007:12). Это верно для Go-кода запросов, но не для таблиц. Почему приемлемо: общая база держит инвариант одной транзакцией (ADR 021:47). Что дальше: при выносе модуля чтения чужих таблиц заменяются вызовом или событием.
- **Точка сборки без правил.** `cmd/api` и `cmd/worker` импортируют все модули (`cmd/api/main.go:27-39`; `cmd/worker/main.go:23-31`). Так задумано: модули связываются только здесь. Ответ: доменная логика в `cmd/` не живёт, там только сборка и адаптеры вроде `cmd/api/objectstore.go`.
- **Чувствительность depguard не зафиксирована.** Намеренного нарушения с упавшим CI в репозитории нет. Ответ: проверку легко повторить: добавить импорт `internal/booking` в catalog и запустить `make lint`.
- **Отменённые прогоны.** `cancel-in-progress` экономит время, но промежуточные коммиты могут остаться без тестов (evidence.md:80; ci.yml:10-12). Ответ: в main попадает PR целиком, а по правилам проекта PR сливается с зелёным CI (CLAUDE.md, «Как работаем»); обязательную проверку настройками репозитория эти файлы не показывают.
- **Локальный зелёный `make test` мало значит.** Без переменных окружения интеграционные тесты пропускаются (evidence.md:397). Полную картину дают `make test-integration` и CI.
