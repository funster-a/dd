# ADR 005. Модель данных

Статус: принято, 2026-09-28

## Контекст

Бизнес-решения (`docs/spec.md`): покупатель входит по телефону и SMS-коду без регистрации, организатор — отдельный арендатор, секции без мест продаются как виртуальные места, заказ, платёж, возврат и билет живут по статусным моделям. Главный инвариант — место не продаётся дважды ни при какой конкурентности. Эксперимент сравнит три стратегии захвата места (`SELECT FOR UPDATE`, версия строки, Redis), и схема должна поддерживать все три без переделки.

Схема — `migrations/00002_core_schema.sql`.

## Решение

1. **Арендаторы в общей схеме, изоляция — составными ключами.** У всех данных организатора есть `organizer_id`. Ссылки между ними идут парами `(organizer_id, id)`, поэтому событие не может сослаться на зал чужого организатора, а заказ — на место чужого события: база отвергнет такую запись. Внутри события связи тоже составные, `(event_id, id)`: позиция заказа ссылается только на место того же события, возврат — только на платёж своего заказа, а билет — на то же место и тот же заказ, что и позиция, по которой он выпущен.
2. **Главный инвариант держит база:** частичный уникальный индекс `tickets (event_seat_id) WHERE status IN ('issued', 'used')`. Какая бы стратегия ни захватила место и что бы ни случилось с Redis, второй действующий билет на место не вставится. Отозванный при возврате билет освобождает место для новой продажи.
3. **Места события — строки таблицы `event_seats`.** Схема зала из редактора хранится документом `seat_maps.layout` (jsonb). При публикации события из него генерируются строки мест, так что правка схемы не меняет уже опубликованные события. Виртуальное место — это строка с `kind = 'general'` без ряда. Уникальность позиции проверяется с `NULLS NOT DISTINCT`, иначе виртуальные места с `row_label = NULL` не считались бы одинаковыми.
4. **Поля для всех трёх стратегий захвата.** `status` (`available`, `held`, `sold`), `hold_order_id` и `hold_expires_at` используют стратегии в PostgreSQL, `version` — оптимистичная блокировка. При стратегии на Redis холд живёт только в Redis, а строка сразу переходит в `sold`. Какая стратегия пойдёт в продукт, решит эксперимент (январь).
5. **Покупатель — телефон в формате E.164**, общий для всех организаторов. SMS-коды хранятся в Redis с TTL, в базе их нет. Email хранится в заказе: он нужен для доставки, а не для идентификации.
6. **Идемпотентность хранится в базе.** В `idempotency_keys` лежат ключ, хеш запроса и сохранённый ответ изменяющих эндпоинтов, в `payment_webhook_events` — идентификаторы уже полученных уведомлений шлюза. Повтор отсекается первичным ключом.
7. **Соглашения.**
   - Ключи — `uuidv7()`, встроенный в PostgreSQL 18: упорядочены по времени, поэтому индекс по ключу растёт в конец, как у последовательности, а идентификатор нельзя угадать.
   - Деньги — `bigint` в тиынах.
   - Время — `timestamptz`.
   - Статусы — `text` с `CHECK`.
   - Инварианты статусов (`paid` ⇔ есть `paid_at`, `held` ⇔ заполнены поля холда) записаны как `CHECK`.
   - Цена фиксируется в позиции заказа на момент покупки.
8. **Тесты схемы на временной базе.** `internal/platform/db/dbtest` создаёт отдельную базу на каждый тест, применяет миграции через ядро goose (миграции встроены в бинарь через `embed`) и удаляет базу после теста. Для этого в `go.mod` добавлены ядро goose и три его небольшие зависимости. Драйверы других СУБД по-прежнему только в `tools.mod`.

## Альтернативы

- **Отдельная схема или база на каждого арендатора.** Изоляция сильнее, но миграции приходится катить по N схемам, пул соединений дробится, а общий покупатель на несколько организаторов усложняется. Для 20–50 организаторов это лишняя эксплуатационная нагрузка. Отклонено.
- **Row Level Security как основная изоляция.** Требует выставлять арендатора в каждой сессии и мешает сквозным запросам (например, покупатель смотрит свои билеты у разных организаторов). Составные ключи защищают целостность без этого. RLS можно добавить позже как второй рубеж.
- **Места только в JSON-документе схемы.** Строку места нельзя заблокировать и нельзя повесить на неё уникальный индекс: стратегии захвата и инвариант пришлось бы реализовывать в приложении. Отклонено.
- **Счётчик вместимости для секций без мест.** Экономит строки, но даёт вторую механику продажи рядом с местами, а эксперимент сравнивал бы разные вещи. При 100–3000 мест строки ничего не стоят. Отклонено.
- **Enum-типы PostgreSQL для статусов.** Строже, но добавление и особенно удаление значения требует отдельных приёмов в миграциях. `text` с `CHECK` меняется одной строкой. Отклонено.
- **bigserial или UUID v4.** bigserial раскрывает объём продаж и неудобен при выносе модулей в отдельные сервисы. UUID v4 случаен и фрагментирует индекс. UUID v7 не имеет обоих недостатков.

## Следствия

- Двойную продажу места невозможно создать даже ошибкой в коде: это проверяет тест, где 50 транзакций одновременно выпускают билет на одно место и выпуск удаётся ровно у одной. Без индекса выпускаются все 50, и тест падает.
- Каждый запрос приложения обязан фильтровать по `organizer_id`. Составные ключи не дают записать чужие данные, но от чтения чужих данных защищает только код. Это правило для слоя запросов (sqlc) и кандидат на RLS.
- Генерация мест при публикации — задача модуля catalog (декабрь). Срок холда и освобождение мест — задача модуля booking (январь).
- Сумма возвратов не больше суммы платежа проверяется в транзакции с блокировкой строки платежа. В схеме это не выражается без триггера, триггер сознательно не используем.
