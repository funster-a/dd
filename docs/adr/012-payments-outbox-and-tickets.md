# ADR 012. Оплата, события между модулями и билеты

Дата: 2026-09-29. Статус: принято.

## Контекст

После холда (ADR 011) заказ нужно оплатить, выпустить билеты и вернуть деньги, если оплата опоздала. Ограничения:
- правило 7 CLAUDE.md: только песочница, никаких реальных ключей и карточных данных;
- правило 3: вебхуки идемпотентны;
- spec.md: между оплатой и выпуском билета стоит очередь, потому что шлюз отвечает медленно и иногда дважды.

Бизнес-решения 2026-09-29:
- карта вводится только на странице провайдера;
- в MVP работаем с моком провайдера;
- билет — страница по ссылке с QR, без PDF.

## Решение

### Провайдер и его мок

Платформа не принимает карточные данные. Покупатель уходит на страницу оплаты провайдера, результат приходит подписанным вебхуком (hosted payment page). Приложение не попадает в область PCI DSS. Самостоятельный приём карт потребовал бы полной сертификации, и в дипломе это не обосновать.

Провайдер скрыт за интерфейсом `payment.Gateway`. В MVP реализация одна — `PSPClient` для протокола мока `fakepsp`.

`fakepsp` — отдельный сервис (`cmd/fakepsp`, в Compose свой контейнер) с поведением настоящего провайдера:
- REST API с ключом;
- идемпотентное создание платежа и возврата по нашему id;
- своя страница оплаты;
- вебхуки с подписью HMAC-SHA256 и повторами при неудаче.

На странице только кнопки «Оплатить», «Отказать» и «Оплатить, уведомление придёт дважды». Поля для карты нет. Продуктовый код не импортирует мок, это проверяет depguard.

### Оплата

- У заказа одна действующая попытка оплаты. Это держит частичный уникальный индекс (миграция 00008). Повторный запрос возвращает ту же страницу.
- Если провайдер недоступен, попытка остаётся `created`, и следующий запрос создаёт её у провайдера тем же id. Провайдер вернёт уже созданный платёж.
- Попытка закрывается как `failed` только при явном отказе провайдера (4xx).
- Если оплата уже прошла, новая попытка не создаётся, даже пока заказ ещё ждёт подтверждения через очередь.
- Вебхук записывается в `payment_webhook_events`. Первичный ключ `(provider, event_id)` отсекает повторную доставку. Статус платежа, запись вебхука и событие `payment.succeeded` меняются в одной транзакции.
- Платёж ищется по нашему id из уведомления (`merchant_payment_id`), а не по id провайдера. Так находится и попытка, чей ответ о создании потерялся из-за сбоя связи.

### События между модулями: transactional outbox

Модули не вызывают друг друга. Изменение данных и событие о нём записываются одной транзакцией в таблицу `outbox`. Релей в worker публикует события в RabbitMQ с подтверждением брокера и помечает их опубликованными.

| Событие | Кто пишет | Кто обрабатывает | Что происходит |
|---|---|---|---|
| `payment.succeeded` | payment (вебхук) | booking | заказ `paid`, места `sold`, пишется `order.paid`; либо заказ закрыт и пишется `refund.requested` |
| `order.paid` | booking | ticket | выпуск билетов, письмо со ссылками |
| `refund.requested` | booking | payment | возврат у провайдера |

Гарантии доставки:
- **Хотя бы один раз.** Все обработчики идемпотентны:
  - заказ уже `paid` — ничего не делается;
  - `order_item_id` у билета уникален;
  - возврат за позднюю оплату один на платёж (миграция 00008), и у провайдера тот же ключ.
- **Сбой обработчика.** Worker повторяет обработку дважды с паузой. Потом сообщение уходит в очередь `<имя>.dead` для разбора, а не пропадает.
- **Параллельная публикация.** Несколько релеев не публикуют одно событие одновременно (`FOR UPDATE SKIP LOCKED`).

Контракты событий (имена и содержимое) лежат в `internal/platform/events`, потому что модули не импортируют друг друга. Модуль читает чужие таблицы только на чтение и только связанные внешними ключами: payment читает заказ, ticket — позиции заказа. Меняет данные только модуль-владелец.

### Оплата после истечения холда

Решает момент подтверждения оплаты платформой (`paid_at` в событии), а не момент обработки события. Иначе задержка очереди отменяла бы вовремя оплаченные заказы.

Заказ оплачен, если выполнены три условия:
- подтверждение пришло до `expires_at`;
- сумма совпала с суммой заказа;
- все места всё ещё за заказом. Место с истёкшим холдом мог перехватить другой покупатель.

Места продаются только все сразу. Во всех остальных случаях заказ не восстанавливается (spec.md), а деньги возвращаются автоматически.

Тест гоняет подтверждение оплаты против фоновой очистки: у каждого заказа ровно один согласованный исход. Либо заказ `paid` и места `sold`, либо он `expired` и запрошен возврат.

### Билеты

- Билет — строка `tickets` на каждую позицию оплаченного заказа. Частичный уникальный индекс не даёт выпустить второй действующий билет на место, это последний рубеж главного инварианта.
- Ссылка `/t/{token}`. Токен — id билета и 16 байт HMAC-SHA256 от него, base64url. Подделать ссылку нельзя, хранить токен не нужно.
- QR кодирует ту же ссылку. Камера телефона открывает страницу билета, сканер контролёра (следующий этап) берёт токен из ссылки.
- QR рисует `rsc.io/qr`: маленькая библиотека без зависимостей. Рисовать QR самим — сотни строк кода коррекции ошибок.
- Письмо уходит после коммита и только при первом выпуске. В разработке оно пишется в лог, как код входа.

## Альтернативы

- **Своя страница с вводом карты.** Отвергнута: PCI DSS, правило 7.
- **Песочница реального провайдера сейчас.** Нужны договор или тестовый доступ. Мок даёт то же поведение и позволяет воспроизводить сбои для защиты: двойное уведомление, недоступность провайдера, опоздавшая оплата. Реальный провайдер подключается реализацией `Gateway`.
- **Синхронные вызовы между модулями из обработчика вебхука.** Проще, но вебхук ждал бы выпуска билетов, а сбой посередине оставлял бы заказ полуобработанным.
- **Публикация в RabbitMQ прямо из транзакции.** Сообщение уходит, а транзакция откатывается, или наоборот. Outbox убирает этот разрыв.
- **PDF-билет.** Сложнее и не нужен для входа по QR. Отложен.

## Следствия

- Новый сервис `fakepsp` в Compose и новые переменные: `PUBLIC_BASE_URL`, `PSP_*`, `PAYMENT_CALLBACK_URL`, `TICKET_SIGNING_KEY`, `QUEUE_PREFIX`. Значения по умолчанию годятся только для разработки.
- Бесплатные заказы (сумма 0) пока не оформляются: у платежа сумма должна быть положительной. Появятся, когда понадобятся бизнесу.
- Если провайдер отклонил возврат, возврат помечается `failed`, а сообщение уходит в dead letter. Такие случаи разбираются вручную.
- Остаётся узкое окно: вебхук об успехе может прийти ровно между проверкой «оплата уже прошла» и созданием новой попытки. Тогда второе уведомление об успехе упрётся в индекс «одна успешная оплата» и будет доставляться повторно. Этот случай заметен в логах и требует ручного возврата.
