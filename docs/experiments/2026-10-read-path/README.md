# Эксперимент: нагрузка на ведущий узел PostgreSQL при старте продаж

Дата: 2026-10-06. Решение по итогам — [ADR 031](../../adr/031-read-path.md).

## Вопрос

Этап 5 плана развития (spec.md) — читающий контур. Ведущий узел PostgreSQL один, все заказы идут через него, и на штурме стадиона он упирался первым (ADR 023, ADR 026).

Вопросы:
- на что он тратит время в момент старта продаж;
- сколько снимают с него реплики и кэш на краю.

## Как мерили

Серия `loadtest/readpath.sh`:
- **Кластер.** PostgreSQL из трёх узлов (ADR 028): ведущий и две реплики, с `pg_stat_statements`.
- **Приложение.** Два экземпляра api за nginx.
- **Штурм.** Концерт на Центральном стадионе (33 509 мест), 5 000 покупателей, очередь 150 в секунду — лучший вариант ADR 026. Путь покупателя — как в ADR 026: страница события, очередь, сводка по секторам, сектор, заказ, при отказе снова.
- **Метрики:**
  - процессорное время каждого узла PostgreSQL за прогон (cgroup контейнера) — главная;
  - тяжёлые запросы ведущего узла;
  - путь покупателя;
  - инвариант.
- **Варианты, каждый добавляет одно изменение к предыдущему:**
  1. **до** — api из main, база без индекса этапа (миграции откатываются до 00018);
  2. **запросы исправлены** — счётчик одной фан-зоны и индекс выбора мест зоны;
  3. **+ чтения с реплик** — `DATABASE_REPLICA_URL`;
  4. **+ кэш на краю** — nginx держит публичные GET по `Cache-Control`.

По 2 прогона на вариант. Таблицы — [`tables.md`](tables.md).

## Результаты

| Вариант | Ведущий узел, с CPU | Реплики, с CPU | Заказ p95 | Сектор p95 | Сводка p95 | Купили | Двойных броней |
|---|---:|---:|---:|---:|---:|---:|---:|
| До: сборка из main | **73,6** | 13,7 | 6,0 с | 3,2 с | 2,5 с | 4 985 | 0 |
| Запросы исправлены | **38,1** | 15,0 | 1,0 с | 0,5 с | 0,4 с | 4 948 | 0 |
| + чтения с реплик | **29,2** | 25,7 | 1,5 с | 0,5 с | 0,4 с | 4 982 | 0 |
| + кэш на краю | **30,4** | 22,0 | 0,9 с | 0,2 с | 0,2 с | 4 994 | 0 |

Время работы реплик без нагрузки — около 7 секунд CPU на узел за прогон: столько стоит сама потоковая репликация.

## Разбор

**Профиль первым делом.** До изменений ведущий узел тратил время не на чтения:

| Запрос | До | После исправления | Что это |
|---|---:|---:|---|
| `HoldGeneral` | 681 с | 10 с | Взять N мест фан-зоны при заказе |
| `CountGeneralAvailable` | 274 с | 2 с | Счётчик всех фан-зон на каждое открытие сектора |
| Все чтения занятости и событие для очереди | около 35 с | уходят на реплики | |

Время — суммарное время выполнения вместе с ожиданием блокировок.

**Два запроса — половина нагрузки ведущего узла.**
- `HoldGeneral` брал первые свободные места фан-зоны по `id`, а индекс не покрывал порядок. База сортировала все свободные места зоны — шесть тысяч строк — на каждый заказ, держа блокировки, и параллельные заказы ждали друг друга. С `id` в частичном индексе первые места читаются по порядку: в 65 раз быстрее.
- `CountGeneralAvailable` считал свободные места всех фан-зон на каждое открытие любого сектора, хотя сектору нужна только своя зона. Теперь в режиме сектора считается одна зона по индексу свободных мест; полный подсчёт остался только для сводки, которая секунду живёт в памяти api.
- Итог: ведущий узел — **73,6 → 38,1 секунды CPU (−48%)**, заказ p95 — **6,0 → 1,0 секунды**.

**Реплики снимают ещё четверть.**
- Занятость секторов, сводка и событие для опроса очереди (35 тысяч вызовов за прогон) ушли на реплики: **38,1 → 29,2 секунды** на ведущем.
- Реплики взяли эту работу: 15 → 25,7 секунды CPU на двоих.
- Заказ p95 немного вырос (1,0 → 1,5 с) — в пределах разброса двух прогонов: в кластере одна машина на всё, и нагрузка реплик идёт с тех же 4 vCPU.

**Кэш на краю разгружает реплики и ускоряет покупателя.**
- Занятость, одинаковая для всех, держится 2 секунды на балансировщике: сектор и сводка p95 — **0,5 → 0,2 секунды**, нагрузка реплик — 25,7 → 22 секунды.
- На ведущий узел кэш не влияет: его нагрузка — это уже заказы.

**Итог: −59% нагрузки на ведущий узел, заказ p95 в 6,7 раза быстрее.** Последняя покупка — на 35-й секунде во всех вариантах после исправления: столько нужно, чтобы пропустить 5 000 человек по 150 в секунду. Дальше упираемся в скорость очереди, а не в базу.

**Корректность не зависит от реплик.** Двойных броней — ноль во всех 8 прогонах. Реплика может показать место свободным на миллисекунды дольше, но заказ проверяет его на ведущем.

## Что нашли по дороге

1. **Узкое место — запись, а не чтение.** План этапа предполагал, что ведущий узел разгрузят реплики и кэш. Профиль показал, что 80% его времени уходит на два запроса фан-зон, один из которых — запись. Без профиля реплики сняли бы около 5%.
2. **Все экземпляры api читали с одной реплики.** pgx подключается к первому подходящему хосту из списка. Теперь порядок перемешивается при старте экземпляра. С двумя экземплярами и двумя репликами оба экземпляра иногда всё равно выбирают одну — в этой серии так вышло в трёх прогонах из четырёх; с ростом числа экземпляров распределение выравнивается.
3. **Лимит соединений балансировщика.** Первая серия упёрлась в стандартный лимит nginx: 5 000 покупателей держат соединения одновременно, и балансировщик рвал их (обрывы на опросе очереди). Лимит поднят до 16 384 на процесс и в Compose (`deploy/nginx/nginx.conf`), серия перемерена.

## Ограничения

- **Одна машина.** Узлы PostgreSQL, api, Redis и k6 — на 4 vCPU. Разгрузка ведущего узла видна, но и реплики, и k6 конкурируют с ним за те же ядра.
- **Предохранители Redis под нагрузкой машины.** В двух прогонах (по одному в вариантах 2 и 3) Redis не укладывался в бюджет 300 мс, очередь на секунды пропускала всех (ADR 020), и часть заказов получила «заказ уже оформляется». На нагрузку ведущего узла это почти не влияет.
- **Кэш на краю — nginx, а не CDN.** Решение то же: кэшировать по `Cache-Control`, который ставит api. CDN снял бы и сами запросы до балансировщика.
- **Два прогона на вариант.**
