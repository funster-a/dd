# ADR 031. Читающий контур: сначала профиль, потом реплики и кэш на краю — разбор к защите

Неделя 8 (30.11–06.12.2026). ADR: [`docs/adr/031-read-path.md`](../../adr/031-read-path.md).

## Суть в трёх фразах

Ведущий узел PostgreSQL один, все заказы идут через него, и на штурме стадиона он упирался первым; план этапа предполагал разгрузить его репликами и кэшем, но сначала сняли профиль запросов. Профиль показал, что около 82 % времени ведущего уходит на два запроса фан-зон, причём один из них — запись: выбор мест сортировал всю зону, а счётчик считал все зоны на каждое открытие сектора; их исправили индексом (миграция 00019) и подсчётом одной зоны, а потом перевели чтения занятости на реплики и поставили перед api кэш nginx на месте CDN. Нагрузка на ведущий узел упала на 58–60 %, заказ p95 после исправления запросов — с 6,0 до 1,0 секунды, а корректность не пострадала: место по-прежнему проверяет транзакция заказа на ведущем.

Решение действует, позже не пересматривалось. Его дополнил ADR 032: в Kubernetes кэш на краю — отдельный Deployment с HPA, у каждого пода края свой кэш, поэтому с шестью подами в api придёт до шести запросов на адрес вместо одного (ADR 032:24, 83). Поды api край находит через headless Service (ADR 032:77-79).

## Почему так, а не иначе

- **Только реплики, без профиля.** Так предполагал план этапа. Профиль показал, что главная нагрузка — не чтения, а сортировка мест фан-зоны при заказе; без профиля реплики сняли бы только чтения — около 31 из 1 158 секунд, меньше 3 % (ADR 031:85; evidence.md:194).
- **Материализованные счётчики свободных мест.** Подсчёт стал бы бесплатным, но каждый заказ спорил бы за строку счётчика своей зоны — горячая точка там, где решается главный инвариант; тот же довод, что в ADR 026 (ADR 031:86).
- **Реплики для публичной страницы события.** Её кэш в Redis сбрасывается при смене обложек; отстающая реплика вернула бы в кэш старую страницу на 10 минут (ADR 031:45, 87).
- **Настоящий CDN.** На продакшене — да. На стенде ту же роль играет nginx с `proxy_cache`: решение то же — кэшировать по `Cache-Control`, который ставит api; подключение CDN не требует изменений в коде (ADR 031:88).
- **Чтения с реплик через прокси (pgpool-II, HAProxy).** Ещё один компонент и точка отказа. Список хостов в клиенте с чередованием даёт то же (ADR 031:89).

## Чем подтверждено

Эксперимент [`docs/experiments/2026-10-read-path`](../../experiments/2026-10-read-path/README.md): ведущий и две реплики PostgreSQL, два api за nginx, концерт на стадионе (33 509 мест), 5 000 покупателей, очередь 150 в секунду; четыре варианта по 2 прогона, каждый добавляет одно изменение (evidence.md:199).
- **Профиль:** два запроса фан-зон — ≈82 % времени ведущего по `pg_stat_statements` ((680,9 + 273,5) / 1 158,1) (evidence.md:194).
- **`HoldGeneral`:** 680,9 → 10,5 с за прогон, в 65 раз по сумме (evidence.md:192).
- **`CountGeneralAvailable`:** 273,5 → 1,6 с; новый `CountGeneralAvailableInSection` — 3,3 с (evidence.md:193).
- **Исправление запросов:** ведущий 73,6 → 38,1 с CPU (−48 %); заказ p95 6,0 → 1,0 с, сектор 3,2 → 0,5 с, сводка 2,5 → 0,4 с (evidence.md:187, 191).
- **Реплики:** ещё −22 % на ведущем (38,1 → 29,6 с CPU); реплики взяли работу почти поровну, в среднем 15 и 12 с CPU (evidence.md:189, 325); около 40,7 тысячи вызовов за прогон ушли с ведущего (evidence.md:195).
- **Кэш на краю:** нагрузка реплик 27 → 21 с CPU, сектор и сводка p95 0,3 с (evidence.md:190).
- **Итог:** ведущий −58…60 % (73,6 → 29,6 / 31,2 с CPU) (evidence.md:188).
- **Скорость задаёт очередь:** последняя покупка 35,1 / 35,4 / 35,3 с после исправления против 44,1 с до (evidence.md:196).
- **Корректность:** 0 двойных броней в 8 прогонах, из них 4 — с чтениями с реплик (evidence.md:72, 281).

Тесты:
- **Счётчик одной зоны в режиме сектора:** зона показывает 17 свободных, сектор с местами — ни одной зоны, сводка по-прежнему считает все зоны (`internal/booking/orders_test.go:716-743`).
- **Чтение с ведущего при недоступной реплике:** `QueryRow` и `Query` работают при мёртвой реплике, без реплики и с живой (`internal/platform/db/read_test.go:12-49`).
- **Чередование хостов:** три хоста дают три порядка перебора по кругу, ни один хост не теряется, записи одного хоста не разрываются (`internal/platform/db/shuffle_test.go:13-33`).

## Вопросы комиссии

1. **Что такое «читающий контур» и какую задачу решал этап?**
   Ответ: Этап 5 плана: публичные страницы и схемы — через кэш и CDN, остальные чтения — с реплики. До этапа страница события уже жила в Redis, сводка — секунду в памяти api, а занятость сектора, опрос очереди и список событий шли в ведущий узел. Цель — снять нагрузку с ведущего узла PostgreSQL, потому что все заказы идут через него, и на штурме стадиона он упирался первым.
   Источник: ADR 031:7-12.

2. **Что показал профиль?**
   Ответ: Около 82 % времени ведущего уходило на два запроса фан-зон. `HoldGeneral` — 680,9 секунды за прогон: он брал N мест зоны и сортировал все свободные места по `id`, потому что индекс не покрывал порядок. `CountGeneralAvailable` — 273,5 секунды: считал все фан-зоны на каждое открытие любого сектора. Параллельные заказы друг друга не ждали: `HoldGeneral` берёт строки с `SKIP LOCKED` (`internal/booking/queries.sql:56-65`), дорогой была сама сортировка на каждый заказ.
   Источник: ADR 031:14-21; evidence.md:192-194. В ADR для «до» указаны 689 и 277 с; верить `tables.md`, оттуда 680,9 и 273,5 (evidence.md:192-193).

3. **Как исправили выбор мест в фан-зоне?**
   Ответ: Миграция 00019 заменила частичный индекс свободных мест зоны `(event_id, section)` на `(event_id, section, id)`. Теперь первые N мест по `id` читаются по порядку индекса, без сортировки всей зоны — около шести тысяч строк на каждый заказ под блокировками. `HoldGeneral` — 680,9 → 10,5 с за прогон.
   Источник: ADR 031:28; `migrations/00019_general_pick_index.sql:8-10`; `internal/booking/queries.sql:53-62`; read-path/README.md:58.

4. **Какие чтения ушли на реплики, а какие остались на ведущем и почему?**
   Ответ: На реплики — занятость мест, событие для опроса очереди и список предстоящих событий. На ведущем — проверки и запись заказа, потому что решение о месте принимает только ведущий в транзакции; свой заказ покупателя, потому что реплика отстаёт и только что созданный заказ мог бы «пропасть»; публичная страница, потому что её кэш получил бы старые обложки.
   Источник: ADR 031:32-45; `internal/booking/strategy.go:45-47`; `internal/catalog/organizers.go:43-47`.

5. **Реплика отстаёт. Не продаст ли это место дважды?**
   Ответ: Нет. Реплика может показать место свободным на миллисекунды дольше, но заказ проверяет место на ведущем. Покупатель получит «место занято», как если бы место заняли через секунду после загрузки сектора. В 8 прогонах — 0 двойных броней, в 4 из них чтения шли с реплик.
   Источник: ADR 031:47; evidence.md:72.

6. **Что будет, если реплики упадут?**
   Ответ: `db.Reader` читает с реплики, а при её недоступности — с ведущего: отказ реплик возвращает нагрузку, но не ломает страницы. В `/readyz` реплика — необязательная проверка, так что экземпляр api из ротации не выводится. Тест проверяет чтение при мёртвой реплике.
   Источник: ADR 031:37-40; `internal/platform/db/read.go:40-74`; `cmd/api/main.go:227-229`; `read_test.go:12-49`.

7. **Зачем чередовать хосты на каждом соединении?**
   Ответ: pgx подключается к первому подходящему хосту из списка. Сначала порядок перемешивался один раз на экземпляр, и оба api выбирали одну реплику во всех четырёх прогонах. Теперь каждое новое соединение пула начинает перебор со следующего хоста; реплики нагружены почти поровну, в среднем 15 и 12 секунд CPU.
   Источник: ADR 031:39; `internal/platform/db/db.go:27-45`; read-path/README.md:77; evidence.md:325.

8. **Как работает кэш на краю и почему nginx, а не CDN?**
   Ответ: nginx-балансировщик держит публичные GET столько, сколько разрешает `Cache-Control` ответа api: страница события — 60 секунд, занятость — 2. Одновременные промахи идут в api одним запросом. Устаревший ответ обновляет первый запрос и сам ждёт api, пришедшие за это время получают прежний: после паузы ответ свежий, а в api по-прежнему один запрос. Если api отвечает 5xx или молчит дольше 30 секунд, край отдаёт прежний ответ. На другой экземпляр запрос повторяется только при ошибке соединения, в первые 3 секунды, а в Kubernetes медленное чтение не выводит под из записи (исправление 19.10.2026 в конце ADR). Решение то же, что у CDN, и CDN подключается без изменений в коде; на стенде его роль играет nginx.
   Источник: ADR 031:51-59, 88; `deploy/nginx/api-lb.conf:27-47`; `internal/catalog/http.go:51`; `internal/booking/http.go:53`.

9. **Какие итоговые числа?**
   Ответ: Ведущий узел — 73,6 секунды CPU за прогон до, 38,1 после исправления запросов, 29,6 с репликами и 31,2 с кэшем на краю: минус 58–60 %. Основной вклад — исправление запросов, минус 48 %. Заказ p95 после исправления запросов — с 6,0 до 1,0 секунды; ADR называет эти прогоны «чистыми», но и в них предохранитель срабатывал: 3 и 2 раза в «До», 18 раз во втором прогоне «Запросы исправлены». Последняя покупка — на 35-й секунде: дальше скорость задаёт очередь, а не база.
   Источник: ADR 031:67-81; evidence.md:187-188, 191, 196.

10. **Что в этом решении не доказано?**
    Ответ: Время ответа в вариантах с репликами и кэшем нельзя сравнивать с первыми двумя: на перегруженной машине срабатывал предохранитель Redis. Настоящий CDN не мерили. Купили не все: 4 838–4 985 из 5 000 в среднем на прогон. Всё на одной машине, по 2 прогона на вариант.
    Источник: evidence.md:191, 197, 387, 414-415.

## Где слабое место

- **Варианты 3–4 зашумлены** (evidence.md:191, 414). Предохранитель Redis срабатывал до 130 раз за прогон, и очередь на секунды пропускала всех; заказ p95 3,0 и 1,8 с (read-path/README.md:83-90). Ответ: главная метрика этапа — CPU ведущего — от этого почти не зависит, заказов столько же. Сравнивать время ответа можно только внутри вариантов 1–2, и они тоже не совсем чистые: во втором прогоне «Запросы исправлены» 18 срабатываний и 607 отказов (evidence.md:191).
- **Не все купили билеты** (evidence.md:197). Ответ: потери объяснены тем же предохранителем — отказы «заказ уже оформляется» точно следуют за срабатываниями; в штурме ADR 026 при той же очереди купили все 5 000.
- **Расхождения ADR с таблицами.** ADR даёт 689 и 277 с «до», `tables.md` — 680,9 и 273,5; «274 → 2» в ADR не учитывает новый запрос на 3,3 с; «около 35 секунд» остальных чтений в ADR 031:21 осталось, а в README исправлено на ≈31 (evidence.md:192-193, 348). Ответ: числа брать из `tables.md` и реестра, вывод от этого не меняется.
- **CDN не мерили** (evidence.md:415). Ответ: nginx на стенде делает то же по тем же заголовкам; CDN снимет ещё и запросы до балансировщика.
- **С кэшем на краю ведущий нагружен чуть больше, чем без него** (31,2 против 29,6 с) (evidence.md:188). Ответ: кэш разгружает реплики, а не ведущий: нагрузка ведущего — уже заказы; разница — шум стенда.
- **Отставание данных складывается.** Сводка живёт секунду в памяти api и 2 секунды на краю; реплика добавляет миллисекунды. Ответ: это вывод из настроек, отдельно не измерялся; корректность не зависит, место проверяет заказ.
- **Одна машина, 2 прогона на вариант** (evidence.md:385, 387). Ответ: сравниваются только варианты одной серии. Реплики и k6 конкурируют с ведущим за те же ядра (read-path/README.md:82); на отдельных серверах не проверяли.

## Проверь себя

1. Почему реплики без исправления запросов сняли бы меньше 3 % времени ведущего? Объясните через то, какой из двух тяжёлых запросов — запись.
2. Покупатель только что оформил заказ и открыл «Мои заказы». Откуда читается этот список и что случилось бы, если бы его читали через `db.Reader`?
3. В Kubernetes шесть подов края, занятость кэшируется 2 секунды. Сколько запросов занятости одного сектора в секунду дойдёт до api и до реплик при 5 000 одновременных покупателей?
