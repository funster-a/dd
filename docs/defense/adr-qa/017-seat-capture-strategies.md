# ADR 017. Стратегии захвата места: эксперимент и выбор для продукта — разбор к защите

Неделя 5 (09–15.11.2026). ADR: [`docs/adr/017-seat-capture-strategies.md`](../../adr/017-seat-capture-strategies.md).

## Суть в трёх фразах

Спецификация требует сравнить три способа захватить место при конкурентном доступе: пессимистичную блокировку строки, оптимистичную блокировку по версии строки и атомарный захват в Redis перед базой. Все три сделаны за одной настройкой `BOOKING_STRATEGY` и измерены нагрузочным экспериментом: двойных броней ноль в 63 прогонах, а Redis + БД быстрее обеих стратегий «только база» на всех уровнях нагрузки. В продукте осталась Redis + БД с предохранителем: при отказе Redis захват сразу идёт через базу, а эксперимент с отказом нашёл вторую зависимость от Redis — проверку сессий, её закрыл ADR 018.

Выбор стратегии действует до сих пор. Позже часть механизма изменили:
- ADR 018: исправление сессий, которое ADR 017 предлагал (кэш на 30–60 с всегда), не принято. Выбран кэш только на случай отказа Redis, на 10 минут (ADR 018:19-25, 51). Предохранитель вынесен в общий `internal/platform/redis.Gate` (ADR 018:27);
- ADR 023: предохранитель стал полуоткрытым. Пока он открыт, раз в 100 мс один запрос проходит в Redis пробой, удачная проба закрывает его сразу (ADR 023:36-49; `internal/platform/redis/gate.go:21-25, 55-86`). Фиксированные 5 секунд без проб превращали короткую задержку в 5 секунд отказов (ADR 023:38-42);
- ADR 029: Redis пишет журнал (AOF), а стенд `deploy/ha` добавляет Sentinel с двумя репликами; там запись снова доступна через 3 секунды (ADR 029:30-31, 42-47). Это не меняет стратегию, но сокращает время, когда фильтр выключен.

## Почему так, а не иначе

- **Оптимистичная стратегия в продукте.** Не требует Redis и почти не уступает при малой нагрузке. Но на пике медленнее Redis + БД в 1,7 раза (p95 на одном месте, 5 000 покупателей), а Redis в стеке уже есть для холдов с TTL по правилу 2 (ADR 017:79; evidence.md:52).
- **Пессимистичная в продукте.** Самая медленная на пике: p95 8 071 мс на одном месте при 5 000 покупателях (evidence.md:49). Остаётся режимом работы при отказе Redis: `HoldSeats` и есть путь Redis + БД без фильтра (ADR 017:80).
- **Только Redis, без проверки в базе.** Быстрее, но истина о брони оказалась бы в Redis, что нарушает правило 2, а рассинхрон при потере Redis пришлось бы разбирать отдельно. ADR 011 это уже отверг, а эксперимент показал, что проверка в базе после фильтра стоит немного (ADR 017:81).
- **SERIALIZABLE вместо явных блокировок.** Не входил в спецификацию эксперимента. Даёт те же откаты, что оптимистичная стратегия, но без контроля над повтором (ADR 017:82).
- **Эксперимент на отдельных машинах для k6 и api.** Честнее для абсолютных чисел, но у дипломного проекта один стенд. Сравнение стратегий на одном стенде корректно (ADR 017:83).

## Чем подтверждено

Тесты с параллельными горутинами (подтест `redis` создаётся только при `REDIS_TEST_ADDR`, `internal/booking/strategy_test.go:15-22`):
- **200 покупателей на одно место для каждой стратегии:** 1 успех, 199 `seat_taken`, затем проверка инварианта по данным. `TestStrategiesSameSeat`, `strategy_test.go:46-83`; evidence.md:87.
- **60 покупателей на случайные наборы по 3 из 12 мест:** ни одно место не попало в два заказа, успешных заказов 1–4. `TestStrategiesOverlappingSeats`, `strategy_test.go:85-121`; evidence.md:89.
- **Повтор при конфликте версий:** чужая транзакция меняет строку места, заказ повторяется и проходит, счётчик повторов растёт. `TestOptimisticRetriesOnVersionConflict`, `strategy_test.go:140-180`.
- **Триггер версии:** любое изменение места увеличивает `version` на 1. `TestSeatVersionTrigger`, `strategy_test.go:123-138`; `migrations/00012_seat_version.sql:9-20`.
- **Предохранитель:** первый вызов к мёртвому Redis укладывается в бюджет, следующий сразу получает `ErrGateOpen`, отмена запроса Gate не открывает; заказ при мёртвом Redis проходит через базу. `internal/booking/holds_test.go:12-68`.

Эксперимент ([`docs/experiments/2026-10-booking-strategies`](../../experiments/2026-10-booking-strategies/README.md)):
- **0 двойных броней в 63 прогонах:** 54 основных (3 стратегии × 500/2 000/5 000 покупателей × 3 повтора × 2 сценария) и 9 с отказом Redis (evidence.md:38-39).
- **p95 на одном месте при 500 / 2 000 / 5 000:** пессимистичная 882 / 3 123 / 8 071 мс, оптимистичная 722 / 2 578 / 5 711, Redis + БД 507 / 1 485 / 3 419 (evidence.md:49).
- **Захватов в секунду в зале на 1 000 мест:** пессимистичная 312 / 128 / 69, оптимистичная 333 / 153 / 68, Redis + БД 394 / 201 / 103 (evidence.md:54).
- **В Redis + БД все отказы отсекает Redis,** до базы доходит только победитель: `rejected_by_db = 0` (evidence.md:58).
- **У оптимистичной почти нет повторов:** 4–10 на 500 попыток при 500 покупателях, 0 при 5 000; в зале 0,11–1,54 % попыток (evidence.md:59).
- **Отказ Redis:** без предохранителя покупатели увидели успех у 178 из 864 созданных заказов; с предохранителем — 659 из 659; с кэшем сессий (ADR 018) — 984 места, 0 ошибок (evidence.md:299-300).

## Вопросы комиссии

1. **Что сравнивали и что выбрали для продукта?**
   Ответ: Три стратегии захвата места: пессимистичную блокировку, оптимистичную по версии строки и атомарный захват в Redis перед базой. Все три живут в коде за настройкой `BOOKING_STRATEGY`, остальной путь заказа одинаков. В продукте осталась Redis + БД: она быстрее на всех уровнях нагрузки, а корректность держит база.
   Источник: ADR 017, «Решение» (строки 20-26), «Продукт» (строка 62); `internal/booking/strategy.go:13-40`.

2. **Как работает оптимистичная стратегия и зачем понадобился триггер?**
   Ответ: Места читаются без блокировки вместе с версией строки, приложение проверяет статус, затем `UPDATE … WHERE version = $v`. Если обновилось меньше строк, транзакция откатывается и повторяется, до 4 попыток с растущей паузой и разбросом. Колонка `version` была в схеме с миграции 00002, но её никто не обновлял, поэтому версию теперь ведёт триггер при любом изменении места. Ручная мутационная проверка: без условия на версию одно место продаётся трижды, тест это ловит; в репозитории мутация не зафиксирована.
   Источник: ADR 017:26, 29, 31; `strategy.go:53-103`; `internal/booking/queries.sql:33-51`; `migrations/00012_seat_version.sql:9-20`; evidence.md:88.

3. **Гипотеза говорила о массовых откатах у оптимистичной стратегии. Почему она оказалась быстрее пессимистичной?**
   Ответ: Запросы доходят до базы через пул из 32 соединений, и к моменту чтения большинства победитель уже зафиксировал холд. Такой запрос видит «занято» и уходит сразу, без записи и без ожидания блокировки. Повторов 4–10 на 500 попыток при 500 покупателях и 0 при 5 000. На 5 000 покупателях p95 5 711 мс против 8 071 мс у пессимистичной.
   Источник: ADR 017:57; booking-strategies/README.md:82-86; evidence.md:49, 59.

4. **Насколько Redis + БД быстрее? Назовите числа.**
   Ответ: На одном месте при 5 000 покупателях p95 3 419 мс против 5 711 мс у оптимистичной и 8 071 мс у пессимистичной. В зале на 1 000 мест при 5 000 покупателях — 103 захвата в секунду против 68 и 69. ADR пишет «до 1,5 раза больше захватов», по ступеням выходит от 1,2 до 1,6 раза. Все отказы отсекает Redis, база видит только победителя.
   Источник: ADR 017:56; evidence.md:49, 54, 57, 58.

5. **Насколько честно сравнение?**
   Ответ: Стратегии «только база» не используют Redis для холдов вовсе. Пул соединений api задан явно, 32, одинаковый для всех. Каждая точка — 3 повтора, и после каждого прогона `loadseed check` проверял инвариант по данным. Первая серия прошла целиком на одной стратегии из-за занятого порта и выброшена; теперь скрипты проверяют, что попытки записаны нужной стратегией.
   Источник: ADR 017:28, 49, 91; `strategy.go:49-51`; booking-strategies/README.md:28, 139; evidence.md:297.

6. **Почему не хранить бронь только в Redis, раз он так быстр?**
   Ответ: Правило 2 требует, чтобы истина о брони была в PostgreSQL. Если бронь только в Redis, при его потере нужно разбирать рассинхрон. В выбранной схеме Redis не решает, продано ли место, а только отсекает заведомых проигравших, поэтому рассинхрона по построению нет. Цена проверки в базе небольшая: до неё доходит только победитель.
   Источник: ADR 017:81; booking-strategies/README.md:15, 92; evidence.md:58.

7. **Что происходит, если Redis падает посреди продаж?**
   Ответ: Первая версия ждала таймаутов клиента Redis по 3–4 секунды, запросы обрывались по `WriteTimeout`: база оформила 864 заказа, покупатели увидели успех у 178. После исправления у вызова Redis для холдов бюджет 500 мс, после ошибки фильтр выключается на 5 секунд и заказы идут в базу: 659 из 659 дошли до покупателя. С ADR 023 открытый предохранитель раз в 100 мс пропускает пробу и закрывается первой удачной, не дожидаясь 5 секунд. Оставшиеся ошибки дала проверка сессий, после ADR 018 — 984 места и 0 ошибок (прогон с прогревом сессий). Двойных броней не было ни в одном варианте.
   Источник: ADR 017:64-71; `internal/booking/holds.go:29-39`; booking-strategies/README.md:101-120; evidence.md:42, 43, 299-300; ADR 023:44-47; `internal/platform/redis/gate.go:55-64`.

8. **Почему задержка растёт даже у самой быстрой стратегии?**
   Ответ: У каждого заказа есть общий путь, одинаковый для всех стратегий: проверка сессии, ключ идемпотентности в базе и три чтения. На 4 vCPU рядом с k6, PostgreSQL и Redis этот путь становится пределом: p95 у Redis + БД 507 → 1 485 → 3 419 мс. Отсюда же одинаковые 68–69 захватов в секунду у стратегий «только база» на 5 000. Этот вывод стал основанием для очереди ожидания (ADR 020).
   Источник: ADR 017:58; booking-strategies/README.md:91; evidence.md:60; ADR 020:9.

9. **Почему не взять уровень изоляции SERIALIZABLE и не писать блокировки руками?**
   Ответ: SERIALIZABLE не входил в спецификацию эксперимента. Он даёт те же откаты, что оптимистичная стратегия, но повтор при ошибке сериализации не контролирует приложение. Это не измерялось. В текущем коде ошибки `40001` и `40P01` из базы превращаются в «место занято», а не в 500.
   Источник: ADR 017:82; `internal/booking/orders.go:463-465`; evidence.md:394.

10. **Что в этом эксперименте не доказано?**
    Ответ: Все сервисы и k6 работали на одной машине с 4 vCPU, поэтому абсолютные числа описывают стенд. Один процесс api и пул 32: с большим пулом оптимистичная получит больше повторов, это не измерялось. Отказ Redis проверен только для Redis + БД, сценария hall и 2 000 покупателей. Мутационная проверка с версией сделана вручную и в репозитории не зафиксирована.
    Источник: evidence.md:11, 392, 395, 397; booking-strategies/README.md:135-138.

## Где слабое место

- **Один стенд.** k6, api, PostgreSQL и Redis делили 4 vCPU (booking-strategies/README.md:35-38). Ответ: доказательную силу имеет сравнение стратегий внутри одной серии, а не абсолютные миллисекунды (evidence.md:11). Следующий шаг — повтор на отдельных машинах, ADR его прямо называет альтернативой (ADR 017:83).
- **Пул 32 и вывод про оптимистичную стратегию.** «Почти без повторов» — свойство этого пула: он растягивает приход запросов к базе (evidence.md:59). Ответ: ADR прямо связывает вывод с пулом (ADR 017:57), а отчёт уточняет, что гипотеза верна для другой нагрузки — большого пула и малой задержки (booking-strategies/README.md:86). Следующий шаг — серия с пулом больше 32.
- **Отказ Redis — одна конфигурация.** Только Redis + БД, hall, 2 000 покупателей; k6 не повторял запрос с тем же ключом (evidence.md:395). Ответ: корректность при отказе держит база, это проверено и в отдельном эксперименте ADR 029 — 15 прогонов без двойных броней (evidence.md:76).
- **Предохранитель с фиксированными 5 секундами оказался ошибочным.** На перегруженной машине одна медленная команда открывала его при здоровом Redis (evidence.md:303). Исправлено в ADR 023 полуоткрытым режимом: один экземпляр с пол-ядра при 400 заказах в секунду, p95 3 623 → 127 мс, по одному прогону до и после (evidence.md:128). Ответ: эксперимент ADR 017 этого не видел, при обычной нагрузке предохранитель не срабатывал (evidence.md:61).
- **Округление в ADR.** «До 1,5 раза больше захватов» занижает максимум 1,57, а «в 1,7 раза» — отношение p95 на одном месте; по другим метрикам иначе (evidence.md:52, 57). Ответ: называть метрику вместе с числом.
- **Мутационные проверки вручную.** «Без версии место продаётся трижды» в репозитории не зафиксировано (evidence.md:88, 397). Ответ: тест `TestStrategiesSameSeat` идёт на настоящем коде в CI; следующий шаг — закрепить мутацию отдельным тестом.
- **SERIALIZABLE не измерялся** (evidence.md:394). Ответ: не входил в спецификацию; для защиты достаточно трёх стратегий из spec.md.

## Проверь себя

1. В оптимистичной стратегии место уже держит действующий холд другого заказа. Будет ли повтор и почему — покажите по `strategy.go`.
2. Почему на 5 000 покупателях в зале у пессимистичной и оптимистичной стратегий почти одинаковая пропускная способность (69 и 68), хотя на одном месте их p95 заметно различается (8 071 и 5 711 мс)?
3. Redis вернулся через 2 секунды после отказа. Сколько заказов пройдёт без фильтра по ADR 017 и сколько после ADR 023?
