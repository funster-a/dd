# ADR 029. Отказ Redis: Sentinel с репликами и журнал на каждом узле

Дата: 2026-10-05. Статус: принято.

## Контекст

Этап 4 плана развития — отказоустойчивость. После api (ADR 027) и PostgreSQL (ADR 028) — Redis. Разбор — [`docs/experiments/2026-10-redis-failover`](../experiments/2026-10-redis-failover/README.md).

Что живёт в Redis:
- **холды мест** — фильтр перед базой: место продаёт база, Redis только отсекает проигравших конкурентов (ADR 011, ADR 017);
- **сессии** покупателей и организаторов (ADR 006);
- **одноразовые коды** входа;
- **очередь ожидания** при старте продаж (ADR 020).

Отказ Redis приложение уже переживает:
- холды и очередь при недоступности Redis пропускаются (предохранитель `redis.Gate`);
- знакомая сессия проверяется по кэшу в памяти api (ADR 018).

Но всё это держится, пока Redis недоступен. Эксперимент показал, что хуже всего не сам простой, а то, что Redis теряет, когда поднимается снова.

**Один Redis с настройками по умолчанию** (так было в Compose) пишет на диск только снимки (RDB): раз в 5 минут при 100 изменениях, раз в час при одном. Перезапуск после падения теряет всё со времени последнего снимка:
- сессии всех, кто вошёл перед продажей, — в эксперименте 12 тысяч из 18 тысяч покупателей получили `401 invalid_session`, сайт выкинул их из аккаунта, и купить они не смогли;
- очередь ожидания — пришедшие встают в неё заново, в конец;
- все холды — фильтр пуст, конкуренты идут прямо в базу.

## Решение

### Журнал на каждом узле

Redis пишет журнал операций (AOF) и сбрасывает его на диск раз в секунду (`appendonly yes`, `appendfsync everysec`). Перезапуск теряет не больше секунды записей.
- **Основной Compose:** включено для единственного узла.
- **Цена:** запись на диск раз в секунду; при нагрузке продаж это незаметно.

Только журнала мало. Один Redis с журналом в эксперименте никого не потерял, но 20 секунд простоя:
- покупатель ждал до 23 секунд — почти весь бюджет повторов сайта (30 с);
- новый вход и очередь ожидания всё это время не работали.

Сколько продлится простой, зависит от того, кто и как быстро поднимет узел.

### Sentinel и две реплики

`deploy/ha/docker-compose.redis-ha.yml` — три узла Redis с журналом и три Sentinel.
- **Роли.** Один ведущий, две реплики.
- **Переключение.** Ведущий не отвечает 2 секунды, двое из трёх Sentinel это подтверждают — они повышают реплику и переключают на неё остальные узлы. Вернувшийся бывший ведущий становится репликой.
- **Клиент.** api спрашивает адрес ведущего у Sentinel (go-redis `FailoverClient`) и сам переходит на новый: `REDIS_SENTINELS=host1:26379,host2:26379,host3:26379`, `REDIS_MASTER=dd`. Без `REDIS_SENTINELS` api подключается к одному адресу `REDIS_ADDR`, как раньше.

В эксперименте запись снова доступна через 2–3 секунды, и без билета не ушёл никто.

### Пауза на «хранилище сессий недоступно» — 2 секунды

Ответ `503 session_store_unavailable` советовал повторить через 5 секунд (ADR 018): тогда Redis был один, и простой длился, пока его не поднимут. С Sentinel простой — 2–3 секунды, и пауза в 5 заставляла покупателя ждать уже работающий Redis. Теперь `Retry-After: 2`, как у недоступной базы (ADR 028).

### Асинхронная репликация — допустимо

Реплики Redis всегда получают записи асинхронно. Ведущий, упав, уносит последние миллисекунды записей. Чем это грозит:
- **Холд.** Пропавший холд ослабляет фильтр: конкурента за это место отсечёт база, а не Redis. Лишний холд (снятие пропало) отказывает покупателям «место занято» до конца своего срока, хотя место в базе свободно. В эксперименте после переключения пропало 0–4 холда на прогон, лишних не было.
- **Сессия.** Вошедший за миллисекунды до падения войдёт снова.
- **Место в очереди ожидания.** Вставший в очередь за миллисекунды до падения встанет снова.

Ни один случай не продаёт место дважды и не теряет деньги: истина о бронях и оплате — в PostgreSQL (правило 2 CLAUDE.md). Поэтому синхронной записи (`WAIT`) на каждую операцию нет, в отличие от базы (ADR 028).

## Альтернативы

- **Redis Cluster.** Шардирование и переключение в одном. Нужен, когда данные не помещаются в один узел или один узел не справляется с нагрузкой. У нас ни то, ни другое: на штурме стадиона Redis не был узким местом (ADR 026). К тому же ключи холдов заказа должны лежать в одном слоте (`{eventID}` в ключе это уже обеспечивает).
- **Управляемый Redis с репликой** (у облачного провайдера). На продакшене предпочтительнее, если он есть: переключение то же, обслуживать его не нам. Код не меняется — тот же `FailoverClient` или один адрес, который провайдер переносит сам.
- **Только журнал, без реплик.** Корректно, но простой длится, пока узел не поднимут; на одной машине это десятки секунд, при потере машины — дольше.
- **Сессии в PostgreSQL.** Убирает потерю сессий совсем, но добавляет запрос в базу на каждый запрос (ADR 018). Журнал и реплики решают ту же проблему без нагрузки на базу.
- **Синхронная репликация (`WAIT 1`) для сессий.** Сессия не пропадёт даже за миллисекунды до падения, но каждый вход ждёт реплику. Потеря нескольких входов раз в много месяцев дешевле.

## Следствия

- **Код:** `REDIS_SENTINELS` и `REDIS_MASTER` в настройках, `redis.Open` выбирает клиент. `Retry-After: 2` на недоступность хранилища сессий.
- **Compose:** Redis пишет журнал.
- **Стенд:** `deploy/ha/docker-compose.redis-ha.yml`.
- **Нагрузочный стенд:** серия `loadtest/redischaos.sh`, сверка холдов Redis с базой `loadseed holds-check`, отчёт `loadseed redischaos-report`. Отчёты переключения PostgreSQL и Redis — общий код.
- **Ограничение эксперимента:** в потоке нет отмен и замен корзины, поэтому лишние холды от пропавших снятий он почти не создаёт. Механизм их появления и вред описаны выше; самовосстановление лишних холдов — кандидат на следующий шаг, если они появятся на продакшене (метрика — отказы Redis «место занято» при свободном месте в базе).
- **Дальше по этапу 4:** кластер RabbitMQ.
