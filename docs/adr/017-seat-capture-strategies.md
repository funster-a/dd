# ADR 017. Стратегии захвата места: эксперимент и выбор для продукта

Дата: 2026-10-01. Статус: принято.

## Контекст

spec.md («Инженерное ядро») требует сравнить три стратегии захвата места при конкурентном доступе:
- пессимистичную блокировку;
- оптимистичную блокировку;
- атомарный захват в Redis.

Нужно измерить двойные брони, p95 и p99, пропускную способность, долю откатов и поведение при отказе Redis. Для защиты — таблица, графики и обоснование, какая стратегия ушла в продукт.

ADR 011 ввёл продуктовую стратегию (Redis отсекает проигравших, PostgreSQL — истина) и оставил место для экспериментальных: шаг «держать места» в транзакции заказа.

## Решение

### Три стратегии за одной настройкой

`BOOKING_STRATEGY` у api выбирает стратегию. Весь остальной путь заказа одинаков.

| Значение | Как держится место с рядом |
|---|---|
| `redis` (по умолчанию) | Lua-скрипт в Redis атомарно ставит ключи мест заказа; затем `HoldSeats` — `SELECT … FOR UPDATE` в порядке id и условный `UPDATE` |
| `pessimistic` | только `HoldSeats`, без Redis |
| `optimistic` | `ReadSeatsForHold` без блокировки → проверка статуса в приложении → `HoldSeatsIfVersion`: `UPDATE … WHERE version = $v`; конфликт — откат всей транзакции и повтор, до 4 попыток с растущей паузой и разбросом |

- Стратегии «только база» не используют Redis для холдов вовсе, чтобы сравнение было честным.
- Версию строки ведёт триггер (миграция 00012) при любом изменении места: холд, освобождение, продажа, возврат. Колонка `version` была в схеме с 00002, но до сих пор её никто не обновлял.
- Каждая стратегия покрыта тестом инварианта: 200 параллельных покупателей на одно место и пересекающиеся наборы мест.
- Для оптимистичной есть детерминированный тест повтора при конфликте версий. Мутационная проверка: без условия на версию одно место продаётся трижды, тест это ловит.

### Метрики

У api появился `/metrics` (Prometheus, официальный клиент — Prometheus в стеке CLAUDE.md):
- `dd_booking_attempts_total{strategy, result, reject_by}` — исход попытки и кто отказал: Redis или база;
- `dd_booking_retries_total{strategy}` — повторы оптимистичной стратегии;
- `dd_booking_attempt_seconds{strategy, result}` — время оформления заказа, корзины до 60 с;
- `dd_booking_redis_gate_opened_total` — срабатывания предохранителя (ниже).

Наружу `/metrics` не публикуется: nginx проксирует только `/v1`. Prometheus в Compose теперь собирает метрики api.

### Стенд эксперимента

- `cmd/loadseed` создаёт покупателей с сессиями и события кодом модулей — тем же, что в продукте. После прогона проверяет инвариант по данным и строит отчёт: CSV, таблицы и SVG-графики.
- Сессии без кода выдаёт `identity.IssueBuyerSession`. Метод только для доверенных инструментов рядом с базой, через HTTP он недоступен.
- `loadtest/booking.js` — сценарии k6 one-seat и hall с общим моментом старта.
- `loadtest/run.sh` — серия прогонов, `loadtest/redis-failure.sh` — отказ Redis в середине прогона.
- Пул соединений api с базой в эксперименте задаётся явно (32) и одинаков для всех стратегий. В продукте он по-прежнему из `DATABASE_URL`.

Результаты и разбор — [`docs/experiments/2026-10-booking-strategies`](../experiments/2026-10-booking-strategies/README.md).

### Итоги эксперимента

- **Двойных броней — ноль** во всех 60 прогонах, включая отказ Redis.
- **Redis + БД — самая быстрая** на всех уровнях. На одном месте при 5000 покупателях p95 3,4 с против 5,7 с (оптимистичная) и 8,1 с (пессимистичная). В зале на 1000 мест — до 1,5 раза больше захватов в секунду. Все отказы на одном месте отсекает Redis.
- **Оптимистичная быстрее пессимистичной**, и почти без повторов. Проигравшие видят «занято» при чтении и уходят без ожидания блокировки. Гипотеза о массовых откатах на высокой конкуренции на нашем стенде не подтвердилась: пул соединений растягивает приход запросов к базе.
- **Общий путь запроса — предел для всех.** Сессия, ключ идемпотентности и три чтения дают рост задержки с нагрузкой и у Redis + БД.

### Продукт: Redis + БД с предохранителем

В продукте остаётся `redis`. Эксперимент с отказом Redis нашёл и исправил одну проблему и нашёл вторую.

1. **Исправлено: потеря заказов при отказе Redis.**
   - Холды ждали таймаутов клиента Redis (3–4 с на вызов), запросы копились в очередь и обрывались по `WriteTimeout` сервера. База успевала оформить 864 заказа, а покупатели увидели успех только у 178.
   - Теперь у вызовов Redis для холдов бюджет 500 мс. После ошибки фильтр выключается на 5 с, и заказы сразу идут в базу.
   - Итог: каждый созданный заказ доходит до покупателя (659 из 659), корректность прежняя.
   - При обычной нагрузке до 5000 одновременных покупателей предохранитель не срабатывал.
2. **Найдено, исправлено в ADR 018: сессии покупателей в Redis.**
   - При отказе Redis не проходит проверка сессии, это все оставшиеся ошибки прогона.
   - Захват мест от Redis больше не зависит, а вход — зависит.
   - Предлагаемое исправление — отдельным решением, потому что меняет модель безопасности:
     - короткий таймаут на чтение сессии;
     - кэш недавно проверенных сессий в памяти процесса на 30–60 с.
   - Цена кэша: отозванная сессия остаётся действительной до этого срока на других экземплярах api.

## Альтернативы

- **Оптимистичная стратегия в продукте.** Почти не уступает при малой нагрузке и не требует Redis. Но на пике она медленнее Redis + БД в 1,7 раза, а Redis в стеке уже есть для холдов с TTL (правило 2).
- **Пессимистичная в продукте.** Самая медленная на пике. Остаётся режимом работы при отказе Redis: `HoldSeats` и есть путь Redis + БД без фильтра.
- **Только Redis, без проверки в базе.** Быстрее, но тогда истина о брони в Redis, нарушается правило 2, и рассинхрон при потере Redis надо разбирать отдельно. ADR 011 это уже отверг. Эксперимент показал, что проверка в базе после фильтра стоит немного.
- **SERIALIZABLE вместо явных блокировок.** Не входило в спецификацию эксперимента. Даёт те же откаты, что оптимистичная стратегия, но без контроля над повтором.
- **Повторять эксперимент на отдельных машинах для k6 и api.** Честнее для абсолютных чисел, но у дипломного проекта один стенд. Сравнение стратегий на одном стенде корректно, ограничения описаны в отчёте.

## Следствия

- Новая миграция 00012 (триггер версии), настройка `BOOKING_STRATEGY`, эндпоинт `/metrics`, сбор метрик api в Prometheus Compose.
- Предохранитель Redis в модуле booking и метрика его срабатываний.
- `cmd/loadseed`, `loadtest/*`, отчёт в `docs/experiments`.
- Сырые данные прогонов (`loadtest/results/raw`) в git не попадают. Всё нужное для отчёта — в `results.csv`, а серия повторяется скриптом.
- Скрипты эксперимента отказываются работать при занятом порте api и после каждого прогона проверяют, что попытки записаны нужной стратегией. Первая серия из-за этого прошла целиком на одной стратегии и была выброшена.
