# ADR 018. Проверка сессий при отказе Redis

Дата: 2026-10-02. Статус: принято.

## Контекст

Сессии хранятся в Redis (ADR 006): ключ — хеш токена, значение — участник и срок. Каждый запрос с токеном проверяет сессию в Redis.

Эксперимент ADR 017 с отказом Redis посреди продаж показал:
- захват мест после предохранителя от Redis не зависит;
- вход по сессии зависит: 6118 ошибок `load session`, покупатели не могут оформить заказ.

Новые входы без Redis невозможны в любом случае, потому что одноразовые коды тоже живут в нём. Но покупатель, который уже вошёл и открыл страницу события, должен суметь купить.

Пользователь подтвердил, что задачу решаем (2026-10-02). Бизнес-цена решения ниже: отозванная сессия какое-то время может действовать.

## Решение

**Кэш последних успешных проверок, только на случай отказа.**

- **Пока Redis отвечает**, каждая проверка, как и раньше, идёт в Redis. Отзыв сессии (выход на любом экземпляре api) действует сразу. Ответ Redis «сессии нет» удаляет её из кэша.
- **Успешная проверка** запоминается в памяти процесса: сессия и момент проверки.
- **При отказе Redis** запрос пускается по запомненной проверке, если ей не больше 10 минут и сама сессия не истекла.
- **Незнакомая или слишком старая сессия** при отказе получает `503 session_store_unavailable` с `Retry-After: 5`, а не 500 и не ожидание.
- **Выход** удаляет сессию из кэша своего процесса сразу.

**Предохранитель.** Тот же, что у холдов мест. Он вынесен в `internal/platform/redis.Gate` и общий для booking и identity:
- бюджет проверки в Redis — 300 мс;
- после ошибки Gate открыт 5 с, и проверки сразу идут в кэш, не ожидая таймаутов;
- отмена самого запроса Gate не открывает.

**Объём кэша.** До 200 000 сессий на процесс, около 60 МБ. При переполнении вытесняется произвольная запись.

**Метрики:**
- `dd_identity_session_gate_opened_total` — переходы на кэш;
- `dd_identity_session_stale_hits_total` — запросы, пропущенные по кэшу.

### Цена решения

Отозванная сессия может пройти, только если выполнены все три условия:
- Redis сейчас недоступен;
- выход был сделан на *другом* экземпляре api;
- этот экземпляр проверял сессию не больше 10 минут назад.

Во время самого отказа выход не записывается нигде: удалить ключ в недоступном Redis нельзя. Так что окно риска — сессии, отозванные незадолго до отказа. Это меньше, чем обсуждавшийся вариант «кэш на минуту всегда»: там задержка отзыва была бы при любой работе Redis.

10 минут — значение по умолчанию: оно перекрывает время от открытия страницы события до оплаты. Это бизнес-параметр: короче — безопаснее, но больше покупателей увидят «вход временно недоступен» при отказе.

## Альтернативы

- **Кэш на 30–60 с всегда, до похода в Redis.** Меньше нагрузки на Redis, но отзыв сессии задерживается всегда, а не только при отказе. Redis не узкое место (ADR 017), поэтому выигрыш не нужен.
- **Самоподписанные токены (JWT) без хранилища.** Проверка без Redis вообще, но отзыв требует списка отозванных — в том же Redis. Это переделка входа и формата токенов ради редкого сценария.
- **Сессии в PostgreSQL.** Одним источником отказа меньше, но лишний запрос в базу на каждый запрос — к той самой базе, которая под нагрузкой при старте продаж.
- **Реплика Redis (Sentinel).** Правильный ход для эксплуатации, но это инфраструктура, а не код, и она не защищает от отказа на время переключения. Решение в коде нужно и с репликой.

## Следствия

- **Проверено экспериментом.** Повтор прогона с отказом Redis (ADR 017, 2000 покупателей, 3 прогона):
  - ни одной ошибки;
  - продано 984 места в среднем — столько же, сколько при работающем Redis;
  - p50 1,6 с против 1,5 с;
  - около 2 200 запросов за прогон прошли по кэшу.
- **Тесты:**
  - отозванная сессия при работающем Redis отклоняется сразу, даже если она в кэше;
  - при отказе знакомая сессия проходит, незнакомая получает быстрый `ErrUnavailable`;
  - лимиты возраста и срока;
  - выход забывает сессию;
  - HTTP 503 с `Retry-After`.
  - Мутационные проверки: без кэша падает тест отказа, кэш до Redis — тест отзыва.
- **k6.** В сценарии появился разогрев `WARMUP=1`: покупатель открывает профиль до старта продаж. Скрипт отказа Redis использует его по умолчанию.
- **Кэш живёт в процессе.** После перезапуска api во время отказа Redis он пуст, и все запросы с токеном получают 503 до восстановления Redis.
