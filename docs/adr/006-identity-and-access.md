# ADR 006. Идентификация и доступ

Статус: принято, 2026-09-28

## Контекст

В системе четыре вида участников (`docs/spec.md`):

- **администратор платформы** — наш сотрудник, заводит организаторов после договора;
- **организатор** — один вход на организатора;
- **контролёр** — сканирует билеты на входе без учётной записи;
- **покупатель** — входит по телефону и SMS-коду.

Нужны вход без паролей (быстро для покупателя, меньше рисков для нас), мгновенный отзыв доступа и изоляция арендаторов на уровне API.

## Решение

1. **Никаких паролей: вход по одноразовому коду.**
   - Покупатель получает код по SMS, организатор и администратор — по email.
   - Код — 6 цифр, живёт 5 минут в Redis, даёт не больше 5 попыток ввода.
   - Число запросов кода ограничено по адресату и по IP, иначе нас можно разорить отправкой SMS.
   - Отправка скрыта за интерфейсами. В разработке и тестах код пишется в лог, реальные SMS- и email-провайдеры подключаются отдельно.
2. **Сессии — непрозрачные токены в Redis**, а не JWT.
   - Токен — 32 случайных байта. В Redis хранится его SHA-256 с данными сессии: кто, роль, арендатор. TTL — 30 дней у покупателя, 12 часов у организатора и администратора.
   - Выход и отзыв удаляют ключ и действуют мгновенно.
   - Проверка — один запрос в Redis, это дешевле, чем кажется, и не требует инфраструктуры ключей.
3. **Роль и арендатор берутся из сессии, а не из запроса.** Middleware кладёт в контекст `organizer_id` сессии, и все запросы к данным организатора фильтруются по нему. Идентификатор организатора в URL или теле запроса для авторизации не используется. Так закрывается следствие из ADR 005: от чтения чужих данных защищает код.
4. **Администраторы платформы задаются списком email в конфигурации** (`ADMIN_EMAILS`). Для команды из одного-двух человек таблица и интерфейс управления администраторами не нужны.
5. **Доступ сканера — отдельный токен на событие.** Организатор создаёт его в кабинете, контролёр открывает ссылку. Токен разрешает только проверку билетов одного события и отзывается удалением. Устройство при этом получает идентификатор для журнала сканирований.
6. **Организатора создаёт отдельная операция** в модуле catalog. Сейчас её вызывает админка, в будущем её вызовет форма самостоятельной регистрации без изменения модели данных.

## Альтернативы

- **JWT.** Не требует хранилища, но токен нельзя отозвать до истечения срока, а для организатора с доступом к деньгам это существенно. Для отзыва пришлось бы вести чёрный список в Redis, и выигрыш исчезает. Отклонено.
- **Пароли.** Хранение, сброс и утечки паролей плюс лишний шаг для покупателя. Отклонено.
- **Внешний провайдер идентификации** (Keycloak, Auth0 и подобные). Лишний сервис или внешняя зависимость для четырёх простых сценариев входа. Отклонено.
- **Учётные записи для контролёров.** Организатору пришлось бы управлять пользователями ради одного вечера работы на входе. Отклонено: ссылки сканера проще и отзываются так же.

## Следствия

- Redis становится обязательной зависимостью входа: при его недоступности вход и проверка сессий не работают. Это приемлемо, потому что без Redis не работают и холды мест.
- Таблица `organizer_members` из ADR 005 пока хранит только владельца. Роли `manager` и `controller` зарезервированы и понадобятся, если появятся сотрудники.
- SMS-провайдер — отдельное будущее решение с учётом стоимости SMS. До него вход покупателя работает через заглушку.
