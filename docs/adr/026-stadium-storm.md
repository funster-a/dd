# ADR 026. Штурм стадиона: сводка занятости в памяти и скорость очереди

Дата: 2026-10-05. Статус: принято.

## Контекст

Этап 3 плана развития (spec.md) заканчивается экспериментом «штурм стадиона». Его первые прогоны показали два узких места чтения занятости (ADR 024):
- **Сектор считал весь стадион.** Режим `?section=` вместе с местами сектора возвращал сводку по всем секторам. Это `GROUP BY` по 33 тысячам строк мест — около 14 мс процессора базы — на каждый открытый сектор.
- **Сводку пересчитывал каждый запрос.** Каждая попытка каждого покупателя открывает план, и в первые секунды продаж таких запросов тысячи. Singleflight объединял только запросы, пришедшие в одну и ту же миллисекунду.

## Решение

### Сектору — только его счётчик

В режиме `?section=` поле `sections` содержит один сектор, посчитанный по индексу. Сайт помнит последнюю сводку плана и не затирает её ответом по сектору.

### Сводка — из памяти на секунду

- **Где живёт.** Экземпляр api хранит последний ответ `?view=summary` по каждому событию `AVAILABILITY_SUMMARY_TTL` (по умолчанию 1 с, `0` — без кэша).
- **Что кэшируется.** Только сводка для плана. Места открытого сектора и заказ всегда идут в базу.
- **Почему устаревание безвредно.** Секундная задержка на плане ничего не ломает: место проверяет заказ. В худшем случае покупатель увидит в секторе, что свободных мест меньше, чем показал план.
- **Почему в памяти, а не в Redis.** На экземпляр получается одно чтение базы в секунду; при N экземплярах — N. Поход в Redis стоил бы почти столько же, сколько сам кэш экономит.
- **Объём.** Кэш хранит по одной сводке на событие и чистит записи старше TTL.

### Скорость очереди на стадионе

Эксперимент подтвердил рекомендацию ADR 020: скорость пропуска подбирается по ёмкости. На стенде путь покупателя стадиона — сводка, сектор и заказ, при отказе всё снова.
- На один экземпляр api комфортно 150 покупателей в секунду.
- При 300 в секунду время ответа растёт вчетверо.

Значение по умолчанию (`QUEUE_ADMIT_PER_SECOND=50`) не меняется: на продакшене ёмкость считают по метрикам, как описано в ADR 020 и ADR 023.

## Результаты эксперимента

Концерт на Центральном стадионе, 33 509 мест, 5 000 покупателей в момент старта, один экземпляр api, 4 vCPU. Разбор — [`docs/experiments/2026-10-stadium-storm`](../experiments/2026-10-stadium-storm/README.md).

| Вариант | Заказ p95 | Последняя покупка | Ушли без билета | Двойных броней |
|---|---:|---:|---:|---:|
| Без очереди, без кэша сводки | 14,5 с | 33 с | 22 | 0 |
| Без очереди | 11,0 с | 24 с | 18 | 0 |
| Очередь, 150 в секунду | 1,06 с | 35 с | 0 | 0 |
| Очередь, 300 в секунду | 4,5 с | 27 с | 22 | 0 |

- **Кэш сводки:** заказ на 24% быстрее, спрос удовлетворён на 9 секунд раньше.
- **Очередь на 150 в секунду:** заказ в 10 раз быстрее, в 8 раз меньше отказов «место заняли», билеты получили все.
- **Корректность и устойчивость:** ноль двойных броней, ноль ответов 5xx и таймаутов во всех восьми прогонах.
- **Данные:** весь путь покупателя — 13–15 КБ.

## Альтернативы

- **Материализованная сводка в базе.** Счётчики по секторам обновляются в той же транзакции, что и холд. Сводка становится точной и бесплатной, но каждый заказ начинает спорить за строку счётчика своего сектора. Это новая горячая точка ровно там, где решается главный инвариант.
- **Сводка в Redis по событиям холда.** Быстро, но нужно сверять её с базой при отказе Redis. Кэш в памяти на секунду проще и даёт почти тот же эффект.
- **Отдавать сводку через CDN.** `Cache-Control: public, max-age=2` уже стоит (ADR 024). На продакшене CDN снимет и эти запросы, а кэш в api защищает базу, когда CDN нет или он промахнулся. Это этап 5, «читающий контур».
- **Больше генератора нагрузки.** 10 000 покупателей не поместились в память k6 на стенде. Проверить полную распродажу можно с отдельной машиной для k6 — это в планах этапа 6.

## Следствия

- **Настройка:** `AVAILABILITY_SUMMARY_TTL`, в README.
- **API:** в режиме `?section=` поле `sections` содержит только запрошенный сектор.
- **Нагрузочный стенд:** сценарий `loadtest/stadium.js`, серия `loadtest/storm.sh`, отчёт `loadseed storm-report`.
- **Тесты:** сводка из кэша устаревает, а места сектора нет; без кэша сводка свежая; режим сектора считает только свой сектор.
